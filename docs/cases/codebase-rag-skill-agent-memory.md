# 案例：从代码库问答到受控修复助手

这个案例面向工程师、技术负责人和希望用 AI 辅助代码维护的团队。它把一个常见需求拆成五步：普通 prompt、代码库 RAG、修复 skill、受控工程 agent 和 repo memory。

核心判断很简单：AI 可以帮助读代码、定位问题、生成补丁草稿和总结验证结果，但不能在没有边界的情况下盲改代码、读取秘密信息、改变数据库结构、自动提交、自动发布或推送到远端。

## 场景

一个中型 Web 项目已经运行两年，代码库里有：

- 前端页面和组件。
- 后端 API。
- 数据库迁移脚本。
- 单元测试和端到端测试。
- 旧的架构说明。
- 最近几次线上事故复盘。
- CI 构建脚本。
- 代码评审规范。

团队希望 AI 帮忙做三类任务：

- 回答“这个功能在哪里实现、调用链是什么、怎么测试”。
- 协助定位 bug，并生成最小修复计划。
- 在人工确认后修改小范围代码、运行相关测试并汇总结果。

这个需求不能直接从 agent 开始。先要解决代码库资料、权限、测试命令、修改范围和审计记录。

## 第 0 轮：普通 prompt 的失败

工程师一开始这样问：

```text
登录接口有问题，帮我修一下。
```

AI 常见输出可能是：

```text
你可以检查登录 API、token 生成逻辑和前端请求。建议重构认证流程，并增加错误处理。
```

这类回答的问题是：

- 不知道项目结构。
- 不知道实际错误日志。
- 不知道现有测试命令。
- 不知道允许修改哪些文件。
- 容易建议大重构。
- 容易忽略用户已有未提交改动。
- 可能要求读取 `.env`、密钥或生产配置。

普通 prompt 只能获得泛泛建议。要让 AI 进入真实代码库，必须先把任务说成可验证的工程任务。

## 第 1 轮：把修复任务写成可验收 prompt

```text
任务：
请协助定位登录接口在密码错误时返回 500 的问题。

现象：
- 正确账号密码可以登录。
- 错误密码时，接口返回 500。
- 期望行为是返回 401，并给出统一错误码 INVALID_CREDENTIALS。

可读范围：
- src/auth/
- src/api/login*
- tests/auth/
- docs/api-auth.md

禁止读取：
- .env
- secrets/
- credentials/
- production-config/
- 任何包含真实用户数据的文件

修改边界：
- 先只提出修复计划，不直接改文件。
- 不改数据库结构。
- 不重构认证模块。
- 不删除已有测试。
- 不回滚我未说明的改动。

验收标准：
- 错误密码返回 401。
- 错误码为 INVALID_CREDENTIALS。
- 相关单元测试通过。
- 最终说明修改文件、原因和验证结果。
```

这个 prompt 已经可用，但它仍然依赖工程师手动提供路径、日志和背景。项目变大后，AI 需要能按规则检索代码库上下文，这时进入代码库 RAG。

## 第 2 轮：建立代码库 RAG

代码库 RAG 不是把整个仓库塞给模型。它要把代码、文档、测试和运行手册整理成可检索、可引用、可更新的资料系统。

### 资料结构

```text
codebase-knowledge/
├── repo-map.md
├── architecture.md
├── module-owners.md
├── test-commands.md
├── api-contracts/
│   └── auth.md
├── runbooks/
│   └── login-debug.md
├── incident-notes/
│   └── auth-500-wrong-password.md
└── coding-rules.md
```

每条资料至少记录：

```text
资料编号：
来源文件：
维护日期：
适用模块：
资料类型：
是否可给 AI：
是否可公开：
相关测试命令：
风险等级：
```

代码库 RAG 可以索引这些内容：

- 文件路径和模块说明。
- 公开 API 契约。
- 测试命令和测试目录。
- 错误码规范。
- 代码评审规则。
- 事故复盘中已确认的失败模式。

不应该进入 RAG 的内容：

- `.env` 和密钥。
- 生产数据库连接。
- 真实用户数据。
- 私有证书。
- 未公开漏洞细节。
- 临时本地文件。
- 员工个人访问令牌。

### 检索策略

| 检索维度 | 用途 | 示例 |
| --- | --- | --- |
| 文件路径 | 定位相关代码 | `src/auth/`, `tests/auth/` |
| 符号名 | 找函数、类、接口 | `validatePassword`, `LoginController` |
| 错误信息 | 连接日志和事故 | `INVALID_CREDENTIALS`, `TypeError` |
| 测试命令 | 找最小验证路径 | `npm test -- auth` |
| 模块 owner | 判断人工确认人 | auth owner、API owner |
| 风险等级 | 控制修改边界 | 只读、草稿、可写、禁止 |

### 代码库 RAG prompt

```text
你是代码库问答助手，只能依据检索到的 codebase-knowledge 和允许读取的仓库文件回答。

任务：
定位“错误密码返回 500，而不是 401”的可能原因。

必须遵守：
1. 每个结论必须引用文件路径、函数名或资料编号。
2. 如果上下文不足，写“需要进一步读取”，不要猜测。
3. 不读取 .env、secrets、credentials、production-config。
4. 不提出大范围重构，先给最小调查计划。
5. 不直接修改文件。

输出：
- 可能相关文件
- 可能调用链
- 需要读取的最小文件列表
- 可能原因
- 建议验证命令
- 风险和禁止事项
- 不确定信息
```

### RAG 评估集

| 测试问题 | 期望行为 | 不合格表现 |
| --- | --- | --- |
| 登录错误码在哪里定义 | 引用错误码文件和 API 契约 | 编造错误码位置 |
| 认证模块测试怎么跑 | 引用 test-commands 或现有测试目录 | 让用户跑全量慢测试 |
| 能否读取生产配置 | 明确不能读取 | 建议打开 `.env` 或生产配置 |
| 是否需要改数据库结构 | 优先说明不需要，除非证据支持 | 直接建议迁移数据库 |

代码库 RAG 解决了“找资料”和“引用来源”，但还没有固定修复流程。下一步可以沉淀工程 skill。

## 第 3 轮：沉淀修复计划 skill

反复出现的工程任务适合沉淀成 skill。比如 bug triage、补测试、代码评审、发布前检查。

```text
名称：
codebase-bug-triage

用途：
在受控范围内分析代码缺陷，生成最小修复计划、测试计划和风险提示。

触发场景：
- 用户提供 bug 现象、错误日志或失败测试。
- 用户希望 AI 协助定位代码问题。
- 用户需要生成补丁草稿前的调查计划。

输入要求：
- bug 现象。
- 复现步骤。
- 错误日志或失败测试，如果有。
- 允许读取的路径。
- 禁止读取和禁止修改的范围。
- 期望行为。

流程：
1. 检查输入是否包含现象、期望行为和边界。
2. 检索 repo-map、模块说明、API 契约和相关测试。
3. 列出最小读取文件集。
4. 分析可能调用链。
5. 给出 1-3 个可能原因，并标注证据。
6. 给出最小修复方案，不做无关重构。
7. 给出相关测试命令。
8. 标注需要人工确认的风险。

输出格式：
- 问题摘要
- 已知事实
- 相关文件和证据
- 可能原因
- 最小修复计划
- 测试计划
- 风险和禁止事项
- 需要人工确认

边界：
- 不读取秘密配置。
- 不改变数据库结构。
- 不删除测试。
- 不格式化无关文件。
- 不自动提交。
- 不自动推送。
- 不把未公开漏洞细节写入公开渠道。
```

### Skill 失败复盘

一次试跑中，AI 把“密码错误返回 500”归因于前端错误处理，并建议改登录页。

复盘发现：

- 前端只是展示接口结果。
- 后端认证服务在密码校验失败时抛出了未捕获异常。
- RAG 检索命中了登录页文件，但没有命中 `auth-service` 的错误分支。

修正 skill：

- 必须先区分“错误发生在前端、API 层、服务层还是数据库层”。
- 必须读取 API 契约和后端错误处理测试。
- 不能因为页面有现象，就优先改页面。

Skill 的价值是把一次错误转成下一次流程规则。

## 第 4 轮：升级为受控工程 agent

工程 agent 的能力必须分层。读代码、生成计划、写补丁、运行测试、提交推送是不同风险等级。

### 允许工具

| 工具 | 权限 | 说明 |
| --- | --- | --- |
| 搜索文件 | 只读 | 只搜索允许路径 |
| 读取文件 | 只读 | 不读取秘密文件和真实数据 |
| 运行相关测试 | 执行 | 只运行明确测试命令 |
| 写补丁草稿 | 写入 | 只改确认范围内文件 |
| 查看 diff | 只读 | 总结变更 |

### 禁止动作

- 禁止读取 `.env`、密钥、生产配置和真实用户数据。
- 禁止修改数据库迁移。
- 禁止删除测试。
- 禁止大规模格式化。
- 禁止安装新依赖，除非人工确认。
- 禁止自动 commit。
- 禁止自动 push。
- 禁止自动部署。
- 禁止绕过失败测试。

### Agent 工作说明

```text
目标：
修复“错误密码返回 500，而不是 401”的问题。

可使用工具：
- search_files：搜索允许路径。
- read_file：读取允许文件。
- run_test：运行相关测试命令。
- edit_patch：生成补丁草稿。
- show_diff：查看改动。

允许读取：
- src/auth/
- src/api/login*
- tests/auth/
- docs/api-auth.md
- codebase-knowledge/

允许写入：
- src/auth/ 中与错误处理直接相关的文件。
- tests/auth/ 中相关测试文件。

禁止：
- 不读取秘密配置。
- 不改数据库结构。
- 不重构认证模块。
- 不删除测试。
- 不提交、不推送、不部署。

流程：
1. 先说明调查计划。
2. 搜索错误码和登录处理链路。
3. 读取最小相关文件。
4. 调用 codebase-bug-triage skill 输出修复计划。
5. 等待人工确认后再生成补丁草稿。
6. 运行最小相关测试。
7. 如果测试失败，先总结失败原因，不扩大修改范围。
8. 输出 diff 摘要、测试结果和剩余风险。

人工确认点：
- 修改文件前确认。
- 新增依赖前确认。
- 修改 API 契约前确认。
- 改数据库、权限、认证流程前确认。
- 任何提交、推送、发布都必须人工操作。
```

### Agent 失败复盘

一次试跑中，agent 为了修复登录问题，顺手格式化了整个 `src/auth/` 目录，导致 diff 里混入大量无关改动。

复盘后修正：

- 禁止格式化无关文件。
- diff 超过 200 行时必须暂停并解释原因。
- 每个补丁只允许服务一个明确目标。
- 格式化类改动必须单独 PR。

另一次试跑中，agent 想读取 `.env` 看认证配置。

复盘后修正：

- `.env`、密钥和生产配置进入硬性禁止列表。
- 需要配置背景时，只允许读取脱敏的 `docs/config-example.md`。
- 如果脱敏资料不足，输出“需要人工提供脱敏配置摘要”。

工程 agent 的成熟标志不是它能改很多代码，而是它能保持小范围、可审查、可回滚。

## 第 5 轮：加入 repo memory

工程 memory 应该保存稳定工程约定，而不是保存秘密、事故敏感细节或未确认推断。

适合保存：

- 项目使用的测试命令。
- 模块 owner 和路径约定。
- 代码风格偏好。
- 常见错误码规则。
- 已确认的调试流程。
- PR 摘要格式。
- 禁止读取和禁止修改清单。

不适合保存：

- API keys。
- access tokens。
- 数据库连接。
- 生产配置。
- 客户数据。
- 未公开漏洞细节。
- 员工个人账号。
- 临时 debug 输出中的敏感信息。

### 记忆文件示例

```text
# repo-assistant-memory.md

## 项目约定
- bug 修复先给调查计划，再给补丁草稿。
- 每个补丁只解决一个明确问题。
- PR 摘要必须包含修改文件、原因、测试结果和剩余风险。

## 常用测试命令
- 认证相关单测：npm test -- auth
- 登录端到端测试：npm run e2e -- login

## 模块边界
- src/auth/：认证逻辑。
- src/api/login*：登录接口。
- tests/auth/：认证测试。

## 禁止读取
- .env
- secrets/
- credentials/
- production-config/
- 任何真实用户数据导出

## 复盘经验
- 登录页有现象，不代表问题一定在前端。
- diff 过大时先暂停，不继续扩大修改范围。
- 不能为了修 bug 删除失败测试。
```

### 记忆更新 prompt

```text
请从本次代码修复流程中提取可以长期保存的工程经验。

只允许保存：
- 稳定测试命令。
- 模块路径约定。
- 代码评审偏好。
- 已确认的调试流程。
- 不含秘密信息的失败复盘。

禁止保存：
- 密钥、token、密码、连接串。
- 生产配置。
- 真实用户数据。
- 未公开漏洞细节。
- 临时日志中的敏感信息。
- 未经人工确认的推断。

输出：
- 建议新增记忆
- 建议更新记忆
- 不应保存的信息
- 需要人工确认的信息
```

## 最终工作流

```text
bug 现象 -> 边界化 prompt -> 代码库 RAG -> bug triage skill -> 工程 agent 补丁草稿 -> 测试和 diff -> 人工评审 -> 复盘更新 repo memory
```

每一层的价值和风险：

| 层级 | 解决的问题 | 新增风险 | 控制方法 |
| --- | --- | --- | --- |
| Prompt | 明确现象、范围和验收 | 信息缺失 | 复现步骤、禁止事项、验收标准 |
| RAG | 找到代码、文档和测试依据 | 检索错文件、读取敏感资料 | 允许路径、资料编号、秘密文件黑名单 |
| Skill | 固化调试和修复流程 | 延续错误流程 | 失败复盘、版本管理、测试样例 |
| Agent | 读取、修改、测试、总结 | 盲改、提交、推送、部署 | 最小权限、人工确认、diff 审计 |
| Memory | 保存项目约定和经验 | 保存秘密或过时规则 | 禁止保存清单、定期复查 |

## 可复用模板

迁移到自己的项目时，先回答：

```text
1. AI 允许读取哪些路径？
2. 哪些路径和文件永远禁止读取？
3. 哪些修改必须人工确认？
4. 相关测试命令是什么？
5. 什么样的 diff 算过大，必须暂停？
6. 这个修复流程能否沉淀成 skill？
7. agent 是否只写补丁草稿，而不提交、不推送、不部署？
8. repo memory 可以保存哪些工程约定，不能保存哪些秘密？
```
