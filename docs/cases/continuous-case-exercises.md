# 连续案例练习与复盘评分表

本页把三条连续案例转成可自学、可课堂使用、可团队复盘的练习包：

- [客户反馈知识库到可治理行动助手](rag-skill-agent-memory.md)
- [教学资料库到受控助教助手](teaching-rag-skill-agent-memory.md)
- [代码库问答到受控修复助手](codebase-rag-skill-agent-memory.md)
- [连续案例课堂试跑版](continuous-case-classroom-run.md)
- [连续案例团队试点版](continuous-case-team-pilot.md)
- [连续案例样例库](continuous-case-samples.md)
- [连续案例课堂投影短版](continuous-case-slide-brief.md)

这三条案例都走同一条主线：普通 prompt -> RAG -> skill -> agent -> memory。练习的重点不是记住概念，而是判断什么时候该升级、升级后新增了什么风险、怎样用证据和边界把系统管住。

## 使用方式

自学版：

1. 先完整阅读一条连续案例。
2. 按本页对应练习完成一份 2-4 页设计稿。
3. 用评分表自评，低于 70 分时只修改最影响真实使用的 2 个问题。

课堂版：

1. 课前分组阅读不同案例。
2. 课堂上每组只展示失败点、升级理由、权限边界和验收证据。
3. 组间互评时优先问“证据在哪里”和“哪些动作必须人工确认”。

团队复盘版：

1. 把案例背景替换成团队真实但已脱敏的任务。
2. 保留 RAG、skill、agent、memory 四层检查。
3. 输出一份可以进入试点的最小工作说明，而不是一次性做完整系统。

## 通用提交物

每条案例练习建议提交这些材料：

- 一段失败 prompt 和失败原因。
- 一段边界清楚的改进 prompt。
- 一份 RAG 资料结构和 5 条检索评估样例。
- 一张 skill/card。
- 一份 agent 工作说明。
- 一份 memory 保存与禁止保存清单。
- 一份复盘记录，说明本轮会把什么经验固化回知识库、skill 或 memory。

## 通用评分表

| 维度 | 分值 | 合格证据 | 危险信号 |
| --- | --- | --- | --- |
| 问题定义 | 15 | 场景、目标、输入、输出和验收标准清楚 | 只写“帮我总结”“帮我修复” |
| RAG 设计 | 20 | 资料结构、权限、引用、更新频率和评估集完整 | 把知识库当成文件堆 |
| Skill 沉淀 | 20 | 触发场景、输入要求、流程、边界和失败复盘清楚 | 只是把 prompt 换了名字 |
| Agent 边界 | 20 | 工具权限、禁止动作、人工确认点和日志要求明确 | 允许自动发送、提交、发布或改权限 |
| Memory 治理 | 15 | 写清可保存、禁止保存、复查和删除规则 | 保存隐私、秘密、未经确认的推断 |
| 迁移价值 | 10 | 能说明怎样迁移到自己的任务 | 只复述案例，没有形成自己的流程 |

评分解释：

- 90-100 分：可以作为课堂示范或团队试点初稿。
- 75-89 分：结构基本可用，还需要补验证样例或权限边界。
- 60-74 分：能看出思路，但还不能进入真实试点。
- 60 分以下：先回到 prompt 和工作流，不急着做 agent。

## 案例一：客户反馈知识库到行动助手

适合角色：产品、运营、客服、客户成功、管理者。

### 练习目标

- 把“总结客户反馈”改成可追溯、可验收的内部分析任务。
- 设计一个不会泄露客户身份的反馈知识库。
- 把每周反馈分析沉淀成 `customer-feedback-triage` skill。
- 为行动助手写出只读、写草稿和人工确认边界。
- 判断哪些团队偏好可以进入 memory，哪些客户信息必须禁止保存。

### 课前阅读任务

1. 阅读 [客户反馈连续案例](rag-skill-agent-memory.md)。
2. 标出案例中每次升级解决的问题。
3. 找出至少 3 个不能自动化的动作。
4. 用一句话说明：如果只用普通 prompt，最容易造成什么误判。

### 分组讨论题

- 客户反馈周报最应该引用哪些证据？
- “导出慢”“导出失败”“不会导出”为什么不能简单合并？
- 高价值客户信息能否进入报告？如果能，怎样脱敏？
- 哪些建议可以进入任务草稿，哪些必须产品负责人确认？
- 如果 RAG 检索不到足够反馈，AI 应该怎样输出？
- 哪些团队偏好值得保存为长期记忆？

### 实操改写任务

把下面的弱需求改成完整工作流：

```text
请总结这周客户反馈，并告诉我产品下周应该优先做什么。
```

提交时至少包含：

1. 改进 prompt：限制资料来源、输出结构、引用要求和隐私规则。
2. RAG 资料表：列出反馈编号、来源、日期、模块、匿名化描述、隐私等级和证据链接。
3. 检索评估集：写 5 个测试问题，每个问题都说明期望行为和不合格表现。
4. Skill/card：写出 `customer-feedback-triage` 的触发场景、流程、边界和验收标准。
5. Agent 工作说明：列出允许工具、禁止动作、人工确认点和执行日志。
6. Memory 规则：写 5 条可保存内容和 5 条禁止保存内容。

### 复盘问题

- 这套流程中，哪一步最容易把推断写成事实？
- 如果反馈编号缺失，报告是否还能进入下一步？
- 是否存在“为了好看而自动生成产品承诺”的风险？
- 哪些内容应该进入知识库，哪些应该进入 memory，哪些不该保存？
- 下次试跑时最需要补的一条评估样例是什么？

### 评分表

| 维度 | 分值 | 判断标准 |
| --- | --- | --- |
| 反馈证据链 | 20 | 每个结论都能回到反馈编号或资料编号 |
| 隐私处理 | 15 | 客户、联系人、邮箱、电话和合同信息已明确脱敏或禁止保存 |
| 分类质量 | 15 | 能区分 bug、功能请求、使用误解、性能问题和需确认项 |
| Skill 可复用性 | 15 | 每周都能复用，且能记录失败复盘 |
| Agent 权限 | 20 | 只读资料、只写草稿，所有对外动作和承诺都需人工确认 |
| Memory 边界 | 15 | 只保存流程偏好和通用经验，不保存客户身份和原始投诉 |

### 可交付证据

- 一份匿名化客户反馈周报样例。
- 一张反馈知识库字段表。
- 一份 `customer-feedback-triage` skill/card。
- 一份行动助手工作说明。
- 一份本轮失败复盘和下轮评估样例。

### 常见失败点

- 把“客户很生气”当成已验证事实，而不是反馈语气。
- 把单个战略客户需求直接写成全体用户需求。
- 把 AI 建议当成产品路线图决定。
- 把原始投诉、合同金额或联系人信息保存到 memory。
- 让 agent 自动发客户邮件或自动创建正式任务。

## 案例二：教学资料库到受控助教助手

适合角色：教师、培训者、读书会主持人、企业内训负责人。

### 练习目标

- 把“帮我备课”改成基于课程目标、周次和资料编号的备课任务。
- 建立只使用允许资料和匿名化作业的教学 RAG。
- 把作业点评沉淀成 `teaching-feedback-draft` skill。
- 为助教 agent 写清只写草稿、不直接评分、不直接发送的边界。
- 设计不会给学员贴长期标签的 teaching memory。

### 课前阅读任务

1. 阅读 [教学资料库连续案例](teaching-rag-skill-agent-memory.md)。
2. 对照 [教学版本材料包](../teaching-kit.md)，标出第 3 周课程需要哪些材料。
3. 找出案例中所有和学员隐私有关的禁止事项。
4. 写出一个你认为最容易被 AI 误写的反馈句子，并改成可执行建议。

### 分组讨论题

- 为什么助教 agent 不应该直接给正式分数？
- 匿名化作业是否一定可以进入知识库？还需要检查什么？
- “评价作业文本”和“评价学员能力”边界在哪里？
- 第 3 周课程能否提前展开 agent 自动执行？为什么？
- 课程 memory 应保存共性误解，还是保存单个学员表现？
- 讲师确认点应该放在反馈生成前、生成后，还是发送前？

### 实操改写任务

把下面的弱需求改成完整工作流：

```text
请帮我准备一节 RAG 和 agent 的课，并点评学员作业。
```

提交时至少包含：

1. 改进 prompt：限定周次、学习目标、资料来源、输出结构和隐私边界。
2. 教学 RAG 资料结构：列出资料编号、周次、资料类型、是否可给学员、是否可给 AI、维护日期。
3. 检索评估集：写 5 个测试问题，覆盖越级讲解、匿名化作业、正式评分和资料引用。
4. Skill/card：写出 `teaching-feedback-draft` 的输入要求、流程、边界和验收标准。
5. Agent 工作说明：列出允许读取、允许写入、禁止动作、人工确认点和日志要求。
6. Memory 规则：写清课程经验、讲师偏好、共性误解和禁止保存的个人信息。

### 复盘问题

- 反馈草稿是否每条都指向具体作业文本？
- 是否出现了人格、智力、态度或长期能力判断？
- 是否有任何资料越过了当前课程周次？
- 讲师能否根据输出快速判断是否可发给学员？
- 哪些共性误解值得下次课开场复盘？

### 评分表

| 维度 | 分值 | 判断标准 |
| --- | --- | --- |
| 教学目标一致性 | 15 | 每个课堂活动都能对应学习目标 |
| 资料引用 | 15 | 备课和反馈能引用课程资料编号 |
| 隐私保护 | 20 | 不读取、不输出实名、联系方式、成绩和未授权作业 |
| 反馈质量 | 20 | 指向具体文本，给出可直接修改的建议 |
| Agent 边界 | 15 | 只写草稿，正式评分、发送反馈和公告均需讲师确认 |
| Memory 治理 | 15 | 只保存课程经验和匿名化共性问题，不保存个人标签 |

### 可交付证据

- 一份 90 分钟备课草稿。
- 一份匿名化作业反馈草稿。
- 一张教学资料权限表。
- 一份 `teaching-feedback-draft` skill/card。
- 一份助教 agent 工作说明。
- 一份课程复盘 memory 更新建议。

### 常见失败点

- 把没有学过的概念提前塞进课堂。
- 用真实作业、姓名或成绩做示例。
- 反馈写成“你逻辑不行”，而不是指出具体可修改文本。
- 让 agent 自动给分或自动发给学员。
- 把单个学员的失误保存成长期标签。

## 案例三：代码库问答到受控修复助手

适合角色：工程师、技术负责人、代码评审者、工程效能团队。

### 练习目标

- 把“帮我修一下”改成包含现象、范围、禁止事项和验收标准的工程任务。
- 设计不会读取秘密配置和真实用户数据的代码库 RAG。
- 把 bug 定位流程沉淀成 `codebase-bug-triage` skill。
- 为工程 agent 写出最小读取、最小修改、测试和 diff 审计规则。
- 设计只保存工程约定、不保存秘密的 repo memory。

### 课前阅读任务

1. 阅读 [代码库问答连续案例](codebase-rag-skill-agent-memory.md)。
2. 标出所有“禁止读取”和“禁止修改”的内容。
3. 写出一个你所在项目中适合 AI 协助的低风险 bug 任务。
4. 写出一条 agent 必须暂停并请求人工确认的条件。

### 分组讨论题

- 代码库 RAG 应该索引代码本身，还是优先索引 repo map、测试命令和 API 契约？
- 什么情况下 AI 可以写补丁草稿？
- 为什么 `.env` 和生产配置不能作为调试捷径？
- diff 超过多少行应该暂停？标准由谁决定？
- 如果相关测试失败，agent 应该扩大修改范围吗？
- repo memory 适合保存哪些工程约定？

### 实操改写任务

把下面的弱需求改成完整工作流：

```text
登录接口有问题，帮我修一下。
```

提交时至少包含：

1. 改进 prompt：写清现象、期望行为、可读范围、禁止读取、修改边界和验收标准。
2. 代码库 RAG 资料结构：列出 repo map、API 契约、测试命令、runbook、事故复盘和编码规则。
3. 检索评估集：写 5 个测试问题，覆盖错误码位置、测试命令、秘密文件、数据库结构和相关调用链。
4. Skill/card：写出 `codebase-bug-triage` 的流程、输出格式、边界和失败复盘规则。
5. Agent 工作说明：列出搜索、读取、测试、写补丁、查看 diff 的权限。
6. Memory 规则：写清测试命令、模块边界、PR 摘要格式和禁止保存秘密。

### 复盘问题

- 是否先给调查计划，再进入修改？
- 是否有证据说明问题发生在哪一层？
- 是否避免了无关重构、大规模格式化和删除测试？
- 测试命令是否足够小，能证明本次修复？
- 最终输出是否包含修改文件、原因、验证结果和剩余风险？

### 评分表

| 维度 | 分值 | 判断标准 |
| --- | --- | --- |
| 工程任务定义 | 15 | 现象、期望行为、范围和验收标准完整 |
| 敏感文件边界 | 20 | `.env`、密钥、生产配置和真实用户数据进入硬性禁止清单 |
| 调查质量 | 15 | 先定位调用链和证据，不凭文件名猜测 |
| Skill 可复用性 | 15 | 能迁移到其他 bug，并记录失败复盘 |
| Agent 审计 | 20 | 最小修改、相关测试、diff 摘要和暂停条件明确 |
| Repo memory | 15 | 只保存工程约定、测试命令和安全边界，不保存秘密 |

### 可交付证据

- 一份 bug 调查计划。
- 一份代码库 RAG 资料清单。
- 一张 `codebase-bug-triage` skill/card。
- 一份受控工程 agent 工作说明。
- 一份测试和 diff 审计模板。
- 一份 repo memory 更新建议。

### 常见失败点

- 看到登录页有问题就先改前端。
- 为了找配置去读取 `.env`。
- 没有人工确认就修改认证流程或数据库结构。
- 为了让测试通过删除失败测试。
- 顺手格式化大量无关文件，导致 diff 不可审查。

## 横向比较练习

完成任意两条连续案例后，建议再做一次横向比较：

| 问题 | 客户反馈 | 教学资料 | 代码库 |
| --- | --- | --- | --- |
| 最核心的资料风险是什么 | 客户身份和商业信息 | 学员隐私和越权评价 | 密钥、生产配置和真实数据 |
| 最适合沉淀的 skill 是什么 | 周报分流 | 反馈草稿 | bug triage |
| Agent 最危险的动作是什么 | 对外承诺或发邮件 | 直接评分或发反馈 | 自动提交、推送、部署 |
| Memory 最该保存什么 | 报告格式和分类规则 | 课程经验和共性误解 | 测试命令和模块约定 |
| Memory 最不该保存什么 | 原始客户反馈 | 学员个人标签 | 密钥和漏洞细节 |

横向复盘问题：

- 三个案例中，哪些边界是共通的？
- 哪些边界只属于特定行业或角色？
- 哪些任务可以停留在 prompt 或 skill，不需要 agent？
- 哪些任务必须有人承担最终责任？
- 如果把其中一个案例迁移到你的工作，第一周只能做哪一个最小试点？
