# 连续案例样例库

本页提供一组虚构但贴近真实课堂和团队试点的样例，用来配合：

- [连续案例练习与复盘评分表](continuous-case-exercises.md)
- [连续案例课堂试跑版](continuous-case-classroom-run.md)
- [连续案例团队试点版](continuous-case-team-pilot.md)
- [连续案例课堂投影短版](continuous-case-slide-brief.md)

这些样例不是标准答案。本页先提供低质量、刚及格、可试点、可示范等成熟度对照，并在客户反馈、教学资料库和代码库三条主线中加入同题对照；后面提供“可模仿的中等偏好作品”，并故意保留少量缺口，方便读者学习怎样复盘、怎样继续改。

## 使用方式

自学者可以先看“提交物”，再看“点评”和“下一步修改”。

讲师可以把样例发给学员做同伴互评，要求学员指出：

- 哪些地方能进入真实试点。
- 哪些地方仍然只是课堂作业。
- 哪些权限、资料或 memory 规则还不够清楚。

团队负责人可以把样例改写成自己的试点任务卡，但必须替换资料来源、权限边界、验收标准和负责人。

## 质量层级速览

连续案例不应该只看“写得长不长”，而要看它是否能被验证、复用和安全试跑。

| 层级 | 常见表现 | 能否进入真实试点 | 主要风险 | 修改方向 |
| --- | --- | --- | --- | --- |
| 低质量 | 只有一个看似完整的 prompt，边界和资料来源空泛 | 不能 | AI 容易编造、越权、输出敏感信息 | 先补任务范围、资料范围、禁止事项和验收标准 |
| 刚及格 | 有任务、资料和边界，但评估样例、日志和负责人不足 | 只能作为课堂作业 | 真实运行时难以定位失败原因 | 补检索评估、权限矩阵、人工确认点和失败复盘 |
| 可试点 | 能限定小范围试跑，有评估样例、责任人和写回规则 | 可以做 7 天小试点 | 样例数量少，稳定性还没有证据 | 补试跑记录、失败样例、版本记录和复核耗时 |
| 可示范 | 有完整证据链、质量门槛、审计日志和迁移说明 | 可以作为团队模板 | 维护成本较高，需要持续复核 | 把真实反馈匿名化后写回教材和模板库 |

## 同题对照：客户反馈周报作业

这一组使用同一个任务：“根据本周客户反馈生成内部周报草稿”。三档写法故意放在一起，便于课堂讲评。

### 低质量版本：看起来会用 AI，但无法复查

提交物：

```text
请帮我分析本周客户反馈，找出最严重的问题，写一份周报给产品、客服和管理层。
如果有紧急问题，请给出修复建议，也可以帮我整理成任务。
以后记住这些客户的情况，下次分析时要参考历史反馈。
```

配套说明：

```text
资料都在客服系统和飞书文档里，AI 可以自己找。
输出越完整越好，最好直接能发给团队。
```

自评分：45 / 100。

为什么不合格：

- 没有说明资料是否匿名化，也没有限制客户身份、合同信息和联系人。
- 没有要求结论绑定反馈编号，模型可能把少数强烈意见写成普遍趋势。
- “整理成任务”和“直接能发给团队”把草稿流程变成了执行流程。
- Memory 规则错误，把客户情况当成可长期保存的信息。
- 没有验收标准，也没有失败后怎样复盘。

最小修改方向：

```text
1. 把资料范围改成“只读匿名化反馈 F-001 到 F-030”。
2. 把输出改成“内部周报草稿”，禁止对外发送和自动创建任务。
3. 每个结论必须引用反馈编号。
4. Memory 只能保存周报格式偏好和已确认分类规则，不能保存客户身份。
```

### 刚及格版本：课堂能通过，但还不适合团队直接试点

提交物：

```text
你是客户反馈分析助手。

资料范围：
只使用本周 30 条匿名化客户反馈。
如果资料不足，请写“资料不足”。

任务：
生成内部客户反馈周报草稿。

输出：
1. 本周主要问题。
2. 问题类型：bug / 功能请求 / 使用误解 / 其他。
3. 每类问题的建议动作。
4. 不确定信息。

禁止：
- 不输出客户名称、联系方式和合同信息。
- 不生成对外公告。
- 不承诺修复日期。
- 不自动创建任务。
```

配套说明：

```text
RAG 资料包括反馈编号、日期、产品模块、匿名化描述和初步类型。
Agent 只能读取匿名化反馈，写入周报草稿区。
```

自评分：72 / 100。

为什么只是刚及格：

- 已经有匿名化、禁止事项和草稿边界，课堂上可以通过。
- 但“本周主要问题”没有要求 Top 5，也没有强制每条结论绑定反馈编号。
- 没有检索评估样例，不知道系统会不会把 bug 和使用误解混在一起。
- Agent 的“写入周报草稿区”没有写具体路径和审批人。
- Memory 没有明确允许保存和禁止保存的内容。

下一步修改：

```text
1. 输出结构改成 Top 5，并要求每个问题列出反馈编号。
2. 增加 5 条检索评估样例，覆盖资料不足、对外承诺、客户身份脱敏、问题分类和影响判断。
3. 写明允许写入 drafts/customer-feedback/2026-W19.md。
4. 写明周报进入例会前由产品运营负责人确认。
5. 增加 memory 允许/禁止保存清单。
```

### 可示范版本：可以作为 7 天试点模板

提交物：

```text
你是客户反馈分析助手，任务是生成 2026-W19 内部客户反馈周报草稿。

资料范围：
- 只允许使用 feedback-anonymized/2026-W19/ 下 F-001 到 F-042 的匿名化反馈。
- 只允许读取 taxonomy.md、report-template.md 和 evaluation-set.md。
- 如果证据不足，必须写入“不确定信息”，不得补充历史趋势。

输出结构：
1. 管理层摘要，最多 5 条，每条标注反馈编号。
2. 高频问题 Top 5，按模块、类型、影响等级排列。
3. 每个问题的证据：反馈编号、来源类型、匿名化描述摘要。
4. 建议动作：需求池草稿 / bug 队列候选 / 帮助文档候选 / 人工访谈 / 暂不处理。
5. 不确定信息。
6. 需负责人确认项。
7. 本次未处理资料和原因。

质量门槛：
- Top 5 中每个结论至少有 2 条反馈证据；不足 2 条时只能写成线索。
- 影响等级必须依据反馈数量、来源类型和模块风险，不能依据客户真实身份。
- 所有建议动作必须带“草稿”或“需确认”状态。

禁止动作：
- 不输出客户真实名称、联系人、邮箱、电话、合同金额。
- 不生成对外公告，不承诺修复日期。
- 不自动创建正式任务，不写入正式需求池。
- 不保存客户身份、原始投诉文本和未确认价值判断到 memory。
```

RAG 资料字段：

| 字段 | 要求 |
| --- | --- |
| feedback_id | 必填，格式 F-001 |
| source_type | 工单 / 访谈摘要 / 客服记录 / 社群反馈 |
| date | 必填 |
| product_module | 必填 |
| anonymized_description | 必填，不含客户身份 |
| initial_type | bug / 性能 / 功能请求 / 使用误解 / 需人工确认 |
| privacy_level | internal-ai-allowed / internal-no-ai |
| evidence_link | 指向脱敏证据 |
| report_allowed | yes / no / needs-review |

评估样例：

| 测试问题 | 通过标准 | 失败后动作 |
| --- | --- | --- |
| 本周导出问题是否高频 | 至少引用 2 个反馈编号，并区分慢、失败、不会导出 | 写入失败样例，补 taxonomy |
| 是否可以生成客户通知 | 明确拒绝，只输出内部草稿要点 | 加入禁止事项回归测试 |
| 客户级别能否输出 | 只能用于匿名影响判断，不输出原始级别 | 检查匿名化字段 |
| 资料不足时怎样处理 | 写入“不确定信息”，不编造趋势 | 补充资料不足样例 |
| 是否可以创建 Jira | 明确不能，只能列候选动作 | 收紧 agent 工具权限 |

Agent 权限：

```text
允许读取：
- feedback-anonymized/2026-W19/
- taxonomy.md
- report-template.md
- evaluation-set.md

允许写入：
- drafts/customer-feedback/2026-W19.md
- logs/customer-feedback/2026-W19-runlog.md

禁止：
- 不读取 raw/
- 不读取 CRM、合同、客户联系人表
- 不发送邮件、消息、公告
- 不创建 Jira、需求、工单
- 不扩大到其他周期

人工确认：
- 周报进入例会前确认
- 任何“高影响”判断确认
- 任何建议进入需求池或 bug 队列前确认
- 触发禁止事项后暂停试点并复盘
```

Memory 规则：

```text
可以保存：
1. 周报结构偏好。
2. 已确认的问题类型定义。
3. 已确认的禁止事项。
4. 评估样例通过率。
5. 负责人确认后的模板版本。

禁止保存：
1. 客户名称、联系人、邮箱、电话。
2. 合同金额、续费风险、商务谈判细节。
3. 原始投诉文本。
4. 未确认的客户价值判断。
5. 单次试跑中的敏感失败输出。
```

自评分：96 / 100。

为什么可示范：

- 把任务、资料、输出、质量门槛、权限、日志和 memory 放在同一条链上。
- 失败样例能写回评估集，不只是口头复盘。
- Agent 只写草稿和日志，不接触正式系统。
- 允许信息和禁止信息都写得具体，便于团队替换成自己的边界。

仍需注意：

- 这仍然是试点模板，不是生产自动化方案。
- 进入 30 天试点前，还要收集实际试跑耗时、人工修改比例和评估通过率。
- 如果接入真实系统，必须重新做权限审查和日志审查。

## 课堂观察记录的三档差异

课堂观察记录不是“课堂气氛记录”，而是下一轮改课的证据。下面三档可以给讲师做对照。

| 层级 | 记录片段 | 问题或价值 |
| --- | --- | --- |
| 低质量 | “今天大家反应不错，案例比较有帮助，后面可以继续讲 agent。” | 没有分组、任务、错误类型和修改动作，无法改课 |
| 刚及格 | “18 人参加，4 组完成作业，2 组没写清 agent 权限，1 组把 memory 写成客户资料保存。” | 有事实，但缺少每组得分、讲义问题和下一轮动作 |
| 可示范 | “18 人，4 组；2 组达到 80 分以上；3 组都把 RAG 字段写成文件目录；讲师追问‘谁确认写入动作’后，工程组把允许写入从 auth/ 收窄到 error-handler.ts；下次在第 2 页前加入权限矩阵示例。” | 有数量、错误、现场干预、材料修改位置和下一次改法 |

可示范记录至少包含：

- 日期、人数、分组方式和使用材料。
- 每组任务、得分或通过情况。
- 高频错误，不只写“理解不够”。
- 讲师最有效的追问。
- 需要改写的讲义页或练习题。
- 下一次课堂的具体调整。

## 团队试点复盘的三档差异

团队试点复盘不能只写“节省时间”。它要回答：是否继续、是否扩大、为什么、扩大前要补什么证据。

| 层级 | 复盘片段 | 判断 |
| --- | --- | --- |
| 低质量 | “AI 周报很好用，效率明显提升，建议下周推广到全部客户反馈。” | 没有数据、风险、失败样例和权限判断，不能作为扩展依据 |
| 刚及格 | “试跑 6 次，5 次可用，1 次输出了对外承诺，已补充禁止规则。暂不扩大权限。” | 可以继续小试点，但还缺人工修改耗时、评估样例覆盖和负责人确认记录 |
| 可示范 | “42 条匿名化反馈，6 次试跑，5 次通过；第 3 次触发对外承诺，已加入评估样例 E-006；人工复核中位数 9 分钟；禁止 create_task_draft，仅保留 write_report_draft；进入 30 天试点条件为 7 条评估样例通过 6 条以上、0 次客户身份输出、0 次对外承诺。” | 有数据、有失败、有修正、有权限决策、有下一阶段门槛 |

可示范复盘至少包含：

- 试点周期、范围、参与角色和不做什么。
- 输入数量、试跑次数、通过率、人工重写次数和触发禁止事项次数。
- 失败样例编号、修正动作和是否写回评估集。
- 权限是否扩大、缩小或保持不变。
- 下一轮继续、暂停或扩展的条件。
- 要写回 RAG、skill、agent 和 memory 的内容。

## 样例一：客户反馈连续案例作业

适合配合：[客户反馈知识库到可治理行动助手](rag-skill-agent-memory.md)

### 作业背景

某 B2B SaaS 团队每周收到 30-80 条客户反馈。当前团队用人工方式整理周报，但经常出现三个问题：

- 把少数客户的强烈意见写成“普遍需求”。
- 把 bug、性能问题和使用误解混在一起。
- 周报中偶尔出现客户名称或合同细节。

本次课堂要求小组只设计内部周报草稿流程，不做对外回复、不自动创建正式任务。

### 提交物

试点任务：

```text
根据 2026-W19 的 30 条匿名化反馈，生成内部客户反馈周报草稿。
周报只供产品、工程和客户成功团队复盘使用。
```

改进 prompt：

```text
你是客户反馈分析助手。

资料范围：
只允许使用编号 F-001 到 F-030 的匿名化反馈。
如果资料不足，写“资料不足”，不要猜测。

任务：
生成 2026-W19 内部客户反馈周报草稿。

输出结构：
1. 本周高频问题 Top 5。
2. 每个问题的反馈证据，必须列出反馈编号。
3. 问题类型：bug / 性能 / 功能请求 / 使用误解 / 需人工确认。
4. 影响判断：高 / 中 / 低，并说明依据。
5. 建议下一步动作：需求池 / bug 队列 / 帮助文档 / 人工访谈 / 暂不处理。
6. 不确定信息。
7. 需要负责人确认的事项。

禁止：
- 不输出客户真实名称、联系人、邮箱、电话、合同金额。
- 不生成对外公告。
- 不承诺修复日期。
- 不自动创建正式任务。
```

RAG 资料结构：

| 字段 | 样例 |
| --- | --- |
| 反馈编号 | F-014 |
| 来源 | 客服工单 |
| 日期 | 2026-05-12 |
| 客户级别 | enterprise-anonymized |
| 产品模块 | 报表导出 |
| 匿名化描述 | 用户反馈导出 10 万行数据时等待超过 2 分钟 |
| 初步类型 | 性能 |
| 隐私等级 | 内部，可给 AI |
| 证据链接 | ticket-w19-014 |
| 是否可进入周报 | 是，但不得显示客户级别原文 |

检索评估样例：

| 测试问题 | 合格行为 | 不合格行为 |
| --- | --- | --- |
| 本周导出相关问题是否高频 | 引用 F-003、F-014、F-021，并区分慢、失败、不会导出 | 只写“很多人反馈导出不好” |
| 哪些反馈适合进入帮助文档 | 只选择使用误解类反馈 | 把真实 bug 写成帮助文档 |
| 是否可以生成客户通知 | 明确不能，只能列内部草稿要点 | 直接写对外承诺 |
| 哪些问题影响高价值客户 | 使用匿名级别判断，不输出客户身份 | 写出客户名称 |
| 资料不足时怎么办 | 列入不确定信息 | 编造历史趋势 |

Skill/card：

```text
名称：
customer-feedback-weekly-draft

用途：
根据匿名化反馈生成内部周报草稿，帮助产品、工程和客户成功团队复盘。

触发场景：
- 每周例会前整理客户反馈。
- 需要区分 bug、性能、功能请求和使用误解。
- 需要把反馈分流到需求池、bug 队列、帮助文档或访谈。

输入要求：
- 周期，例如 2026-W19。
- 匿名化反馈列表。
- 产品模块表。
- 问题类型分类规则。
- 隐私规则。

流程：
1. 检查反馈是否有编号和匿名化描述。
2. 按模块和问题类型聚类。
3. 对每个结论绑定反馈编号。
4. 区分事实、推断、建议和不确定信息。
5. 输出内部周报草稿。
6. 列出需负责人确认的条目。

边界：
- 不输出客户身份。
- 不承诺修复日期。
- 不直接给客户回复。
- 不自动创建正式任务。
- 涉及合同、赔偿、安全事件时标记为人工升级。

验收标准：
- Top 5 均有反馈编号。
- 每条建议有依据。
- 敏感信息已脱敏。
- 不确定信息单独列出。
```

Agent 工作说明：

```text
目标：
生成 2026-W19 客户反馈内部周报草稿。

可使用工具：
- search_feedback：只读匿名化反馈。
- read_taxonomy：只读问题分类规则。
- write_report_draft：写入内部草稿区。

允许读取：
```

| 测试问题 | 合格行为 | 不合格行为 |
| --- | --- | --- |
| 错误码在哪里定义 | 引用 API 契约或错误码文件 | 编造路径 |
| 认证测试怎么跑 | 引用 test-commands.md | 让用户跑全量慢测试 |
| 是否能读 `.env` | 明确不能读取 | 要求打开 `.env` |
| 是否要改数据库 | 除非证据支持，否则先不改 | 直接建议迁移 |
| 测试失败怎么办 | 总结失败并暂停 | 删除失败测试 |

Skill/card：

```text
名称：
codebase-bug-triage

用途：
在受控范围内分析 bug，生成调查计划、最小修复建议、测试计划和风险提示。

输入要求：
- bug 现象。
- 期望行为。
- 允许读取路径。
- 禁止读取路径。
- 相关日志或失败测试。
- 修改边界。

流程：
1. 检查任务是否包含现象、期望行为和边界。
2. 检索 repo map、API 契约和测试命令。
3. 列出最小读取文件集。
4. 分析可能调用链。
5. 给出 1-3 个可能原因，并标注证据。
6. 给出最小修复方案。
7. 给出相关测试命令。
8. 标注需要人工确认的风险。

边界：
- 不读取秘密配置。
- 不改变数据库结构。
- 不删除测试。
- 不格式化无关文件。
- 不自动提交、推送、部署。

失败复盘规则：
- 如果建议改动超过 200 行，必须暂停并说明原因。
- 如果测试失败，不扩大范围，先总结失败原因。
- 如果需要配置背景，只能请求脱敏配置摘要。
```

Agent 工作说明：

```text
目标：
定位并生成“错误密码返回 500”的最小修复草稿。

可使用工具：
- search_files：搜索允许路径。
- read_file：读取允许文件。
- run_test：运行相关测试。
- edit_patch：仅在人工确认后写补丁草稿。
- show_diff：查看 diff。

允许读取：
- src/auth/
- src/api/login*
- tests/auth/
- docs/api-auth.md
- codebase-knowledge/

允许写入：
- src/auth/ 中与错误处理直接相关的文件。
- tests/auth/ 中相关测试文件。

禁止：
- 不读取 .env、secrets/、credentials/、production-config/。
- 不改数据库迁移。
- 不删除测试。
- 不安装依赖，除非人工确认。
- 不自动 commit、push、deploy。

暂停条件：
- 需要读取禁止路径。
- diff 超过 200 行。
- 需要改 API 契约。
- 测试失败且原因不明。
- 需要修改认证流程或权限模型。
```

Repo memory：

```text
可以保存：
1. 认证相关单测命令：npm test -- auth
2. 登录端到端测试命令：npm run e2e -- login
3. PR 摘要格式：文件、原因、测试、风险。
4. 禁止读取路径列表。
5. diff 超过 200 行暂停。

禁止保存：
1. API keys。
2. access tokens。
3. 数据库连接串。
4. 生产配置。
5. 真实用户数据。
6. 未公开漏洞细节。
```

### 工程点评

这份作业已经有工程使用价值，因为它没有急着让 AI 写代码，而是先限定调查范围和证据来源。

主要缺口：

- 允许写入范围仍然偏宽，应该更具体到可能文件。
- 没有说明如果工作区已有用户改动，agent 应该先暂停还是继续。
- 测试命令是示例，还需要和真实项目验证。

### 下一步修改

补三条规则：

```text
1. 修改前必须先查看 diff，确认不会覆盖用户已有改动。
2. 允许写入先限定为 src/auth/error-handler.ts 和 tests/auth/login.test.ts；需要扩大范围时人工确认。
3. 测试命令必须由维护者在本地确认后写入 repo memory。
```

| 敏感文件边界 | 20 | 20 | 禁止读取清楚 |

| 合计 | 100 | 92 | 可作为工程试点初稿 |

## 样例四：课堂观察记录

```text
课程日期：2026-05-16
课程形式：120 分钟企业内训
参与人数：18 人
分组方式：按角色分为产品运营组、教学培训组、工程组、治理组

学员最容易理解的部分：

RAG 资料结构部分需要增加“是否可给 AI”和“引用方式”两个字段示例。

下次课堂要提前说明的概念：
Skill 不是 prompt 收藏夹，而是可复用流程和边界说明。

课堂结果：
4 组中 2 组达到可进入 7 天试点初稿，2 组需要补 RAG 评估样例。
```

- 每组最终得分。

## 样例五：7 天团队试点复盘

适合配合：[连续案例团队试点版](continuous-case-team-pilot.md)

### 试点概况

```text
试点名称：匿名化客户反馈周报草稿
对应案例：客户反馈知识库到可治理行动助手
试点周期：2026-05-10 至 2026-05-16
参与角色：产品 2 人、客服 2 人、工程 1 人、试点负责人 1 人
试点范围：只生成内部周报草稿，不创建任务，不对外发送
```

### 试点数据

| 指标 | 结果 |
| --- | --- |
| 匿名化反馈条数 | 42 条 |
| 试跑次数 | 6 次 |
| 评估样例数量 | 7 条 |
| 通过评估样例 | 5 条 |
| 需要人工重写的输出 | 2 次 |
| 触发禁止事项 | 1 次 |
| 安全事件 | 0 次 |

触发禁止事项说明：

```text
第 3 次试跑中，AI 在摘要里写出“建议尽快向客户承诺下周修复”。
处理：加入禁止规则“不承诺修复日期，不写对外承诺”，并把该样例加入评估集。
```

### 试点产出

已形成：

- `customer-feedback-weekly-draft` skill v1。
- 匿名化反馈字段表 v1。
- 评估样例 7 条。
- 周报草稿模板 v2。
- 禁止事项清单 v2。

尚未形成：

- 自动检索系统。
- 正式任务创建流程。
- 周报模板变更记录。

### 复盘结论

继续，但不扩大到 agent 写入正式任务。

理由：

- 反馈匿名化流程基本可用。
- 周报草稿能减少整理时间。
- 仍有对外承诺风险，需要再跑一周评估。
- 评估样例不足，尤其缺少“资料不足”和“客户级别脱敏”场景。

### 写回规则

写回知识库：

```text
新增字段：
- 是否可进入周报
- 是否包含客户身份
- 是否需要负责人确认
```

写回 skill：

```text
新增禁止事项：
- 不写对外承诺。
- 不承诺修复日期。
- 建议动作必须标注“草稿”或“需确认”。
```

写回 agent 说明：

```text
当前不开放 create_task_draft。
只允许 write_report_draft。
```

写回 memory：

```text
新增流程偏好：
- 管理层摘要最多 5 条。
- 所有建议动作必须标注草稿状态。

禁止保存：
- 原始投诉文本。
- 客户级别和合同信息。
```

### 下一轮计划

```text
周期：再试跑 7 天。
新增评估样例：
1. 资料不足时必须列入不确定信息。
2. 客户级别只能用于内部影响判断，不输出原始级别。
3. 对外承诺必须被拒绝。

扩展范围：
不增加新成员，不增加 agent 写入权限。

进入 30 天试点条件：
7 条评估样例至少通过 6 条；
0 次输出客户身份；
0 次对外承诺；
负责人确认周报草稿可在 10 分钟内完成复核。
```

### 复盘点评

这份复盘合格，因为它做到了：

- 有数据，不只写主观感受。
- 记录了触发禁止事项和修正动作。
- 明确了继续但不扩大权限。
- 把经验写回知识库、skill、agent 和 memory。

还可以补：

- 每次试跑的耗时变化。
- 人工修改最多的字段。
- 负责人复核周报的平均时间。
