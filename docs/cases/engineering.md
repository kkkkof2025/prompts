# 工程案例

## 案例 1：让 AI 协助定位和修复登录 Bug

场景：

工程师遇到登录页提交后没有响应的问题，希望 AI 协助定位和修复。

失败 prompt：

```text
登录坏了，帮我修。
```

为什么失败：

现象、复现步骤、错误日志和修改边界都缺失，AI 可能盲改很多文件。

改进 prompt：

```text
请协助修复登录页提交后无响应的问题。

现象：
- 输入账号密码后点击登录，没有跳转，也没有错误提示。
- 浏览器控制台出现【粘贴错误】。

复现步骤：
1. 打开登录页。
2. 输入有效账号密码。
3. 点击登录。

范围：
- 先只读取登录页组件、认证 API、路由相关文件。
- 修改前先说明你准备修改哪些文件。

禁止：
- 不重构无关代码。
- 不改数据库结构。
- 不删除测试。
- 不回滚我已有改动。

验收标准：
- 登录成功后跳转到 dashboard。
- 错误密码显示错误提示。
- 相关测试通过；如果无法运行测试，说明原因。
```

验收标准：

- 修改范围小。
- 有测试或手工验证记录。
- 最终能说明改了什么、为什么改。

复盘：

如果同类问题反复出现，把复现信息、日志位置、测试命令和禁止事项沉淀成项目级 debug prompt。

## 案例 2：为已有功能补测试而不是重写功能

场景：

工程师接手一个缺少测试的导入功能，希望 AI 帮忙补边界用例。

失败 prompt：

```text
帮这个导入功能补完整测试。
```

为什么失败：

“完整”没有边界，AI 可能写大量脆弱测试，甚至为了测试方便改生产代码。

改进 prompt：

```text
请为导入功能补充测试。

目标：
- 先覆盖最容易造成线上事故的路径。
- 不重写导入实现。

请先阅读：
- 导入入口文件：【文件路径】
- 解析器文件：【文件路径】
- 现有测试目录：【文件路径】

测试范围：
1. 正常导入最小样例。
2. 空文件。
3. 缺少必填列。
4. 重复记录。
5. 非法日期或金额格式。

要求：
- 遵循现有测试风格。
- 每个测试只验证一个行为。
- 如果发现代码不可测试，先说明原因和最小改动建议，不要直接大改。
```

验收标准：

- 测试覆盖关键事故路径。
- 测试命名能说明业务行为。
- 没有为了测试做无关重构。

复盘：

测试补完后记录“曾经缺少哪些边界”，把它变成后续需求评审或代码评审清单。

## 案例 3：发布前用 AI 做风险审查，而不是让 AI 直接合并

场景：

工程团队准备发布一个涉及登录、会员权限和计费展示的小版本。代码已经通过基础测试，但负责人担心“改动范围看起来不大，实际风险可能被低估”。这时 AI 适合做发布前风险审查、测试缺口整理和回滚预案草拟，不适合直接决定是否上线。

失败 prompt：

```text
看看这个 PR 能不能发，没问题就合并。
```

为什么失败：

这个 prompt 把“分析风险”和“决定上线”混在一起。AI 可能只看 diff 表面，忽略迁移脚本、权限边界、配置开关、监控告警、回滚路径和客服影响。更危险的是，“没问题就合并”把发布权交给了模型。

改进 prompt：

```text
请对这个发布候选做风险审查，不要合并，不要推送，不要修改代码。

输入资料：
- PR diff：【粘贴链接或摘要】
- 相关测试结果：【粘贴 CI 摘要】
- 变更说明：【粘贴产品/技术说明】
- 影响模块：登录、会员权限、计费展示

请按下面结构输出：

1. 变更事实
   - 只列从 diff、测试或说明中能确认的事实。
   - 每条标注来源：diff / 测试 / 变更说明。

2. 风险假设
   - 列出你推测的风险，但必须标注“推测”。
   - 按用户影响、数据影响、权限影响、回滚难度排序。

3. 测试缺口
   - 哪些关键路径已有测试。
   - 哪些关键路径缺测试。
   - 哪些只能人工验收。

4. 发布闸门
   - 必须通过的检查。
   - 可以延期的检查。
   - 需要负责人确认的事项。

5. 回滚预案草稿
   - 回滚触发条件。
   - 回滚步骤。
   - 需要通知的人。

禁止：
- 不要输出“可以放心上线”这种绝对结论。
- 不要替负责人做最终发布决定。
- 不要编造测试结果。
```

验收标准：

- 风险按来源分成“事实”和“推测”。
- 输出能直接进入发布评审会，而不是只给一句建议。
- 测试缺口能转成具体任务。
- 回滚预案包含触发条件、执行步骤和负责人。
- 最终发布决定仍由人工负责人作出。

复盘：

发布后把真实事故、告警、客服反馈和回滚记录补回风险清单。如果 AI 标出的风险没有发生，不代表它错了；要看风险是否被测试、开关、灰度或人工验收消掉。如果 AI 没标出的风险发生了，就把它写成下一次发布审查 prompt 的新增检查项。

这个案例可以和 [Agent Trace 生产事故复盘长案例](agent-trace-incident-retrospective.md) 连起来读：发布前审查解决“上线前还有哪些洞”，trace 事故复盘解决“上线后到底哪里断了”。
