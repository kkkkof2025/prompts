# 工程案例

## 案例 1：让 AI 协助定位和修复登录 Bug

场景：

工程师遇到登录页提交后没有响应的问题，希望 AI 协助定位和修复。

失败 prompt：

```text
登录坏了，帮我修。
```

为什么失败：

现象、复现步骤、错误日志和修改边界都缺失，AI 可能盲改很多文件。

改进 prompt：

```text
请协助修复登录页提交后无响应的问题。

现象：
- 输入账号密码后点击登录，没有跳转，也没有错误提示。
- 浏览器控制台出现【粘贴错误】。

复现步骤：
1. 打开登录页。
2. 输入有效账号密码。
3. 点击登录。

范围：
- 先只读取登录页组件、认证 API、路由相关文件。
- 修改前先说明你准备修改哪些文件。

禁止：
- 不重构无关代码。
- 不改数据库结构。
- 不删除测试。
- 不回滚我已有改动。

验收标准：
- 登录成功后跳转到 dashboard。
- 错误密码显示错误提示。
- 相关测试通过；如果无法运行测试，说明原因。
```

验收标准：

- 修改范围小。
- 有测试或手工验证记录。
- 最终能说明改了什么、为什么改。

复盘：

如果同类问题反复出现，把复现信息、日志位置、测试命令和禁止事项沉淀成项目级 debug prompt。

## 案例 2：为已有功能补测试而不是重写功能

场景：

工程师接手一个缺少测试的导入功能，希望 AI 帮忙补边界用例。

失败 prompt：

```text
帮这个导入功能补完整测试。
```

为什么失败：

“完整”没有边界，AI 可能写大量脆弱测试，甚至为了测试方便改生产代码。

改进 prompt：

```text
请为导入功能补充测试。

目标：
- 先覆盖最容易造成线上事故的路径。
- 不重写导入实现。

请先阅读：
- 导入入口文件：【文件路径】
- 解析器文件：【文件路径】
- 现有测试目录：【文件路径】

测试范围：
1. 正常导入最小样例。
2. 空文件。
3. 缺少必填列。
4. 重复记录。
5. 非法日期或金额格式。

要求：
- 遵循现有测试风格。
- 每个测试只验证一个行为。
- 如果发现代码不可测试，先说明原因和最小改动建议，不要直接大改。
```

验收标准：

- 测试覆盖关键事故路径。
- 测试命名能说明业务行为。
- 没有为了测试做无关重构。

复盘：

测试补完后记录“曾经缺少哪些边界”，把它变成后续需求评审或代码评审清单。
