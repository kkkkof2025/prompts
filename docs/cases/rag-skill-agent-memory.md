# 案例：从客户反馈知识库到可治理行动助手

这个案例把第 6-9 章串成一条完整路径：同一个团队任务，怎样从普通 prompt，逐步升级为 RAG、skill、agent，再加入 memory。它适合产品、运营、客服、工程和管理者一起阅读。

案例不追求“系统越复杂越好”。每一步升级都要回答一个问题：为什么普通 prompt 不够，新增能力解决了什么问题，又带来了什么治理成本。

## 场景

一个 SaaS 团队每周都会收到大量客户反馈，来源包括：

- 客服工单。
- 用户社区帖子。
- 销售拜访记录。
- 产品内反馈按钮。
- 发布后 bug 报告。
- 客户成功团队的周报。

团队想让 AI 每周生成一份“客户反馈周报”，帮助产品和工程判断：

- 哪些问题重复出现。
- 哪些反馈是功能请求，哪些是 bug，哪些只是使用误解。
- 哪些问题影响高价值客户。
- 哪些条目需要进入需求池、bug 队列或帮助文档。
- 下周应该优先人工确认哪 5 个问题。

这个任务看起来像总结，但真正难点不是总结，而是资料来源多、事实需要引用、客户隐私要脱敏、产品动作不能自动发布。

## 第 0 轮：普通 prompt 为什么不够

团队一开始这样问：

```text
请帮我总结一下这周客户反馈，给出产品改进建议。
```

AI 很快给出一份看起来完整的报告：

```text
本周用户主要反馈集中在三个方向：
1. 登录体验不够顺畅。
2. 报表功能需要更多自定义选项。
3. 移动端体验需要优化。

建议：
1. 优化登录流程。
2. 增加报表字段配置。
3. 改进移动端界面。
```

这份输出的问题在于：

- 没有说明依据来自哪条反馈。
- 没有区分高频问题和单个用户抱怨。
- 没有标注客户级别、影响范围和来源日期。
- 没有区分“事实”“推断”和“建议”。
- 没有提醒哪些信息需要人工核验。
- 可能把敏感客户名称写进报告。

普通 prompt 可以帮你快速起草，但它无法自动保证资料完整、引用准确、权限可控和流程可复用。

## 第 1 轮：先把 prompt 变成可验收任务

在还没有 RAG、skill、agent 之前，先把任务说明写稳。

```text
任务：
请根据我提供的客户反馈片段，生成一份客户反馈周报。

输入范围：
只允许使用我在本次对话中提供的反馈片段。
不要引用外部资料，不要补充不存在的客户背景。

输出结构：
1. 本周高频问题 Top 5。
2. 每个问题的反馈证据，列出反馈编号。
3. 问题类型：bug / 功能请求 / 使用误解 / 需人工确认。
4. 影响判断：高 / 中 / 低，并说明依据。
5. 建议下一步动作：进入需求池 / 进入 bug 队列 / 更新帮助文档 / 人工访谈。
6. 不确定信息列表。

隐私要求：
客户名称、联系人姓名、邮箱、电话全部匿名化。

验收标准：
- 每个结论必须能追溯到至少 1 条反馈编号。
- 没有证据的内容只能写入“不确定信息”。
- 不得直接输出对外公告文案。
```

这个版本已经明显更好，但仍然只能处理“本次对话里放得下的资料”。当反馈量变大，问题会回来：

- 上下文放不下所有反馈。
- 每周手工粘贴资料成本高。
- 旧反馈和新反馈之间的变化难追踪。
- 团队成员写法不一致。

这时才有必要进入 RAG。

## 第 2 轮：升级为 RAG 知识库

RAG 的目标不是“让 AI 什么都知道”，而是让回答能回到团队资料。

### 资料结构

先把反馈资料整理成固定结构：

```text
feedback-knowledge/
├── raw/
│   ├── tickets-2026-w18.csv
│   ├── community-2026-w18.md
│   └── cs-notes-2026-w18.md
├── normalized/
│   ├── feedback-items-2026-w18.md
│   └── feedback-items-2026-w19.md
├── taxonomy.md
├── privacy-rules.md
└── report-template.md
```

每条反馈最少保留这些字段：

```text
反馈编号：
来源：
日期：
客户级别：
产品模块：
原始描述：
匿名化描述：
初步类型：
证据链接：
隐私等级：
```

### 检索策略

检索不是只搜关键词。这个场景里至少要按四类信号找资料：

| 信号 | 用途 | 例子 |
| --- | --- | --- |
| 产品模块 | 找同一功能相关反馈 | 报表、登录、权限、导出 |
| 问题类型 | 区分 bug、需求和误解 | 导出失败、字段缺失、不会配置 |
| 时间 | 判断是否本周新增或持续出现 | W18、W19 |
| 客户级别 | 判断影响优先级 | 免费、付费、战略客户 |

### RAG 版 prompt

```text
你是客户反馈分析助手。

资料来源：
你只能使用检索到的 feedback-knowledge 内容。

任务：
生成本周客户反馈周报。

必须遵守：
1. 每个结论必须引用反馈编号。
2. 如果检索结果不足，写“资料不足”，不要猜测。
3. 客户、联系人、邮箱、电话全部匿名化。
4. 不输出对外承诺，只输出内部建议。
5. 对高影响建议标注“需产品负责人确认”。

输出：
- 本周高频问题 Top 5
- 新增问题
- 持续问题
- 误解类问题
- 需人工访谈的问题
- 建议动作
- 不确定信息
- 使用的反馈编号列表
```

### RAG 验收集

RAG 必须有小评测，不然“看起来对”很容易误导团队。

| 测试问题 | 期望行为 | 不合格表现 |
| --- | --- | --- |
| 本周导出失败是否高频 | 引用多个反馈编号，说明模块和影响 | 只说“很多用户反馈” |
| 战略客户是否提到权限问题 | 只基于客户级别字段回答 | 编造客户名称 |
| 哪些问题适合进入帮助文档 | 区分使用误解和真实缺陷 | 把所有问题都写成需求 |
| 是否可以发对外公告 | 明确不能直接发，只能给内部草稿 | 直接生成承诺性公告 |

做到这里，团队已经有了一个可核验的客户反馈知识库。但每周报告的写法、字段和边界仍然需要稳定下来，这时适合沉淀为 skill。

## 第 3 轮：沉淀为反馈分析 skill

Skill 的作用是把“每周都要重复做的流程”固化下来。

```text
名称：
customer-feedback-triage

用途：
根据已匿名化的客户反馈知识库，生成内部客户反馈周报和下一步处理建议。

触发场景：
- 用户要求总结某周客户反馈。
- 用户要求识别高频问题、持续问题或新增问题。
- 用户要求把反馈分流到需求池、bug 队列或帮助文档。

输入要求：
- 周期范围，例如 2026-W19。
- 可用反馈知识库路径或检索结果。
- 产品模块范围，如果有限定。
- 输出受众：产品 / 工程 / 客服 / 管理层。

流程：
1. 检查输入是否包含周期、来源和匿名化规则。
2. 检索本周反馈和前 1-2 周相关历史反馈。
3. 按产品模块、问题类型、客户级别聚类。
4. 对每个结论绑定反馈编号。
5. 区分事实、推断、建议和不确定信息。
6. 输出内部周报。
7. 给出下一步处理建议，但不自动创建外部公告或客户回复。

输出格式：
- 摘要
- Top 5 高频问题
- 新增问题
- 持续问题
- 建议分流
- 需人工确认
- 引用反馈编号
- 本周 skill 失败或不确定点

边界：
- 不读取未授权客户资料。
- 不输出真实客户名称和联系人。
- 不承诺修复日期。
- 不自动创建任务、发送邮件或发布公告。
- 遇到法律、合同、赔偿和安全事件，标记为人工升级。

验收标准：
- Top 5 问题均有反馈编号。
- 每条建议都能说明依据。
- 敏感信息已匿名化。
- 不确定信息单独列出。
```

Skill 让流程稳定下来，也方便团队培训新人：不是每个人临场写 prompt，而是共同维护一份可复用能力包。

但如果团队希望 AI 不只生成报告，还能根据报告创建内部草稿任务、提醒负责人、检查帮助文档是否已有说明，就进入了 agent 范围。

## 第 4 轮：升级为受控 agent

Agent 不是“让 AI 全自动管理客户反馈”。在这个案例里，agent 的定位更窄：

```text
目标：
每周读取已匿名化反馈知识库，生成客户反馈周报，提出内部处理建议，并为人工确认后的条目创建草稿任务。
```

### 允许工具

| 工具 | 权限 | 说明 |
| --- | --- | --- |
| 读取知识库 | 只读 | 只能读已匿名化 feedback-knowledge |
| 检索反馈 | 只读 | 返回反馈编号和摘要 |
| 读取帮助文档 | 只读 | 判断是否已有说明 |
| 创建任务草稿 | 写草稿 | 只创建草稿，不分配负责人 |
| 写周报草稿 | 写草稿 | 保存到内部草稿区 |

### 禁止动作

- 禁止读取原始未脱敏客户资料。
- 禁止给客户发邮件。
- 禁止发布公告。
- 禁止承诺修复日期。
- 禁止改动产品路线图。
- 禁止删除反馈记录。
- 禁止把客户级别写进公开文本。

### Agent 工作说明

```text
目标：
生成 2026-W19 客户反馈周报，并给出内部处理建议。

可使用工具：
- search_feedback：检索已匿名化反馈。
- read_docs：读取帮助文档。
- create_task_draft：创建内部任务草稿。
- write_report_draft：写入周报草稿。

流程：
1. 先说明计划。
2. 检索本周反馈。
3. 对比前两周持续问题。
4. 使用 customer-feedback-triage skill 生成周报。
5. 检查建议是否需要帮助文档、bug 队列或需求池。
6. 只为“人工确认通过”的条目创建任务草稿。
7. 输出执行日志和不确定信息。

人工确认点：
- 创建任务草稿前确认。
- 涉及战略客户影响判断时确认。
- 涉及安全、合同、赔偿、法律风险时确认。
- 任何对外内容都必须人工另行处理。
```

### Agent 失败复盘

一次试跑中，agent 把“导出报表慢”和“导出失败”合并成同一个 bug，并建议进入 bug 队列。

复盘后发现：

- 两类反馈都提到了“导出”。
- 但一个是性能问题，一个是权限配置导致的失败。
- 检索结果混在一起，skill 没要求区分失败模式。

修正动作：

- 在 taxonomy 里增加“失败类型”字段。
- 在 skill 流程里增加“同模块不同失败模式不得强行合并”。
- 在评估集中增加一条测试：区分导出慢、导出失败和不会导出。

这就是 agent 的真实价值：不是永远不犯错，而是错误能被记录、复盘并固化回流程。

## 第 5 轮：加入 memory，但只保存该保存的

Memory 在这个案例中不是保存所有客户反馈。客户反馈应进入知识库和业务系统，不应该作为个人助手的长期记忆乱存。

适合保存的记忆：

- 团队固定报告格式。
- 产品模块分类规则。
- 内部术语解释。
- 每周处理节奏。
- 常见失败复盘。
- 用户偏好：管理层版要短，产品版要保留证据表。

不适合保存的记忆：

- 客户真实名称。
- 联系人信息。
- 合同金额。
- 原始投诉内容。
- 安全事件细节。
- 未确认的客户价值判断。

### 记忆文件示例

```text
# team-feedback-assistant-memory.md

## 报告偏好
- 管理层摘要控制在 5 条以内。
- 产品版必须保留反馈编号和模块。
- 工程版必须区分 bug、性能、权限配置和使用误解。

## 固定分类
- bug：功能未按预期工作。
- 性能：能完成但明显慢。
- 使用误解：功能存在，但用户没有找到或理解错误。
- 功能请求：当前不存在的新能力。

## 禁止保存
- 客户真实名称。
- 联系人、邮箱、电话。
- 合同金额。
- 未脱敏原始反馈。
- 安全事件细节。

## 复盘经验
- “导出慢”和“导出失败”不能只按模块合并。
- 没有反馈编号的结论只能进入不确定信息。
```

### 记忆更新 prompt

```text
请从本次客户反馈周报流程中提取可以长期保存的流程经验。

只允许保存：
- 报告格式偏好。
- 分类规则。
- 复盘后确认的流程改进。
- 不含客户身份的通用失败模式。

禁止保存：
- 客户名称、联系人、邮箱、电话。
- 原始反馈内容。
- 合同、价格、赔偿、安全事件细节。
- 未经人工确认的推断。

输出：
- 建议新增记忆
- 建议更新记忆
- 不应保存的信息
- 需要人工确认的信息
```

## 最终系统边界

这个案例最后形成的不是一个“自动替团队决策”的系统，而是一个可治理的工作流：

```text
反馈资料 -> 脱敏与结构化 -> RAG 检索 -> skill 周报流程 -> agent 草稿动作 -> 人工确认 -> 复盘 -> 更新知识库和记忆
```

每一层都有明确价值：

| 层级 | 解决的问题 | 新增风险 | 控制方法 |
| --- | --- | --- | --- |
| Prompt | 把任务说清楚 | 证据不足 | 输出格式和验收标准 |
| RAG | 回到资料和引用 | 检索错误、资料过时 | 评估集、引用、更新流程 |
| Skill | 固化稳定流程 | 旧流程延续错误 | 版本管理、失败案例 |
| Agent | 多步骤调用工具 | 越权行动 | 最小权限、人工确认、日志 |
| Memory | 跨周保留偏好和经验 | 隐私和过时记忆 | 禁止保存清单、复查和删除 |

## 可复用模板

你可以把这个案例改成自己的任务，只要保留下面 8 个问题：

```text
1. 这个任务用普通 prompt 为什么不够？
2. 哪些资料需要进入知识库，哪些不能进入？
3. 每个结论如何追溯到来源？
4. 哪些流程值得固化成 skill？
5. agent 可以读什么、写什么、绝不能做什么？
6. 哪些动作必须人工确认？
7. 哪些信息适合长期记忆，哪些必须禁止保存？
8. 失败后如何把经验更新回知识库、skill 或 memory？
```
