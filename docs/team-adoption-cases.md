# 团队 AI 落地案例集

这份案例集把 [团队 AI 落地手册](team-adoption-playbook.md) 中的方法填成可参考的试点样例。它不是为了展示“AI 多强”，而是展示一个团队如何选择低风险场景、写清边界、建立验收标准、记录失败并决定是否推广。

每个案例都使用同一结构：

```text
试点背景 -> 任务盘点 -> 数据边界 -> 工作流 -> 模板 -> 评测 -> 失败记录 -> 复盘结论
```

建议先读 [AI 任务选择决策指南](task-decision-guide.md)，再根据团队情况选择一个案例改写。

## 案例 1：会议纪要试点

适用团队：

项目组、运营团队、产品团队、跨部门协作小组。

为什么选它：

- 高频。
- 输出格式稳定。
- 风险相对可控。
- 验收标准清楚。
- 可以快速看到节省时间的效果。

不适合的情况：

- 会议包含客户隐私、未公开财务、人事讨论或法律争议。
- 会议结论本身还没有确认。
- 团队没有人愿意复核纪要。

### 任务盘点

```text
任务名称：
项目会议纪要整理。

当前做法：
参会人手动整理，通常需要 30-45 分钟。

频率：
每周 3-5 次。

涉及数据：
内部会议记录，不包含客户身份信息。

输出用途：
团队内部同步和任务管理。

风险等级：
中。

是否容易验收：
是。可以检查决定、待办、负责人、截止时间和争议是否准确。

是否适合试点：
是。先从内部低敏会议开始。
```

### 数据边界

允许输入：

- 内部项目会议转写。
- 会后公开给项目组的聊天记录。
- 项目名称的泛称。

禁止输入：

- 客户个人信息。
- 合同金额和报价细节。
- 人事评价。
- 未公开财务数据。
- 密钥、账号和访问链接。

需要先处理：

```text
把具体客户名改成“客户 A”。
把具体成员姓名改成角色名，例如“产品负责人”“工程负责人”。
删除无关闲聊和个人信息。
```

### 工作流

```text
第 1 步：清理输入
输入：会议转写和聊天记录。
输出：匿名化会议记录。
检查点：不包含客户个人信息和敏感链接。

第 2 步：提取事实
输入：匿名化会议记录。
输出：会议摘要、已确认决定、未确认事项。
检查点：不把讨论写成决定。

第 3 步：整理待办
输入：第 2 步输出。
输出：事项、负责人、截止时间、依赖。
检查点：缺失字段写“待确认”。

第 4 步：风险和争议
输入：第 2-3 步输出。
输出：争议、风险、需要会后确认的问题。
检查点：风险具体，不写空话。

第 5 步：人工复核
输入：完整纪要。
输出：可发送给项目组的纪要。
检查点：会议主持人确认后再发布。
```

### Prompt 模板

```text
请只依据下面会议记录整理内部项目纪要。

目标：
让项目组知道会议决定、待办、争议和待确认问题。

约束：
1. 不补充记录中没有出现的信息。
2. 区分已确认决定、仍在讨论和待确认事项。
3. 负责人、截止时间和依赖缺失时写“待确认”。
4. 不替团队做业务判断。
5. 不输出个人评价。

输出格式：
1. 会议摘要，不超过 150 字。
2. 已确认决定。
3. 待办事项，字段为事项、负责人、截止时间、依赖。
4. 争议或分歧。
5. 需要会后确认的问题。
6. 可能风险。

会议记录：
【粘贴已匿名化记录】
```

### 评测样例

```text
样例 1：普通项目例会
预期：能提取决定和待办。

样例 2：负责人缺失的会议
预期：负责人字段写“待确认”。

样例 3：存在争议的会议
预期：争议不写成决定。

样例 4：包含客户名的记录
预期：试点流程要求先匿名化，不直接处理。

样例 5：只有讨论没有结论的会议
预期：输出“未形成决定”。
```

### 验收标准

- 每个待办能复制到任务管理工具。
- 争议没有被误写成决定。
- 缺失信息没有被 AI 猜测。
- 摘要能在 2 分钟内读完。
- 发布前有会议主持人确认。

### 失败记录

失败 1：

AI 把“可以考虑下周上线”写成“决定下周上线”。

修正：

在 prompt 中增加“只有明确出现决定、确认、同意等表达，才写入已确认决定；其他写入仍在讨论”。

失败 2：

AI 给没有负责人事项补了默认负责人。

修正：

增加“缺失字段必须写待确认，不得根据角色猜测负责人”。

### 复盘结论

是否继续：

继续，但只用于低敏内部会议。

是否入库：

入库为“内部会议纪要模板 v1”。

推广条件：

- 使用前必须匿名化。
- 会议主持人必须复核。
- 涉及客户、财务、人事和法律内容的会议不进入试点。

## 案例 2：用户反馈初分试点

适用团队：

产品、运营、客服、增长团队。

为什么选它：

- 反馈量大。
- 分类工作重复。
- AI 适合做初分和摘要。
- 人可以根据原文证据复核。

不适合的情况：

- 原始反馈包含未脱敏个人信息。
- 团队想让 AI 直接决定产品优先级。
- 没有产品负责人复核。

### 任务盘点

```text
任务名称：
用户反馈初步分类。

当前做法：
运营或产品手动整理，每周约 2 小时。

频率：
每周一次。

涉及数据：
用户反馈文本，可能包含个人信息。

输出用途：
产品评审前的输入材料。

风险等级：
中。

是否容易验收：
部分容易。分类可抽查，优先级建议必须人工判断。

是否适合试点：
适合，但必须先匿名化。
```

### 数据边界

允许输入：

- 已匿名化用户反馈。
- 反馈来源，例如客服、问卷、公开评论。
- 当前版本目标。

禁止输入：

- 手机号、邮箱、账号。
- 身份证、银行卡、住址。
- 客户合同和付费细节。
- 单个用户完整画像。

### 工作流

```text
第 1 步：匿名化
输入：原始反馈。
输出：删除个人信息后的反馈列表。
检查点：无法匿名化的反馈不进入 AI。

第 2 步：初步分类
输入：匿名化反馈。
输出：分类标签和理由。
检查点：允许多标签，不确定时标注“不确定”。

第 3 步：证据保留
输入：分类结果。
输出：每类 2-3 条原文证据。
检查点：结论必须能回到原文。

第 4 步：机会点整理
输入：分类和证据。
输出：机会点、风险、待验证问题。
检查点：需求和 AI 推测分开。

第 5 步：产品负责人复核
输入：整理结果。
输出：评审材料。
检查点：不由 AI 决定最终优先级。
```

### Prompt 模板

```text
请对以下已匿名化用户反馈做初步分类。

背景：
当前版本目标是【填写】。

分类标签：
- 故障
- 功能需求
- 体验问题
- 价格问题
- 理解偏差
- 正面反馈
- 其他

要求：
1. 允许多标签。
2. 每条反馈给出分类理由。
3. 不确定时标注“不确定”。
4. 每个高频问题保留原文证据。
5. 区分用户明确提出的需求和你的推测。
6. 不给最终优先级，只给需要产品负责人判断的问题。

输出：
1. 分类表。
2. 高频问题。
3. 原文证据。
4. 可能机会点。
5. 待验证问题。

反馈：
【粘贴已匿名化反馈】
```

### 评测样例

```text
样例 1：明确故障反馈
预期：分类为故障，并保留原文证据。

样例 2：同时包含价格和体验问题
预期：允许多标签。

样例 3：只有情绪表达，没有具体问题
预期：标注不确定或其他。

样例 4：少量用户提出同一需求
预期：不夸大为普遍趋势。

样例 5：含个人信息的反馈
预期：不进入 AI，先匿名化。
```

### 验收标准

- 分类理由能对应原文。
- 高频问题有证据。
- 不把少量反馈夸大成趋势。
- 不输出个人信息。
- 不替产品负责人做最终决策。

### 失败记录

失败 1：

AI 把 2 条反馈写成“很多用户都反馈”。

修正：

要求输出数量，不允许使用“很多、大量、普遍”等没有计数依据的表达。

失败 2：

AI 把推测写成用户需求。

修正：

增加字段“用户原话”和“AI 推测”，并要求分开输出。

### 复盘结论

是否继续：

继续，作为产品评审前的初步整理。

是否入库：

入库为“用户反馈初分 skill v1”。

推广条件：

- 反馈必须先匿名化。
- 每类结论必须保留原文证据。
- 优先级由产品负责人决定。

## 案例 3：内部知识库问答试点

适用团队：

管理、运营、客服、产品、培训和支持团队。

为什么选它：

- 新人问题重复。
- 内部流程经常被问。
- 知识库能减少重复答疑。
- 适合建立引用和资料边界习惯。

不适合的情况：

- 文档过旧。
- 没有负责人维护资料。
- 权限边界不清。
- 资料中混有敏感信息。

### 任务盘点

```text
任务名称：
内部流程问答。

当前做法：
新人问同事或翻群消息，答案不稳定。

频率：
每天。

涉及数据：
内部流程文档，不含客户资料。

输出用途：
员工内部参考。

风险等级：
中。

是否容易验收：
是。可以按文档来源核验。

是否适合试点：
适合。先从低敏流程开始。
```

### 知识库范围

第一批资料：

- 新人入职流程。
- 请假和报销流程。
- 常用工具申请流程。
- 公开产品介绍。
- 术语表。

暂不纳入：

- 薪酬和绩效。
- 客户合同。
- 账号权限明细。
- 安全事件记录。
- 未公开战略和预算。

### 文档元信息

```text
标题：
负责人：
适用范围：
来源：
最后更新：
权限：
过期规则：
```

### Prompt 模板

```text
请只依据我提供的知识库资料回答问题。

要求：
1. 每个结论标注资料来源。
2. 资料没有说明时写“资料未说明”。
3. 不回答权限外问题。
4. 不猜测公司政策。
5. 如果问题涉及人事、财务、法律或安全事件，请提示咨询负责人。

知识库资料：
【粘贴相关资料】

用户问题：
【填写问题】
```

### 评测样例

```text
样例 1：资料中明确有答案的问题
预期：直接回答并引用来源。

样例 2：资料中没有答案的问题
预期：写“资料未说明”。

样例 3：资料版本过旧的问题
预期：提醒核验最后更新日期。

样例 4：权限外问题
预期：不回答，提示找负责人。

样例 5：多个文档答案冲突
预期：列出冲突，不自行决定。
```

### 验收标准

- 回答有来源。
- 不编造流程。
- 能识别资料缺口。
- 能提示权限边界。
- 过期资料不会被当成确定结论。

### 失败记录

失败 1：

AI 在资料没有说明时给出“通常情况下”的答案。

修正：

要求资料未说明时必须写“资料未说明”，不得使用常识补足。

失败 2：

AI 没有提示资料更新时间。

修正：

在输出格式中增加“依据资料”和“最后更新日期”。

### 复盘结论

是否继续：

继续，但只覆盖低敏流程。

是否入库：

入库为“内部流程问答试点 v1”。

推广条件：

- 每份资料有负责人。
- 每季度复查资料。
- 高风险问题不由 AI 直接回答。

## 案例 4：工程测试建议试点

适用团队：

工程团队、测试团队、数据团队。

为什么选它：

- AI 适合帮助枚举边界。
- 工程师可以复核。
- 不需要一开始让 AI 改生产代码。
- 容易形成测试清单。

不适合的情况：

- 直接让 AI 修改生产代码。
- 仓库包含不能上传的源代码或数据。
- 没有工程师复核测试建议。

### 任务盘点

```text
任务名称：
为已有功能补充测试建议。

当前做法：
工程师手动补测试，容易漏边界。

频率：
每个迭代多次。

涉及数据：
代码摘要、功能说明、错误日志，不包含真实用户数据。

输出用途：
工程师写测试前的参考。

风险等级：
中。

是否容易验收：
是。工程师可判断测试是否合理。

是否适合试点：
适合，但第一阶段只生成测试建议，不自动改代码。
```

### 数据边界

允许输入：

- 功能说明。
- 接口摘要。
- 已脱敏错误日志。
- 现有测试名称。

禁止输入：

- 真实用户数据。
- 密钥和连接串。
- 私有凭据。
- 生产数据库内容。

### 工作流

```text
第 1 步：说明功能
输入：功能说明和接口摘要。
输出：功能行为清单。
检查点：工程师确认理解是否准确。

第 2 步：枚举边界
输入：功能行为清单。
输出：正常、异常、边界和权限场景。
检查点：不使用真实用户数据。

第 3 步：生成测试建议
输入：边界场景。
输出：测试名称、输入、预期结果。
检查点：测试建议能由工程师实现。

第 4 步：人工筛选
输入：测试建议。
输出：保留、修改、删除的测试项。
检查点：工程师决定。

第 5 步：沉淀清单
输入：最终测试项。
输出：功能测试 checklist。
检查点：进入团队模板库。
```

### Prompt 模板

```text
请为下面功能生成测试建议，不要修改代码。

功能说明：
【填写】

接口摘要：
【填写】

已有测试：
【填写】

要求：
1. 先总结你理解的功能行为。
2. 列出正常路径、异常路径、边界输入、权限场景。
3. 为每个场景给出测试名称、输入、预期结果。
4. 不使用真实用户数据。
5. 不要求修改生产代码。
6. 标出需要工程师确认的假设。
```

### 评测样例

```text
样例 1：普通导入功能
预期：覆盖成功、空文件、格式错误、重复记录。

样例 2：权限相关功能
预期：覆盖无权限、只读权限和管理员权限。

样例 3：输入边界不清
预期：列出需要工程师确认的假设。

样例 4：包含真实日志
预期：流程要求先脱敏。

样例 5：已有测试较多
预期：不重复建议已有测试。
```

### 验收标准

- 测试建议覆盖主要边界。
- 不修改代码。
- 不使用真实用户数据。
- 假设清楚标注。
- 工程师能据此写测试。

### 失败记录

失败 1：

AI 直接建议修改实现逻辑。

修正：

在 prompt 中增加“不要修改代码，不要提出生产代码改动，除非单独列为发现的问题”。

失败 2：

AI 生成了太多低价值测试。

修正：

要求每条测试说明它覆盖的风险，不能说明风险的测试删除。

### 复盘结论

是否继续：

继续，作为测试设计辅助。

是否入库：

入库为“测试建议工作流 v1”。

推广条件：

- 只输入脱敏资料。
- 输出只作为建议。
- 工程师必须复核。
- 第二阶段再评估是否允许 AI 修改测试文件。

## 案例 5：内容发布前审查试点

适用团队：

内容、运营、市场、培训、开源项目维护团队。

为什么选它：

- 发布前审查重复且重要。
- AI 适合检查结构、风险和遗漏。
- 人仍然负责最终发布。

不适合的情况：

- 让 AI 自动发布。
- 让 AI 编造引用。
- 内容涉及法律、医疗、金融或敏感承诺。

### 任务盘点

```text
任务名称：
发布前内容审查。

当前做法：
作者自己检查，容易遗漏链接、边界和读者理解问题。

频率：
每周。

涉及数据：
拟发布内容，通常为公开材料。

输出用途：
发布前修改建议。

风险等级：
中。

是否容易验收：
是。可以检查问题是否具体可改。

是否适合试点：
适合，但 AI 不做最终发布判断。
```

### 工作流

```text
第 1 步：说明发布场景
输入：目标读者、发布渠道、内容草稿。
输出：审查目标。
检查点：场景明确。

第 2 步：结构审查
输入：草稿。
输出：结构问题。
检查点：先列问题，不直接重写。

第 3 步：事实和引用审查
输入：草稿和引用。
输出：需核验事实、缺失来源、过时风险。
检查点：不替作者确认事实。

第 4 步：风险和边界审查
输入：草稿。
输出：夸大承诺、隐私、版权和安全风险。
检查点：高风险内容标红。

第 5 步：作者修改
输入：审查结果。
输出：最终稿。
检查点：作者负责发布。
```

### Prompt 模板

```text
请对下面内容做发布前审查。

目标读者：
【填写】

发布场景：
【GitHub/公众号/课程/公司内部/官网】

要求：
1. 先列问题，不要直接重写。
2. 每个问题给出严重程度：高/中/低。
3. 检查事实、结构、初学者可读性、可执行性、风险和链接。
4. 标出需要人工核验的信息。
5. 不要编造引用。

内容：
【粘贴内容】
```

### 评测样例

```text
样例 1：普通教程
预期：指出步骤缺失和链接问题。

样例 2：包含数字结论
预期：要求核验来源。

样例 3：包含夸张承诺
预期：标为高风险。

样例 4：面向初学者但术语密集
预期：指出需要补解释。

样例 5：内容已经合格
预期：只列少量低风险建议，不强行改。
```

### 验收标准

- 问题具体可改。
- 严重程度合理。
- 不把风格偏好当错误。
- 不编造事实和引用。
- 作者保留最终判断。

### 失败记录

失败 1：

AI 直接重写全文，掩盖了具体问题。

修正：

要求“先列问题，不要直接重写”，且输出问题表。

失败 2：

AI 把风格偏好写成严重问题。

修正：

增加“区分事实错误、结构问题、风险问题和风格建议”。

### 复盘结论

是否继续：

继续，作为发布前第二双眼睛。

是否入库：

入库为“发布前审查模板 v1”。

推广条件：

- 作者负责最终发布。
- 高风险领域内容需要专业人士复核。
- 所有事实和引用由人核验。

## 从案例到团队资产

一个案例只有在沉淀后才会变成团队资产。

沉淀路径：

```text
试点案例 -> 稳定工作流 -> Prompt 模板 -> 评测样例 -> Skill -> 团队规范
```

入库前检查：

- 是否通过至少 3 次真实任务测试。
- 是否有明确适用范围。
- 是否写出不适用场景。
- 是否有数据边界。
- 是否有验收标准。
- 是否有失败记录。
- 是否有人维护。

## 最后提醒

团队落地案例不要只记录“成功节省了多少时间”。更重要的是记录：

```text
哪里失败了？
边界在哪里？
人改了什么？
下次如何避免？
是否值得推广？
```

能回答这些问题，案例才真正帮助团队变强。
