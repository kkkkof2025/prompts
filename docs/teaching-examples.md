# 教学示范作业集

这份材料给讲师、读书会主持人和团队学习负责人使用。它不是学员真实作业原文，而是根据本书方法写出的匿名化示范样例，用来说明“合格作业”和“优秀作业”大致长什么样。

建议配合 [教学版本材料包](teaching-kit.md)、[课堂练习工作纸](classroom-worksheets.md)、[读书会与教学方案](facilitation-guide.md) 和 [AI 能力评估量表](assessment-rubric.md) 使用。

## 使用方式

课堂上可以这样使用：

1. 先展示“原始版本”，让学员指出问题。
2. 再展示“改进版本”，让学员找出改进点。
3. 最后展示“讲师点评”，说明可迁移的方法。

不建议直接把这些示例当作标准答案。更好的做法是让学员替换成自己的真实任务，再保留结构、边界和验收标准。

如果要让学员现场填写，可直接使用 [课堂练习工作纸](classroom-worksheets.md) 中的表单。

## 匿名化规则

收集真实作业前，先做匿名化处理：

- 删除姓名、手机号、邮箱、住址、账号、证件号和客户身份信息。
- 删除未公开项目名、合同金额、报价、内部指标和商业计划。
- 把公司、学校、客户和产品名改成泛称。
- 把原始数据改成结构相同、数值不敏感的样例。
- 保留任务结构、约束、失败点和修改过程。

讲师可以保存：

- prompt 结构。
- 工作流步骤。
- 验收标准。
- 失败原因。
- 人工修改记录。

讲师不应保存：

- 原始隐私信息。
- 未授权业务资料。
- 密钥、密码、验证码和访问令牌。
- 能反推出个人身份或客户身份的细节。

## 示例 1：把弱 Prompt 改成五要素 Prompt

场景：

一名职场新人想让 AI 帮自己改周报。原始 prompt 很短，AI 只能生成空泛表达。

原始版本：

```text
帮我优化一下周报，让它看起来专业一点。
```

主要问题：

- 没说周报给谁看。
- 没说本周做了什么。
- 没说要保留事实还是可以扩写。
- 没有输出格式。
- 没有验收标准。

改进版本：

```text
请帮我把下面的周报草稿改写成适合发给直属主管的版本。

目标：
让主管能快速看到本周进展、风险和下周计划。

背景：
我负责一个内部资料整理项目，本周重点是清理历史文档、确认分类规则、整理需求反馈。

约束：
- 不要新增我没有提供的事实。
- 不要使用夸张表达。
- 保留未完成事项，但换成清楚、负责的表达。
- 如果信息不足，请在文末列出需要我补充的问题。

验收标准：
- 主管能在 2 分钟内看懂进展。
- 每个未完成事项都有原因和下一步。
- 风险不要被隐藏。

输出格式：
1. 本周完成
2. 遇到的问题
3. 下周计划
4. 需要支持

周报草稿：
【粘贴草稿】
```

讲师点评：

这个版本的关键改进不是“更礼貌”，而是让 AI 知道读者、目标、事实边界和交付格式。它也明确要求不新增事实，适合周报、邮件、复盘和项目进展类任务。

可迁移点：

- “给谁看”决定语气和信息密度。
- “不要新增事实”能降低编造风险。
- “未完成事项也要写清楚”能避免 AI 过度美化。
- “需要补充的问题”能把不确定性留给人处理。

评分参考：

```text
清晰度：4/5
可执行性：4/5
可验证性：4/5
可复用性：3/5
安全性：4/5
```

进一步修改建议：

把“内部资料整理项目”改成更具体的项目背景，但不要加入敏感名称。也可以补充主管关注的指标，例如进度、阻塞、风险和资源需求。

## 示例 2：资料阅读工作流

场景：

一名学生需要读一篇课程论文。原始做法是把论文全文丢给 AI，让 AI 直接总结，结果看起来完整，但无法支持课堂讨论。

原始版本：

```text
帮我总结这篇论文，越详细越好。
```

主要问题：

- 没有说明课程任务。
- 没有要求区分论文观点和自己的理解。
- 没有检查引用依据。
- 没有输出可用于课堂讨论的问题。

改进后的 5 步工作流：

```text
任务名称：课程论文阅读助手

第 1 步：提取基本信息
输入：论文标题、摘要、引言和结论。
动作：提取研究问题、研究对象、核心结论。
输出：不超过 300 字的论文概览。
检查点：每条结论都能在原文中找到依据。

第 2 步：整理概念
输入：论文中反复出现的关键概念。
动作：用课程初学者能理解的话解释概念。
输出：概念、原文位置、白话解释、例子。
检查点：不要引入课程外没有解释的新术语。

第 3 步：分析论证
输入：论文主体段落。
动作：找出作者如何从证据推出结论。
输出：主张、证据、推理链、可能漏洞。
检查点：区分作者观点和 AI 推测。

第 4 步：生成课堂讨论问题
输入：前 3 步输出。
动作：提出 5 个讨论问题。
输出：事实理解题 2 个、方法批判题 2 个、延伸应用题 1 个。
检查点：问题必须能回到论文内容。

第 5 步：形成阅读卡片
输入：前 4 步输出和我的课堂要求。
动作：整理成复习卡片。
输出：摘要、概念、论证、疑问、课堂发言准备。
检查点：发言准备不超过 150 字。
```

讲师点评：

这个作业的价值在于把“总结论文”拆成了阅读过程，而不是只追求一个漂亮摘要。每一步都有输入、输出和检查点，能够避免 AI 把不确定内容包装成确定结论。

可迁移点：

- 阅读类任务先抓结构，再做批判。
- 学习场景要保留“我还不懂什么”。
- 课堂讨论需要问题，不只是摘要。
- 引用依据比语言流畅更重要。

进一步修改建议：

如果课程有评分标准，把评分标准加入第 5 步。若论文涉及最新数据或现实政策，需要另设事实核验步骤。

## 示例 3：会议纪要工作流

场景：

运营同事需要从一次项目会议转写中整理纪要。原始 prompt 让 AI 自由发挥，容易把讨论变成结论。

原始版本：

```text
把这段会议记录整理成纪要。
```

改进版本：

```text
请只依据我提供的会议记录，整理一份内部项目纪要。

目标：
让项目成员知道会议决定、待办、争议和需要确认的信息。

约束：
- 不补充会议记录中没有出现的信息。
- 区分“已决定”和“仍在讨论”。
- 如果负责人、截止时间或依赖没有出现，写“待确认”。
- 不替团队做业务判断。

输出格式：
1. 会议摘要，不超过 150 字。
2. 已确认决定。
3. 待办事项，字段为事项、负责人、截止时间、依赖。
4. 争议或分歧。
5. 需要会后确认的问题。
6. 可能的风险。

会议记录：
【粘贴匿名化会议记录】
```

验收标准：

```text
1. 每个待办都能复制到任务管理工具。
2. 争议没有被写成决定。
3. 缺失字段明确标注为“待确认”。
4. 纪要没有加入会议之外的猜测。
5. 风险表达具体，不使用“注意推进”这类空话。
```

讲师点评：

会议纪要类作业的关键是事实边界。优秀作业不会追求“看起来顺”，而是能保留缺口、分歧和责任信息。对团队协作来说，错误地把争议写成决定，比语言不够漂亮更危险。

可迁移点：

- 执行类输出必须包含责任人、时间和依赖。
- 缺失信息不要让 AI 猜。
- 会议摘要、决定、待办和争议要分开。
- 对外发送前可以再做一次单独润色。

## 示例 4：用户反馈分析 Skill

场景：

产品经理每周要整理用户反馈。原始 prompt 每次都临时写，输出结构不稳定。

Skill/card：

```text
名称：
用户反馈分拣 skill

用途：
把一批用户反馈整理成可供产品评审使用的分类、证据和机会点。

触发场景：
每周用户反馈复盘、版本迭代评审、需求池整理。

输入要求：
1. 用户反馈原文。
2. 反馈来源，例如客服、问卷、访谈、应用商店。
3. 产品背景和当前版本目标。
4. 已知不能改变的约束。

执行步骤：
1. 去重，把意思接近的反馈合并。
2. 按问题类型分类，例如易用性、性能、价格、功能缺失、理解偏差。
3. 为每类保留 2-3 条原文证据。
4. 区分用户明确提出的需求和 AI 推测的机会点。
5. 给出优先级建议，并写出判断依据。
6. 列出需要进一步访谈或数据验证的问题。

输出格式：
1. 总览。
2. 分类表。
3. 高频问题。
4. 原文证据。
5. 机会点。
6. 风险和待验证问题。

边界：
- 不把单条反馈直接当成普遍结论。
- 不编造用户数量。
- 不替业务负责人做最终优先级决策。
- 涉及个人信息时先匿名化。

验收标准：
1. 每个结论都有原文证据。
2. 需求和推测分开。
3. 优先级建议能解释依据。
4. 输出能直接进入产品评审。

示例：
输入 30 条反馈后，输出 5 类问题，每类包含证据、影响、建议和待验证问题。
```

讲师点评：

这个 skill 把“整理反馈”变成可复用能力，尤其强调证据、推测和决策边界。它适合产品、运营、客服、课程反馈和内部满意度调查等场景。

可迁移点：

- 反馈分析要保留原文证据。
- 分类不是最终结论，只是讨论入口。
- AI 可以帮助整理机会点，但不能替代优先级决策。
- 每周重复任务适合写成 skill。

进一步修改建议：

可以补一个最小评测集：同一批反馈分别交给 skill 前后版本处理，看分类是否稳定、是否保留证据、是否把少量反馈夸大成趋势。

## 示例 5：代码测试补充 Agent 工作说明

场景：

工程师希望让 AI agent 帮忙为一个小型导入函数补测试。任务低风险，但仍然需要限制写入范围和人工确认。

Agent 工作说明：

```text
目标：
为导入模块补充缺失测试，覆盖成功路径、空文件、格式错误、重复记录和权限错误。

可使用工具：
- 读取项目文件。
- 搜索相关测试。
- 运行测试命令。
- 修改测试文件。

允许读取：
- src/importer/ 目录。
- tests/importer/ 目录。
- 项目测试配置文件。

允许写入：
- tests/importer/ 目录下的测试文件。
- 不允许修改生产代码，除非先提出计划并等待人工确认。

禁止事项：
- 不删除现有测试。
- 不重命名公共接口。
- 不修改依赖版本。
- 不跳过失败测试。
- 不把真实用户数据写入测试夹具。

验收标准：
1. 新增测试能在本地运行。
2. 覆盖至少 5 个边界场景。
3. 测试名称能说明业务含义。
4. 如果发现生产代码缺陷，只记录问题和最小复现，不直接改生产代码。

需要人工确认的动作：
- 修改生产代码。
- 删除或重写现有测试。
- 更新依赖。
- 改变测试命令或 CI 配置。

执行日志要求：
最后输出读取了哪些文件、修改了哪些文件、运行了哪些命令、仍有哪些风险。
```

讲师点评：

这个作业的重点不是让 agent “更聪明”，而是让 agent 的权限足够小、目标足够清楚、验收足够具体。工程场景中，允许写入范围和禁止事项比角色设定更重要。

可迁移点：

- 先把 agent 限制在低风险文件范围。
- 运行命令不等于验证完成，还要说明覆盖了什么。
- 生产代码改动必须单独确认。
- 执行日志是审计和复盘的基础。

风险提醒：

如果项目包含真实数据、密钥或客户日志，测试夹具必须先脱敏或改用合成数据。agent 不应该自行决定脱敏是否充分。

## 示例 6：个人记忆规则

场景：

一名长期使用 AI 的写作者希望保存偏好，但不想让 AI 记住敏感资料。

可保存记忆：

```text
1. 我偏好简洁、直接的中文表达。
2. 写长文时先要大纲，再逐段展开。
3. 我常用 Markdown 作为交付格式。
4. 我希望 AI 在事实不确定时明确标注。
5. 我做写作项目时喜欢保留“可删减版本”和“完整版本”。
```

禁止保存的信息：

```text
1. 身份证、银行卡、住址和联系方式。
2. 未发布文章全文。
3. 客户资料和访谈原文。
4. 平台账号、密码、验证码和密钥。
5. 一次性临时情绪、私人关系细节和未经授权的他人信息。
```

记忆更新规则：

```text
1. 新记忆保存前必须先展示给我确认。
2. 临时任务要求不自动进入长期记忆。
3. 每月回顾一次长期记忆，删除过时内容。
4. 如果记忆和当前任务冲突，以当前任务为准。
5. 涉及他人隐私时不保存。
```

讲师点评：

优秀的记忆规则不是“什么都记住”，而是把长期稳定偏好和一次性上下文分开。保存偏好能提高协作效率，保存敏感信息会增加风险。

可迁移点：

- 记忆系统要有新增、确认、删除和覆盖规则。
- 偏好可以保存，隐私和商业资料不应保存。
- 当前任务约束应优先于历史偏好。

## 示例 7：团队 AI 使用安全规范

场景：

一个 12 人团队准备在日常工作中使用 AI，需要先建立最小安全规范。

规范草案：

```text
适用范围：
团队成员使用 AI 进行资料整理、公开信息分析、草稿生成、会议纪要和内部知识库问答。

允许使用：
1. 公开资料摘要。
2. 不含客户身份信息的通用文案草稿。
3. 已匿名化的用户反馈。
4. 内部流程说明的改写。
5. 低风险代码解释和测试建议。

禁止上传：
1. 密码、密钥、令牌和验证码。
2. 客户个人信息。
3. 未公开财务数据。
4. 合同、报价和采购细节。
5. 未发布产品计划。
6. 受保密协议限制的材料。

必须人工复核：
1. 对外发布内容。
2. 法律、财务、医疗和人事相关内容。
3. 数据分析结论。
4. 代码修改建议。
5. 涉及权限、删除、发送、审批和付款的动作。

输出要求：
1. 事实类输出必须列出来源。
2. 不确定信息必须标注。
3. AI 生成内容对外使用前由负责人确认。
4. 重要任务保留 prompt、输入摘要、输出和人工修改记录。

事故处理：
发现误上传敏感信息或错误输出被使用时，立即通知负责人，停止继续扩散，并记录时间、材料、影响范围和处理动作。
```

讲师点评：

这个规范适合作为起点，因为它先定义了允许、禁止、复核和事故处理。很多团队失败在只写“注意安全”，却没有说哪些数据、哪些动作、哪些输出必须被管住。

可迁移点：

- 安全规范要覆盖输入、输出、行动和日志。
- 禁止事项必须具体。
- 高风险领域不应只依赖 AI 自查。
- 事故处理要先阻断扩散，再复盘制度。

进一步修改建议：

不同团队需要补充自己的工具清单、权限分级、日志保存周期和负责人。工程团队还应补充代码仓库、生产环境和密钥处理规则。

## 示例 8：结业项目小包

项目名称：

公开课程资料整理助手。

使用场景：

教师每周把公开课程资料、课堂讨论记录和作业问题整理成下周教学准备材料。

目标用户：

高校教师、培训讲师、助教。

材料 1：高质量 prompt

```text
请根据我提供的公开课程资料和课堂记录，整理下周备课材料。

目标：
帮助教师快速看到本周学生理解情况、下周需要强化的概念和可用课堂练习。

背景：
课程面向 AI 初学者。本周主题是 prompt 五要素和任务拆解。

约束：
- 只依据我提供的资料。
- 不保存学生个人信息。
- 不评价具体学生。
- 不把少数提问当成全班结论。
- 对不确定信息标注“需要教师判断”。

验收标准：
1. 能指出 3 个常见理解偏差。
2. 能生成 2 个课堂练习。
3. 能列出下周讲解重点。
4. 所有结论都有资料依据。

输出格式：
1. 本周学习情况摘要。
2. 常见理解偏差。
3. 下周讲解重点。
4. 课堂练习。
5. 需要教师判断的问题。
```

材料 2：5 步工作流

```text
第 1 步：整理输入资料
输入：公开课程资料、匿名课堂问题、作业共性问题。
输出：资料清单和来源。
检查点：不包含学生个人信息。

第 2 步：提取学习问题
输入：第 1 步资料。
输出：概念误解、操作问题、表达问题。
检查点：每个问题有对应依据。

第 3 步：生成讲解重点
输入：第 2 步输出。
输出：下周 3-5 个讲解重点。
检查点：不要超过课堂时间。

第 4 步：设计课堂练习
输入：讲解重点。
输出：基础练习、进阶练习、讨论问题。
检查点：练习能在课堂内完成。

第 5 步：教师复核
输入：前 4 步输出。
输出：最终备课清单。
检查点：教师确认事实、难度和安全边界。
```

材料 3：skill/card

```text
名称：
课程资料整理 skill

用途：
把公开课程资料和匿名课堂反馈整理成备课材料。

触发场景：
每周课后复盘、下周备课、助教整理问题。

输入要求：
公开资料、匿名问题、课程主题、课堂时长、学习者水平。

执行步骤：
1. 检查输入是否含个人信息。
2. 整理资料来源。
3. 提取共性问题。
4. 生成讲解重点。
5. 设计课堂练习。
6. 列出教师需要判断的问题。

输出格式：
摘要、问题、讲解重点、练习、复核清单。

边界：
不处理未匿名化学生信息，不评价个人表现，不编造课堂数据。

验收标准：
能支持下一次 90 分钟课程备课。
```

材料 4：agent 工作说明

```text
目标：
在教师提供资料后，生成备课草案和复核清单。

可使用工具：
读取指定资料文件，生成 Markdown 草案。

允许读取：
教师指定的公开资料和匿名课堂反馈。

允许写入：
备课草案文件。

禁止事项：
不读取未授权文件，不保存学生个人信息，不自动发布，不发送邮件，不修改原始资料。

验收标准：
草案包含讲解重点、课堂练习和教师复核问题。

需要人工确认的动作：
保存长期模板、对外发送、加入课程资料库。
```

材料 5：安全规范

```text
1. 学生个人信息不进入 AI。
2. 课堂问题必须先匿名化。
3. AI 输出只作为备课草案。
4. 教师负责最终判断。
5. 对外发布前必须人工复核。
```

材料 6：测试记录

```text
测试日期：2026-05-07
输入材料：公开课程大纲、匿名课堂问题 12 条、作业共性问题 6 条。
AI 输出摘要：生成 4 个讲解重点和 2 个课堂练习。
人工修改：删除一个难度过高的练习，补充一个基础练习。
失败点：AI 把 2 条学生问题误认为全班共性问题。
下次修改：要求每个共性问题至少有 3 条依据，少于 3 条则标注为个别问题。
是否可以复用：可以，但必须保留教师复核步骤。
```

讲师点评：

这个结业项目覆盖 prompt、工作流、skill、agent 边界、安全规范和测试记录。它不是复杂系统，但已经具备可复用、可验证和可治理的基本形态。

评分参考：

```text
问题定义：13/15
Prompt 质量：14/15
工作流设计：17/20
Skill 沉淀：13/15
Agent 边界：13/15
验证记录：8/10
安全治理：9/10
总分：87/100
```

优先修改建议：

1. 补充“共性问题”的数量标准。
2. 为课堂练习增加时长和难度标签。
3. 明确哪些资料可以进入长期课程资料库。

## 常见不合格作业对照

不合格写法：

```text
帮我做一个 AI 助手，能自动整理资料、提醒我、发邮件、更新任务，还能记住我的习惯。
```

问题：

- 目标过大。
- 工具权限不清。
- 自动发送邮件是高风险动作。
- 记忆边界不清。
- 没有验收标准。

改进方向：

```text
先选择一个低风险子任务：
只读取我指定的公开资料，生成一份 Markdown 摘要草案。

禁止：
不发送邮件，不删除文件，不读取未授权目录，不保存敏感信息。

验收：
摘要包含来源、结论、不确定信息和人工复核清单。
```

讲师处理方式：

让学员先缩小任务，再补工具、权限、禁止事项和人工确认点。写不清边界的 agent 作业，先退回工作流作业。

## 讲师点评句式

指出亮点：

```text
这个版本最好的地方是把输出格式和验收标准写清楚了，所以 AI 不需要猜交付物长什么样。
```

指出边界问题：

```text
这里的问题不是 prompt 不够长，而是没有写清哪些信息不能上传、哪些动作必须人工确认。
```

指出事实风险：

```text
这个结论需要来源支持。请把“AI 判断”改成“基于哪段资料得出”，或者标注为推测。
```

推动改写：

```text
请保留你的任务目标，只重写背景、约束和验收标准。先不要增加新功能。
```

降低难度：

```text
这个任务适合作为结业项目，但不适合作为第 1 周练习。请先抽出其中一个低风险步骤。
```

## 复用清单

讲师收集作业时，可以按这张清单判断是否值得放入示例库：

- 是否已经匿名化。
- 是否来自真实任务结构。
- 是否包含原始版本和改进版本。
- 是否有明确失败点。
- 是否有验收标准。
- 是否能迁移到其他读者场景。
- 是否没有依赖某个特定工具的短期功能。
- 是否不会鼓励上传敏感资料或放大 agent 权限。
