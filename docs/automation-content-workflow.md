# 自动化维护与扩写方案

最后维护：2026-05-14

这份说明回答一个实际问题：能不能用 GitHub Actions 自动完善、扩充和更新本书内容？

答案是：能自动做一部分，但不应该让程序无审查地替人写定稿。

更稳妥的做法是把自动化分成三层：

1. 自动发现问题。
2. 自动生成候选修改。
3. 人工决定是否合并。

GitHub Actions 擅长第 1 和第 2 层，最终定稿仍应由人负责。

## 适合自动化的部分

GitHub Actions 很适合做这些事：

- 定时检查链接、术语、Markdown 规范和 Pages 构建。
- 扫描哪些页面太旧、哪些目录入口重复、哪些章节需要补例子。
- 根据固定规则生成维护报告。
- 把候选修改整理成 issue 或 draft PR。
- 在人工触发时，调用外部模型生成草稿建议。

这些任务本质上是“发现、整理、提示”，不要求程序像人一样理解整本书的叙事结构。

## 不适合自动化的部分

不建议让 Actions 直接自动完成这些事：

- 直接把 AI 生成的正文推到 `main`。
- 不经人工复核就改事实、改安全边界、改教学路径。
- 让模型决定哪些案例保留、哪些案例删除。
- 让模型单独判断哪些前沿事实已经过时。

原因很简单：程序可以批量处理规则，但很难像人一样判断一本书的节奏、叙事、教学顺序和风险边界。

## 推荐流水线

从 2026-05-18 起，本书维护采用“双轨更新”原则：每次更新除了修复或扩充已有内容，还要评估是否有新的技术概念、生态现象或历史案例需要纳入。自动化可以帮助发现候选项，但不能替人工判断概念是否真实、是否过度推演、是否需要引用。

### 方案 A：只做维护提醒

适合不接模型接口的团队。

```text
定时运行 -> 检查链接和术语 -> 汇总页面状态 -> 生成维护报告 -> 开 issue 或发通知 -> 人工处理
```

适合处理：

- 断链。
- 标题层级问题。
- 过长页面提示。
- 目录入口遗漏。
- 需要复核的前沿资料。

本项目已经落地了这个最低可行版本：

```text
scripts/content-health-report.ps1
.github/workflows/content-health.yml
```

它每周一自动生成一次内容健康报告，也可以手动触发。报告只读扫描 Markdown 文件，输出这些候选项：

- 可能需要扩写的短页面。
- 可能需要拆分或增加导航的长页面。
- 缺少一级标题的页面。
- 第 0-14 章是否缺少本章导读、本章收尾或章节导航。
- 含有前沿技术、协议、模型或复核关键词的动态事实复核候选。

这一步不调用模型，也不改正文。它的作用是先让维护者知道“哪里可能需要看”，再决定是否人工扩写或发起候选 PR。

### 方案 B：生成候选稿

适合愿意接入模型 API 的团队。

```text
定时运行或手动触发 -> 扫描缺口 -> 生成提示词 -> 调用模型 -> 产出草稿分支或 draft PR -> 人工审阅 -> 合并或退回
```

适合处理：

- 补一个同结构案例。
- 补一个术语解释。
- 补一个复盘模板。
- 补一个章节入口说明。
- 按既有风格扩展附录条目。

关键要求：

- 草稿必须保存在分支或 draft PR，不直接写主分支。
- 每次生成都要记录来源、提示词和修改意图。
- 最终合并前，必须人工检查事实、风格和结构。

## 权限和触发建议

GitHub 官方文档建议对工作流权限做最小授权，并把定时触发、手动触发和拉取请求检查分开管理。也就是说，扫描和生成最好不要和发布权限绑在一起。

建议的触发方式：

| 触发 | 用途 |
| --- | --- |
| `schedule` | 每周或每月跑一次维护扫描 |
| `workflow_dispatch` | 人工触发生成候选稿 |
| `pull_request` | 检查候选稿是否符合规范 |

建议的权限思路：

- 扫描工作流只读。
- 创建 issue 或 PR 的工作流才需要写权限。
- 不把密钥暴露给不需要它的步骤。

## 一个可落地的分工

### 自动化负责

- 找出待修复页面。
- 把候选项分组。
- 生成摘要。
- 列出可改位置。
- 建议下一步动作。

### 人工负责

- 决定是否新增案例。
- 决定是否改写章节结构。
- 判断事实是否需要重新核验。
- 判断某个旧技术是保留、标历史还是移出正文。
- 决定最终表述和发布节奏。

## 对这本书最合适的自动化范围

结合本项目的结构，比较合适的自动化是：

1. 定时检查 `docs/SUMMARY.md`、首页入口和本地链接。
2. 自动标出“可能需要扩写”的章节。
3. 把已有案例按角色、技术和风险标签归类。
4. 对前沿资料生成复核提醒。
5. 对重复度高的页面生成简短维护建议。

不建议的自动化是：

1. 自动改写核心章节的教学顺序。
2. 自动替换事实判断。
3. 自动决定删掉哪些案例。
4. 自动把草稿当作定稿发布。

## 如果要上模型接口

如果后续要把模型接进 GitHub Actions，推荐的做法是：

1. 把提示词放进仓库，作为可审查文件。
2. 把生成结果写入独立分支或 draft PR。
3. 让人工维护者审核后再合并。
4. 在 `CHANGELOG.md` 和 `MEMORY.md` 记录这次生成的范围。
5. 对涉及事实的内容，仍按官方来源复核。
6. 每次候选稿必须标注“已有内容扩充”和“新概念添加”两个部分。
7. 每个新概念必须列出来源、核验日期、事实边界和本书推演边界。

这条路能明显提高维护效率，但它不是“让程序像人一样写书”，而是“让程序帮人省掉重复劳动”。

## 新概念候选审查表

| 检查项 | 通过标准 |
| --- | --- |
| 概念是否真实存在 | 至少能找到官方文档、论文、产品说明、可信报告或明确的社区实践痕迹 |
| 是否已有稳定定义 | 有则按来源写；没有则标注为本书综合判断 |
| 是否容易误导 | 涉及账号、绕过限制、隐私、版权、自动化执行时，只写风险和治理，不写滥用步骤 |
| 是否需要引用 | 涉及动态事实、产品能力、协议、论文和安全建议时必须引用 |
| 是否需要进入目录 | 影响读者理解主线的概念要加入 `mkdocs.yml`、`SUMMARY.md`、主题索引和相关首页 |
| 是否完成复查 | 发布前确认没有编造来源、没有把推演写成事实 |

## 建议的最低可行版本

如果你现在就想开始，最小可行版本是：

```text
1. 保留现有本地检查和 Pages 构建检查。
2. 每周跑一次维护扫描。
3. 让扫描结果自动生成 issue。
4. 维护者人工挑选 issue，决定是否扩写。
5. 扩写内容只进 draft PR，不直接进 main。
6. 合并前再跑一次链接、术语和 lint 检查。
```

当前仓库已经完成第 1-2 步，并用 artifact 保存扫描报告。后续如果要继续推进，可以增加一个人工触发 workflow，把报告中的某一条候选项转换成 issue；再往后才考虑接入模型生成 draft PR。

结构层面的人工判断会记录到 [书籍结构审计与内容健康治理](book-structure-audit.md)。如果后续要把扫描结果自动转 issue，建议先读取这页，避免把封面、版权、许可证或故意短的入口页误判成必须扩写的正文缺口。
