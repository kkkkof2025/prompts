# Prompt 调试指南

Prompt 调试不是把一句话越写越长，而是有顺序地定位问题：到底是目标不清、背景不足、约束缺失、输出格式不稳，还是任务本身需要拆成工作流。

这份指南适合在 AI 输出不好时使用。建议配合 [常见误区与纠偏指南](common-pitfalls.md)、[AI 任务选择决策指南](task-decision-guide.md)、[AI 工作流配方库](workflow-recipes.md) 和 [课堂练习工作纸](classroom-worksheets.md) 使用。

## 调试原则

每次只改一个关键变量。

如果同时改目标、背景、语气、格式和示例，你很难知道到底是哪一处让结果变好了。

先修任务，再修表达。

很多输出不好，不是因为 AI 不会写，而是它不知道要解决什么问题。先确认任务目标，再考虑文风。

先让问题暴露，再让 AI 重写。

不要一上来就说“重写一版”。先让 AI 指出哪里不合格，再决定怎么改。

复杂任务先拆开。

如果一个 prompt 调了 3 次仍然不稳定，通常不是继续加字，而是应该拆成工作流。

## 5 步调试流程

```text
保存原始 prompt -> 标记输出问题 -> 判断失败类型 -> 修改一个变量 -> 重新测试
```

填写模板：

```text
原始 prompt：

AI 输出摘要：

主要问题：
1.
2.
3.

我判断属于哪类失败：

这次只修改：

修改后的 prompt：

重新测试结果：

是否需要继续调试：
```

## 快速诊断表

| 输出症状 | 可能原因 | 优先修法 |
| --- | --- | --- |
| 答非所问 | 目标不清或任务太宽 | 重写目标，限定交付物 |
| 说得很空 | 缺少背景、例子或验收标准 | 补场景、读者和合格标准 |
| 编造事实 | 没有限定资料来源 | 要求只依据资料并标注不确定 |
| 格式乱 | 输出格式不明确 | 给字段、顺序和示例 |
| 太长 | 没有长度限制 | 加字数、层级或取舍规则 |
| 太短 | 没有深度要求 | 加分析维度和例子要求 |
| 语气不对 | 读者和场景不清 | 补目标读者、渠道和语气 |
| 越改越偏 | 没有保留约束 | 要求保留结构，只改指定部分 |
| 反复失败 | 任务过大 | 拆成工作流 |
| 风险太高 | 缺少人工复核点 | 降级为草稿或检查清单 |

## 失败类型 1：目标不清

弱 prompt：

```text
帮我优化一下这个方案。
```

问题：

AI 不知道“优化”是什么意思。是要更短、更有说服力、更适合老板、更适合客户，还是更容易执行。

调试方式：

```text
请先不要改写。请判断这个方案是否能用于【场景】。

目标：
让【读者】在【时间】内理解【核心结论】，并能决定【下一步行动】。

请只从以下 3 个角度提修改建议：
1. 结论是否清楚。
2. 依据是否足够。
3. 下一步是否可执行。
```

自查：

- 目标里是否有读者。
- 目标里是否有使用场景。
- 目标里是否能判断完成或未完成。

## 失败类型 2：背景不足

弱 prompt：

```text
帮我写一个学习计划。
```

问题：

AI 不知道学习者基础、目标、时间、偏好和限制，只能生成通用计划。

调试方式：

```text
请先问我最多 5 个问题，再制定学习计划。

你必须确认：
1. 我的当前基础。
2. 我的目标。
3. 每周可投入时间。
4. 我已经有的材料或工具。
5. 我不希望学习的内容。
```

背景补充模板：

```text
我的基础：
我的目标：
可投入时间：
已有材料：
限制：
验收方式：
```

自查：

- 一个不了解你的人能否理解任务背景。
- 背景是否只保留影响输出的信息。
- 是否写出了时间、资源和限制。

## 失败类型 3：约束缺失

弱 prompt：

```text
根据这些会议记录写一份纪要。
```

问题：

AI 可能把讨论写成决定，把缺失负责人补成猜测，把争议抹平。

调试方式：

```text
请只依据会议记录写纪要。

约束：
1. 不补充记录中没有出现的信息。
2. 区分已决定、仍在讨论和待确认。
3. 负责人、截止时间、依赖缺失时写“待确认”。
4. 不替团队做业务判断。
```

自查：

- 是否写了不能做什么。
- 是否说明信息不足时如何处理。
- 是否限制 AI 不能编造、不能过度总结、不能越权判断。

## 失败类型 4：验收标准缺失

弱 prompt：

```text
写得更专业一点。
```

问题：

AI 可能只是换成更复杂的词，但没有让内容更准确、更清晰或更可用。

调试方式：

```text
请按以下验收标准修改：
1. 读者能在 2 分钟内理解主结论。
2. 每个判断都有依据。
3. 删除空泛形容词。
4. 保留限制和风险。
5. 最后列出需要人工确认的信息。

请先指出原文哪里不符合标准，再给修改版。
```

自查：

- 验收标准是否能被第三个人检查。
- 是否写出了拒收条件。
- 标准是否和真实使用场景一致。

## 失败类型 5：输出格式不稳

弱 prompt：

```text
整理一下这些用户反馈。
```

问题：

AI 可能一会儿输出段落，一会儿输出表格，一会儿按情绪分类，一会儿按功能分类。

调试方式：

```text
请按固定表格输出。

字段：
1. 原始反馈编号。
2. 反馈类型。
3. 用户想解决的问题。
4. 原文证据。
5. 是否需要进一步确认。
6. 初步建议。

分类标签只能使用：
故障、功能需求、体验问题、价格问题、正面反馈、其他。
```

自查：

- 是否列出了字段。
- 是否限定了分类标签。
- 是否说明不确定时如何写。
- 是否给了可以复制到下一步工具的格式。

## 失败类型 6：示例不够

弱 prompt：

```text
用我喜欢的风格写。
```

问题：

“喜欢的风格”对 AI 来说太模糊。没有示例时，它只能猜。

调试方式：

```text
请模仿下面示例的结构和语气，但不要复制具体内容。

示例：
【粘贴 1-2 段】

请总结这个示例的风格规则：
1. 句子长度。
2. 语气。
3. 结构。
4. 不使用的表达。

确认规则后，再改写我的内容。
```

自查：

- 是否给了正面示例。
- 是否说明示例中哪些部分要模仿。
- 是否说明哪些部分不能复制。

## 失败类型 7：示例误导

表现：

AI 过度模仿示例，把不该复制的结构、语气或内容也带进新任务。

调试方式：

```text
下面示例只用于说明输出结构，不用于模仿内容和语气。

请只学习：
1. 字段顺序。
2. 信息密度。
3. 每段长度。

不要学习：
1. 示例中的具体事实。
2. 示例中的行业背景。
3. 示例中的结论。
```

自查：

- 示例的作用是否说清楚。
- 是否提供了反例。
- 是否提醒 AI 不要复制示例事实。

## 失败类型 8：一次要求太多

弱 prompt：

```text
请分析资料、做竞品对比、给方案、写汇报、生成执行计划。
```

问题：

任务混合了阅读、判断、决策、写作和计划。任何一步偏掉，后面都会跟着偏。

调试方式：

```text
请把这个任务拆成 5 步，不要直接执行。

每一步只做一类动作：
1. 整理资料。
2. 对比分析。
3. 形成判断。
4. 写汇报草稿。
5. 生成执行计划。

每一步都要写输入、输出和检查点。
```

自查：

- prompt 是否同时用了多个动词。
- 输出是否包含多个不同交付物。
- 是否需要中间验收。

## 失败类型 9：AI 过度服从错误假设

表现：

你给了一个错误前提，AI 没有提醒，直接沿着错误前提继续写。

调试方式：

```text
在执行前，请先检查我的任务说明中是否有明显不合理、矛盾或需要确认的前提。

请输出：
1. 可以直接接受的前提。
2. 需要确认的前提。
3. 可能错误的前提。
4. 你建议我先补充的问题。

确认前不要开始正式生成。
```

自查：

- 是否要求 AI 质疑前提。
- 是否允许 AI 先问问题。
- 是否把“不知道”视为合格输出的一部分。

## 失败类型 10：越改越乱

表现：

每次让 AI 修改，它都会顺手改动其他部分，最后偏离原始目标。

调试方式：

```text
请只修改第【编号】部分。

必须保留：
1. 原有标题结构。
2. 原有事实。
3. 原有结论方向。

只允许修改：
1. 句子顺序。
2. 表达清晰度。
3. 重复内容。

请先列出你将修改的地方，等我确认后再改。
```

自查：

- 是否限定了修改范围。
- 是否写了必须保留的内容。
- 是否要求先列修改计划。

## 失败类型 11：事实核验不足

表现：

AI 输出看起来完整，但里面有未经核验的数字、政策、产品功能、引用和时间。

调试方式：

```text
请不要继续扩写。请把现有回答拆成事实核验表。

字段：
1. 事实陈述。
2. 是否来自我提供的资料。
3. 是否可能过时。
4. 需要核验的来源。
5. 未核验前是否应删除或保留。
```

自查：

- 是否区分事实、推测和建议。
- 是否要求来源。
- 是否删除无法核验但影响判断的内容。

## 失败类型 12：安全边界不清

表现：

AI 生成了可以对外发送、自动执行、修改权限或处理敏感数据的建议，但没有提醒风险。

调试方式：

```text
请先做安全边界检查，不要直接执行或生成最终稿。

请列出：
1. 是否包含敏感数据。
2. 是否涉及对外发布。
3. 是否涉及删除、发送、支付、审批或改权限。
4. 哪些动作必须人工确认。
5. 更低风险的替代做法。
```

自查：

- 这件事是否会影响别人。
- 输出是否会被公开或发送。
- 是否有不可撤回动作。
- 是否需要负责人确认。

## 调试记录模板

建议把重要 prompt 的调试过程保存下来：

```text
任务名称：

版本 1 prompt：

版本 1 输出问题：

修改点：

版本 2 prompt：

版本 2 输出变化：

仍然存在的问题：

最终可用版本：

适用场景：

不适用场景：

需要人工复核的内容：
```

当一个 prompt 连续 3 次在真实任务中有效，就可以考虑整理成模板、配方或 skill。

## 什么时候停止调试 Prompt

出现以下情况，不要继续堆 prompt：

- 同一任务改了 3 次仍然不稳定。
- prompt 已经长到难以维护。
- 每次都需要解释大量背景。
- 输出必须引用大量资料。
- 任务需要多步执行和中间检查。
- 任务需要调用工具或读取文件。
- 任务涉及高风险动作。

对应处理：

| 情况 | 转向 |
| --- | --- |
| 多步骤 | 工作流 |
| 高频重复 | 模板或 skill |
| 依赖资料 | RAG 或资料核验 |
| 需要行动 | agent 工作说明 |
| 高风险 | 人工主导，AI 只辅助 |

## 让 AI 帮你调试 Prompt

可复制 prompt：

```text
请帮我调试这个 prompt。

原始 prompt：
【粘贴 prompt】

AI 输出问题：
【说明哪里不满意】

请输出：
1. 可能失败原因。
2. 最应该先改的 1 个地方。
3. 改写后的 prompt。
4. 这次改写解决了什么。
5. 仍然可能失败的情况。

要求：
不要一次性重写得很复杂，只做最小必要修改。
```

## 一页调试清单

每次输出不好，按顺序检查：

```text
1. 目标是否可判断。
2. 背景是否足够。
3. 约束是否写出不能做的事。
4. 验收标准是否可检查。
5. 输出格式是否固定。
6. 是否需要示例或反例。
7. 是否一次要求太多。
8. 是否需要事实核验。
9. 是否涉及安全边界。
10. 是否应该升级为工作流、skill、RAG 或 agent。
```

## 最后提醒

Prompt 调试的目标不是写出一段万能咒语，而是让任务、资料、边界和验收标准变清楚。

真正有效的调试记录，最后应该能回答：

```text
这个任务适合什么场景？
需要什么输入？
怎样算合格？
哪里必须人工判断？
下次如何复用？
```
