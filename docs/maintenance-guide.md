# 项目维护指南

AI 领域变化很快。这本书要长期有用，关键不是一次写完，而是建立稳定维护流程。

## 维护节奏

建议分三类维护：

| 频率 | 内容 | 负责人 |
| --- | --- | --- |
| 每次提交 | 链接、目录、MEMORY、CHANGELOG | 提交者 |
| 每次提交 | Markdown lint、术语一致性、Pages 构建 | 提交者和 CI |
| 每季度 | 前沿动态、模型、工具、协议、资源链接 | 维护者 |
| 每年 | 全书结构、学习路线、案例是否过时 | 维护者和读者社区 |

## AI 协作交接约定

每次让 AI 继续维护本项目时，先让它说明本轮工作方向，再开始改文件。这个约定用于避免只汇报“已经做了什么”，却没有提前说明“接下来准备做什么”。

开工前建议先交代：

```text
1. 已确认的当前状态：读过哪些入口文件，判断项目处于哪个阶段。
2. 本轮准备做的内容和方向：准备补哪类缺口，为什么优先做它。
3. 本轮不会碰的范围：例如不做联网事实复核、不改发布配置、不重排目录。
4. 计划修改的文件：列出预计会动的核心文件。
5. 验证方式：说明会跑哪些本地检查，或说明为什么本轮不需要跑某类检查。
```

收尾时建议同时给出：

```text
1. 本轮已经完成的内容。
2. 已运行的检查和结果。
3. 尚未处理的问题。
4. 下次建议优先做的方向。
```

## 案例和技术收录原则

本书的案例不以短为目标，而以有效、有特点、能复盘为目标。案例可以较长，也可以围绕同一类技术拆成多个不同案例，只要每个案例能展示不同的任务、失败方式、治理边界或迁移价值。

前沿技术可以纳入正文或案例库，但不能写成永久结论。只要概念、来源和边界没有写错，就可以作为学习对象记录；涉及模型、协议、SDK、接口、价格、许可证和可用地区时，仍要按前沿资料复核流程查官方来源。

过时技术也可以保留。过时技术常常能解释今天的工具为什么强调结构化输出、权限、审计、评估、协议和人工复核。处理过时技术时，优先判断它属于哪一种：

| 类型 | 处理方式 |
| --- | --- |
| 产品入口过时，但思想仍有价值 | 改成技术演进案例 |
| 实践路线不再推荐，但失败有代表性 | 改成历史复盘案例 |
| 概念仍稳定，只是实现变化 | 保留正文并标注核验日期 |
| 容易误导读者直接采用高风险做法 | 从教程中移除，保留风险复盘 |

新增或改写案例时，至少写清：

```text
它想解决什么问题。
它有特点的地方。
它适合和不适合的任务。
它容易失败的地方。
今天还能学什么。
如果已经过时，应怎样标注和复盘。
```

## 每次修改后的检查

必须检查：

```text
1. 新增页面是否加入 docs/SUMMARY.md。
2. 重要入口是否加入 README.md 或 docs/index.md。
3. 本地 Markdown 链接是否可解析。
4. 是否需要更新 MEMORY.md。
5. 是否需要更新 CHANGELOG.md。
6. 若接近 1.0 发布，是否同步检查 [1.0 发布前总检查清单](release-checklist-1.0.md)。
```

可使用本地脚本检查：

```powershell
./scripts/check-markdown-links.ps1 -Root . -CheckPlaceholders
./scripts/check-terminology.ps1 -Root .
```

GitHub Actions 会在 push 和 pull request 时运行 Markdown lint、本地链接检查、术语一致性检查和 Pages 构建检查。外部链接检查默认每月运行一次，也可以手动触发。

如果修改涉及事实：

```text
1. 是否引用官方文档、论文、标准组织或可信报告。
2. 是否标注核验日期。
3. 是否避免写成永久不变的结论。
4. 是否同步更新 docs/appendix-resources.md。
5. 是否需要填写或更新 [前沿资料季度复核记录表](frontier-review-log.md)。
```

## 版本号建议

本项目可以采用简单语义版本：

```text
0.1.x：初稿修正
0.2.x：补充案例、练习、模板
0.3.x：发布、维护、教学材料
0.4.x：图表、电子书、自动化检查
1.0.0：结构稳定，可作为正式开源书发布
```

## 前沿内容维护规则

前沿内容包括：

- 模型名称、能力、上下文长度、价格和接口。
- OpenAI、Anthropic、Google、DeepSeek、Kimi 等厂商产品。
- OpenClaw、Hermes、HiMeS、MCP、A2A 等项目或协议。
- AI 风险、合规、版权、隐私和政策。

维护原则：

- 优先官方来源。
- 记录核验日期。
- 不用社交媒体传言替代文档。
- 对不确定信息标注“待核验”。
- 不写“最强”“唯一”“必然替代”这类不可维护判断。

执行季度复核时，先使用 [前沿资料季度复核执行手册](frontier-review-playbook.md) 确认复核层级、范围和修改顺序，再用 [前沿资料季度复核记录表](frontier-review-log.md) 记录复核批次、来源、影响页面和处理动作。这样可以避免只更新一句结论，却忘记同步案例、选型表、资源附录和发布记录。

## 如何处理读者反馈

读者反馈可以分四类：

| 类型 | 处理方式 |
| --- | --- |
| 错别字和格式 | 直接修复 |
| 初学者看不懂 | 优先补例子，不急着加术语 |
| 事实过时 | 查官方来源后更新 |
| 新工具推荐 | 先放入资源附录，验证后再进正文 |

课堂、读书会和团队试点反馈建议使用 [试读与试跑反馈包](feedback-validation-kit.md) 记录。真实反馈进入公开文档前，先去除可识别个人、组织、客户和业务敏感信息。

## 文件边界

- `README.md`：项目入口，不写过长正文。
- `docs/index.md`：书稿入口，帮助读者开始阅读。
- `docs/SUMMARY.md`：所有主要页面目录。
- `docs/cases/`：按角色拆分的真实应用案例。
- `docs/chapter-validation-map.md`：章节练习、复盘材料和发布验收证据映射。
- `docs/feedback-validation-kit.md`：试读、课堂试跑和团队试点反馈收集模板。
- `docs/frontier-review-playbook.md`：前沿资料季度复核的执行流程、影响判断和收尾检查。
- `docs/frontier-review-log.md`：前沿模型、协议、工具和安全资料的季度复核记录。
- `MEMORY.md`：当前状态和维护记忆。
- `CHANGELOG.md`：面向公开发布的变更记录。
- `ROADMAP.md`：后续方向和版本规划。
- `docs/appendix-resources.md`：前沿来源和核验清单。
- `docs/term-style-guide.md`：术语写法规范。
- `docs/ebook-guide.md`：电子书和离线阅读说明。
- `scripts/`：本地检查、外部链接检查和电子书导出脚本。

## 维护者 prompt

后续可以用这个 prompt 让 AI 协助维护：

```text
请阅读 README.md、MEMORY.md、CHANGELOG.md、docs/SUMMARY.md 和 docs/appendix-resources.md。
任务：检查这本 AI 学习方法开源书是否有过时、断链、缺少目录入口或维护记录不一致的问题。
要求：
1. 先用 3-5 行说明当前已完成状态、本轮准备做的方向、预计修改范围和验证方式。
2. 先列出问题，不要直接修改。
3. 对涉及事实变化的问题，优先查官方来源。
4. 给出最小修改计划。
5. 修改后更新 MEMORY.md 和 CHANGELOG.md。
6. 收尾时说明本轮已完成内容、检查结果和下次建议方向。
```

## 发布质量标准

达到以下条件，可以考虑标记为 `1.0.0`：

- 全书章节结构稳定。
- 每章至少有一个练习和一个真实案例链接。
- 术语表覆盖主要概念。
- 术语写法规范和术语一致性脚本通过。
- 资源附录经过一次季度复核。
- 本地链接检查通过。
- GitHub Actions Markdown Check 通过。
- GitHub Pages 构建检查通过。
- 许可证明确。
- 试读、课堂或团队试点反馈已经记录，或明确标注尚未验证的材料。
- 路线图和变更记录同步。
- README、贡献指南、发布指南、维护指南和 [1.0 发布前总检查清单](release-checklist-1.0.md) 完整。
