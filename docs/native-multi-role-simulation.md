# 原生多角色模拟：没有平台时的多Agent协作

> 在 OpenClaw、Coze、Dify 等平台出现之前，多角色协作已经可以通过纯 Prompt 工程实现。
> 理解这套原生方法，比学会用某个平台更重要——因为你知道了**为什么**需要平台，而不是**只能**用平台。

---

## 一、核心思想：一个模型，N 个角色

**本质**：让同一个 LLM 在其"工作记忆"中同时扮演多个角色，每个角色有独立的视角、职责和输出格式，通过结构化的对话协议进行协作。

与 OpenClaw 多 Agent 的本质区别：

| 维度 | 原生角色模拟 | OpenClaw 多 Agent |
|------|------------|------------------|
| 执行者 | 一个 LLM 实例 | 多个独立的 agent 实例 |
| 记忆隔离 | prompt 内模拟，无真隔离 | 每个 agent 有独立上下文 |
| 工具权限 | 共享模型能力，无法独立授权 | 每个 agent 可以绑定不同工具 |
| 并行能力 | 串行对话，无法真正并行 | 可真正并行执行 |
| 可靠性 | 依赖 prompt 质量，易"串台" | 平台保证角色边界 |
| 上手门槛 | 零，只需要会写 prompt | 需要学习和配置平台 |
| 适用场景 | 轻量分析、多视角审查、快速原型 | 生产级自动化、权限分级、持久化 |

---

## 二、三层递进：从简单到复杂

### 2.1 第一层：一次对话内的多角色输出
{: #2-1第一层一次对话内的多角色输出 }

**最简方案**——在一次 prompt 中要求模型从多个角度输出。

#### 示例：产品方案的多角色审查

```text
请从以下三个角色的视角，分别Review下面这个产品方案。

产品方案：
[粘贴你的方案原文]

角色1 - 工程师视角：
- 这个方案的技术可行性如何？
- 实现上的最大风险是什么？
- 建议的技术方案替代选项？

角色2 - 设计师视角：
- 用户体验的核心问题是什么？
- 有没有违反直觉的设计？
- 建议的优化方向？

角色3 - 运营视角：
- 上线后的用户接受度预测？
- 最大的运营风险？
- 建议的上线策略调整？

请先分别以三个角色输出，最后做一个综合评价。
每个角色的输出用「=== [角色名]视角 ===」分隔。
```

**输出效果**：

```
=== 工程师视角 ===
技术可行性：整体可行，但第三个模块的实时数据处理部分...
最大风险：数据同步延迟可能超过 200ms 的体验阈值...
替代方案：考虑用 Redis Stream 替代 Kafka，降低运维复杂度...

=== 设计师视角 ===
用户体验问题：注册流程的第三步和第五步存在认知跳跃...
违反直觉的设计：删除确认按钮的位置与用户预期相反...
优化方向：将进度指示器从顶部移到左侧导航...

=== 运营视角 ===
用户接受度：核心功能对新用户的吸引力较强，但...
最大风险：上线首周的客服压力可能超出预期...
调整策略：建议先灰度 20% 用户，观察 48 小时再全量...
```

**适用场景**：快速多角度分析、方案评审、风险评估

**局限性**：角色间无法"对话"，只能各自输出；无法迭代讨论

### 2.2 第二层：角色间对话模拟
{: #2-2第二层角色间对话模拟 }

**进阶方案**——让角色之间"对话"，模拟团队的讨论过程。

#### 示例：产品方案讨论会

```text
你即将模拟一场三人产品讨论会。请严格按照以下规则进行：

会议规则：
1. 你先以「主持人」身份开场，提出讨论议题
2. 然后轮流扮演工程师(张工)、设计师(李设)、运营(王运)发言
3. 每个角色发言前先标明「[角色名]：」
4. 每个角色可以回应其他角色的观点
5. 每轮每个角色必须发言
6. 进行 3 轮后，主持人做总结

讨论议题：
我们要在下一版产品中增加一个"AI 学习助手"功能。
目标用户是大学生，核心场景是课后复习和作业辅导。

请开始。
```

**输出效果**：

```
[主持人]：今天的议题是「AI学习助手」的可行性。请各位从自己角度谈谈看法。张工，先从技术角度说说？

[张工]：技术上分两块——前端交互和后端模型调用。前端需要做一个对话界面+文档上传组件。后端核心是RAG pipeline…
最大的挑战是响应延迟。如果学生问一个复杂问题，检索+推理可能需要5-8秒。

[李设]：我对5-8秒的等待很担心。现在大学生的耐心阈值大概是3秒。
我建议设计成"渐进式回答"——先给一个30字摘要立即显示，再逐步展开详细内容...

[王运]：从运营角度看，关键问题不是功能好不好用，而是怎么让学生"知道"这个功能。
建议在考试周前2周灰度推送，配合"期末急救包"的营销主题...

[张工]：@李设 的渐进式方案技术上可以实现，用SSE流式返回就可以...
[李设]：@王运 说的"期末急救包"这个概念特别好，我们可以设计一个专门的彩蛋UI...
[王运]：@张工 技术成本大概多少？如果单次调用超过0.5元，我们运营侧就需要控制推送范围了...

[主持人]：好的，三轮讨论总结如下：技术上用SSE流式+渐进渲染解决延迟问题；
设计上采纳"期末急救包"概念做视觉包装；运营侧先灰度20%用户，按0.5元/次成本控制推广范围。
```

**适用场景**：脑暴会、需求评审、方案讨论

**局限性**：需要精细的 prompt 控制，角色容易"串台"；不适合长对话（上下文窗口有限）

### 2.3 第三层：带工具的角色分工
{: #2-3第三层带工具的角色分工 }

**高级方案**——给不同角色赋予不同的"工具权限"（通过 prompt 模拟）。

#### 示例：代码审查三剑客

```text
你即将模拟一个代码审查团队。每个角色有严格的权限边界。

角色定义：
1. [代码侦探] — 职责：发现 bug 和逻辑错误。权限：可以阅读代码，不能修改代码。
2. [性能顾问] — 职责：评估性能瓶颈。权限：可以阅读和分析代码，不能修改代码。
3. [安全专员] — 职责：检查安全漏洞。权限：可以阅读代码，不能修改代码。
4. [主程评审] — 职责：汇总意见并给出修改建议。权限：可以阅读代码，可以给出修改方案。

协作流程：
第1轮：代码侦探、性能顾问、安全专员各发现问题
第2轮：三人交叉确认（"我同意XX对YY的判断"或"我补充ZZ"）
第3轮：主程汇总，给出修改方案

请对以下代码进行审查：
```python
[粘贴你的代码]
```

每个角色发言格式：[角色名]：内容
```

**适用场景**：代码审查、安全审计、文档评审

## 三、多角色模拟的核心技巧

### 3.1 防止"串台"
{: #3-1防止串台 }

| 技巧 | 说明 | 示例 |
|------|------|------|
| 固定发言格式 | 每个角色必须有标记 | `[张工]：` |
| 限制发言轮次 | 明确总轮数和每轮顺序 | "进行 3 轮，每轮按 张工→李设→王运 顺序" |
| 设定角色边界 | 明确每个角色的"能做/不能做" | "张工只讨论技术，不要评价设计" |
| 要求自检 | 让模型在发言前确认角色 | "每轮发言前确认：你现在是[角色名]" |
| 分段执行 | 长对话拆成多段 prompt | 先讨论→汇总→给方案，分三个 prompt |

### 3.2 增强角色深度
{: #3-2增强角色深度 }

```text
角色设定技巧：
❌ 弱角色："你是一个工程师，审查代码"
✅ 强角色："你是张工，10年后端经验，擅长 Python 和分布式架构。
           你最近刚处理过一个类似的并发问题，所以对此特别敏感。
           你的说话风格：直接、用代码和数据说话，不喜欢废话。
           你特别关注：数据库连接池泄漏、异常处理缺失、竞态条件。"
```

### 3.3 控制讨论质量
{: #3-3控制讨论质量 }

```text
质量约束模板：
- "如果一个角色和前一个角色完全同意，必须说明为什么同意，而不是简单重复"
- "如果发现矛盾，先明确指出矛盾点，再各自解释立场"
- "最后一轮，每个角色必须提出至少一个"我们还没讨论到"的风险点"
```

## 四、什么时候用原生模拟，什么时候上平台

| 场景 | 原生模拟 | 使用平台 |
|------|---------|---------|
| 快速方案评审（10分钟内） | ✅ 足够 | 过度设计 |
| 单次脑暴会议 | ✅ 足够 | 过度设计 |
| 学习理解多Agent概念 | ✅ 最佳方式 | 跳过了理解 |
| 持续运行的自动化流程 | ❌ 不稳定 | ✅ 推荐 |
| 需要工具独立权限 | ❌ 无法隔离 | ✅ 必需 |
| 需要持久记忆和日志 | ❌ 手动管理 | ✅ 自动 |
| 团队多人使用 | ❌ 难以共享 | ✅ 推荐 |

## 五、从原生模拟到平台化的演进路径

学习多Agent的正确顺序应该是：

```
第1步：原生角色模拟（你现在在这里）
  → 理解：什么是"角色"、什么是"协作协议"、什么是"权限边界"
  → 用一两次就够了，重点是理解原理

第2步：用平台搭建第一个 Agent
  → OpenClaw / Coze / Dify
  → 你会发现：平台做的就是你 prompt 里写的那套规则，只是更稳定、更可复用

第3步：设计你的多 Agent 协作系统
  → 有了第1步的理解，你才知道平台为什么这么设计
  → 你才知道什么时候需要分 agent，什么时候一个 agent 足矣
```

## 六、练习

1. **基础练习**：为一个你熟悉的产品的功能更新，写一个三角色审查 prompt，模拟工程师+设计师+运营的讨论。
2. **进阶练习**：写一个会"吵架"的多角色 prompt——让两个角色的观点有冲突，看模型如何处理。
3. **挑战练习**：设计一个五角色的项目启动会 prompt，包含产品、开发、测试、设计、运维，设定发言规则，防止混乱。

---

> **核心理念**：理解原生多角色模拟，你才能判断什么时候一个聪明的 prompt 就够了，什么时候真的需要上平台。
