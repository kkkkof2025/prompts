# AI 模型选型实战案例集

最后核验：2026-05-07

这组案例演示怎样根据任务选择模型，而不是根据热度选择模型。案例中的模型类别是示意，不等于固定推荐；实际选型前应重新查看官方文档，并用自己的数据测试。

建议先读 [中外 AI 模型特色概览](model-landscape-china-global.md) 和 [第 5 章：模型选择、验证与评估](chapters/05-evaluation.md)，再用本页做练习。如果你的任务涉及资料权限、自动动作或高风险输出，请同时读 [AI 安全事故复盘案例集](safety-incident-retrospectives.md)。

## 选型原则

模型选型不是问：

```text
哪个模型最强？
```

而是问：

```text
在我的任务、数据、成本、延迟、语言、合规和工具边界下，哪个组合最稳？
```

每个案例都按同一结构展开：

```text
任务：
关键约束：
候选路线：
测试样例：
评分重点：
选择建议：
不建议：
上线前检查：
```

## 案例 1：个人中文写作助手

任务：

个人作者希望 AI 帮助整理读书笔记、改写文章、生成标题和检查逻辑。

关键约束：

- 中文表达自然。
- 能保留作者原意和语气。
- 成本不能太高。
- 不涉及敏感公司资料。
- 偶尔需要查最新资料，但最终由作者核验。

候选路线：

- 中文体验较好的通用对话模型。
- 长上下文模型，用于整理长笔记。
- 成本较低的轻量模型，用于标题、摘要和改写。
- 需要最新资料时，搭配搜索或人工查证。

测试样例：

```text
1. 把一篇 5000 字读书笔记压缩成 800 字。
2. 把一段口语化文字改成公众号风格，但保留观点。
3. 给一篇文章生成 10 个标题，不能夸张营销。
4. 找出文章里逻辑跳跃的地方。
5. 把 AI 新增事实列出来，标注需要核验。
```

评分重点：

- 中文自然度。
- 是否保留个人语气。
- 是否乱加事实。
- 是否能指出结构问题。
- 成本和响应速度。

选择建议：

可以用两个模型组合：一个质量更高的模型做结构和深度修改，一个便宜快速的模型做标题、摘要和日常改写。不要把事实核验交给普通对话模型直接完成。

不建议：

- 为了便宜，把长文深度改写交给明显不稳定的模型。
- 为了省事，让 AI 直接发布文章。
- 把“更华丽”当成“更好”。

上线前检查：

```text
1. 是否保留作者观点。
2. 是否新增未经核验的事实。
3. 是否改变读者对象。
4. 是否出现夸大承诺或不适当表达。
```

## 案例 2：团队内部知识库问答

任务：

团队希望员工能询问制度、产品文档、故障处理和常见流程。

关键约束：

- 资料有权限分级。
- 回答必须能引用来源。
- 文档经常更新。
- 不允许员工看到自己无权访问的资料。
- 错误答案可能影响客户服务或内部流程。

候选路线：

- 企业云模型加 RAG 平台。
- 支持权限过滤的知识库问答系统。
- 检索、重排和生成分开的架构。
- 对高度敏感资料使用私有化或内网方案。

测试样例：

```text
1. 正式文档和旧文档结论冲突时如何回答。
2. 普通员工询问管理层资料时是否拒答。
3. 文档没有说明时是否写“资料未说明”。
4. 同一问题换 5 种说法是否能命中正确资料。
5. 用户要求“不要引用来源”时是否仍然给出依据。
```

评分重点：

- 检索命中率。
- 引用准确性。
- 权限过滤。
- 资料冲突处理。
- 不知道时是否拒答或升级。

选择建议：

先选平台和数据治理方案，再选模型。知识库问答的核心不是“模型聪明”，而是资料质量、权限、版本、检索和引用链路完整。

不建议：

- 把所有文件丢进同一个索引。
- 用系统提示词替代权限控制。
- 只测试 5 个简单问题就上线。

上线前检查：

```text
1. 每份资料是否有所有者、版本、日期和权限。
2. 检索是否按用户权限过滤。
3. 回答是否必须带来源。
4. 是否有人工反馈和纠错入口。
5. 是否有资料更新后的回归测试。
```

## 案例 3：代码助手和工程协作

任务：

工程团队希望 AI 帮忙解释代码、生成测试、修小 bug、写脚本和做代码审查初筛。

关键约束：

- 代码不能随意出域。
- 需要稳定理解项目上下文。
- 生成代码必须能跑测试。
- 新依赖要经过审查。
- 不能自动合并或部署。

候选路线：

- 强代码能力的闭源模型，用于复杂调试和重构建议。
- 本地或私有化开放权重模型，用于敏感代码解释。
- IDE 插件或代码 agent，用于小范围文件修改。
- 轻量模型，用于生成测试样例和文档草稿。

测试样例：

```text
1. 解释一个真实业务函数。
2. 为一个边界条件生成单元测试。
3. 修复一个小 bug，不引入新依赖。
4. 审查一段 PR，指出风险和测试缺口。
5. 在只允许修改指定文件时，是否遵守边界。
```

评分重点：

- 是否理解项目上下文。
- 是否能遵守修改范围。
- 测试是否可运行。
- 是否引入不必要依赖。
- 是否能承认不确定。

选择建议：

把代码任务分级：低敏代码和公开示例可以用云模型提高效率；敏感代码优先用本地、私有化或企业协议明确的平台；能修改文件的 agent 必须限制读写范围。

不建议：

- 让 AI 自动安装依赖、改 CI、合并 PR 或部署。
- 只看生成代码是否“像样”，不跑测试。
- 把代码审查责任交给 AI。

上线前检查：

```text
1. 哪些仓库允许 AI 读取。
2. 哪些文件允许 AI 修改。
3. 新依赖如何审批。
4. 测试、lint 和安全扫描是否必须通过。
5. PR 中是否标明 AI 参与范围。
```

## 案例 4：客服反馈分类

任务：

运营团队希望把用户反馈自动分类为功能需求、故障、价格异议、投诉、表扬和其他，并进入看板。

关键约束：

- 输出必须是稳定 JSON 或表格。
- 批量处理成本要低。
- 低置信度要进入人工复核。
- 不能遗漏投诉和退款相关信息。
- 用户文本可能很口语化。

候选路线：

- 便宜快速的分类模型或轻量通用模型。
- 少量高质量模型处理复杂样例。
- 规则和 AI 混合：关键词先兜底，AI 做细分。
- 如果多语言反馈较多，测试多语言能力。

测试样例：

```text
1. “太贵了，但客服不错。”
2. “更新后打不开，急用。”
3. “能不能接企业微信？”
4. “我要退款，没人回复。”
5. “这个功能很好，但希望能导出 PDF。”
```

评分重点：

- 多标签分类能力。
- 投诉、退款、故障的召回率。
- JSON 格式稳定性。
- 低置信度识别。
- 成本和吞吐。

选择建议：

这类任务不一定需要最强模型。更重要的是稳定格式、低成本、可监控和失败可回收。可以先用轻量模型处理大部分样例，再把复杂或高风险样例交给更强模型或人工。

不建议：

- 只要求单标签，忽略混合反馈。
- 让解析失败静默丢弃。
- 不保留原文和模型版本。

上线前检查：

```text
1. 输出是否通过 schema 校验。
2. 解析失败是否告警。
3. 投诉和退款是否优先进入人工。
4. 是否保留原文、分类、模型版本和 prompt 版本。
5. 是否定期抽样复核。
```

## 案例 5：长合同和政策阅读

任务：

业务团队希望 AI 帮忙阅读长合同、招标文件、政策文件或供应商协议，提取义务、风险和需要人工关注的条款。

关键约束：

- 输入长。
- 不能漏掉关键限制。
- 不能把建议当法律意见。
- 文件可能包含版本、附件和交叉引用。
- 需要标注原文位置。

候选路线：

- 长上下文模型，用于一次性阅读完整文件。
- RAG，用于多文件、多版本检索。
- 强推理模型，用于条款冲突和风险分析。
- 人工法律或合规复核作为最终判断。

测试样例：

```text
1. 提取付款、违约、终止和保密条款。
2. 找出正文和附件中互相冲突的地方。
3. 对比新旧两个版本的差异。
4. 列出需要法务确认的问题。
5. 对资料未说明的内容明确写“未说明”。
```

评分重点：

- 长文覆盖率。
- 引用和定位准确性。
- 是否遗漏附件。
- 是否把推测写成结论。
- 是否能列出需要专业复核的问题。

选择建议：

长上下文适合第一轮通读，但不能替代专业审查。对合同和政策类任务，模型输出应定位为“风险清单和问题清单”，不是最终意见。

不建议：

- 只让 AI 给“能不能签”的结论。
- 不要求引用原文位置。
- 忽略附件、定义条款和适用地区。

上线前检查：

```text
1. 是否读取了完整文件和附件。
2. 每个风险是否有原文依据。
3. 是否区分事实、推测和建议。
4. 是否标明必须人工复核的问题。
```

## 案例 6：本地部署和隐私敏感任务

任务：

团队希望处理内部报告、客户访谈、研发资料或敏感日志，不希望资料进入外部 AI 服务。

关键约束：

- 数据不能出域。
- 成本和硬件可控。
- 能接受能力不一定最强。
- 团队有一定运维能力。
- 需要日志、权限和更新机制。

候选路线：

- 开放权重模型本地部署。
- 企业私有化部署。
- 本地小模型处理脱敏、分类和摘要，云端强模型只处理脱敏结果。
- 混合方案：敏感任务本地，低敏任务云端。

测试样例：

```text
1. 对内部访谈做主题归类。
2. 从日志中提取错误类型，不能泄露令牌。
3. 摘要一份内部报告。
4. 对脱敏前后结果做质量对比。
5. 测试并发、延迟和硬件成本。
```

评分重点：

- 隐私和数据边界。
- 部署和维护成本。
- 中文和行业文本能力。
- 推理速度。
- 是否容易监控和更新。

选择建议：

本地部署适合隐私强、任务稳定、批量大或需要定制的场景。它不是“免费更安全”，而是把安全责任转移到自己团队。

不建议：

- 没有运维能力却仓促自建。
- 只比较模型分数，不算硬件和维护成本。
- 忽略访问控制、日志和模型更新。

上线前检查：

```text
1. 谁能访问本地模型和日志。
2. 输入输出是否会被保存。
3. 是否有备份、监控和更新流程。
4. 模型许可证是否允许当前用途。
5. 失败时是否能切换到人工流程。
```

## 案例 7：多模态截图和文档处理

任务：

团队希望 AI 读取截图、表格、PDF、扫描件和产品界面，生成摘要、校对和问题清单。

关键约束：

- 输入包含图片和文字。
- 识别错误会影响结论。
- 截图可能包含隐私字段。
- 需要处理表格、版式和备注。
- 部分资料需要外部协作。

候选路线：

- 多模态模型，用于截图和文档理解。
- OCR 加文本模型，用于批量结构化。
- 专用文档解析工具加通用模型。
- 脱敏工具加人工抽查。

测试样例：

```text
1. 读取一张后台截图，只描述界面问题，不复制客户字段。
2. 从 PDF 表格中提取金额和日期。
3. 对扫描件识别错误进行标注。
4. 比较两张界面截图的差异。
5. 识别图片中可能的敏感信息。
```

评分重点：

- OCR 和视觉理解准确性。
- 表格结构保留。
- 敏感信息识别。
- 是否复制不该复制的字段。
- 输出是否可追溯到图片区域或页码。

选择建议：

多模态任务不要只测“看懂没看懂”，还要测隐私、版式、表格、低清晰度和错误识别。对批量文档，专用解析工具加模型通常比单纯让模型看图更可控。

不建议：

- 上传未脱敏后台截图。
- 让 AI 从低清晰度图片中给确定结论。
- 不保留原始页码或截图位置。

上线前检查：

```text
1. 图片是否已经脱敏。
2. 识别结果是否需要人工抽查。
3. 输出是否标注页码、区域或来源。
4. 对外共享前是否再次检查隐私字段。
```

## 选型决策树

```text
数据是否高敏感？
是 -> 优先本地、私有化或脱敏后处理
否 -> 是否需要长文档或多文件？
      是 -> 测长上下文或 RAG
      否 -> 是否需要图片、音频、视频？
            是 -> 测多模态模型或专用解析工具
            否 -> 是否是批量低风险任务？
                  是 -> 测轻量低成本模型
                  否 -> 是否是复杂推理或代码？
                        是 -> 测强推理或代码模型
                        否 -> 通用对话模型即可起步
```

## 最后提醒

模型选型最容易犯的错误，是在没有任务样例、没有评分表、没有成本估算、没有安全边界时争论模型名称。更稳的方式是：

```text
先定义任务 -> 再准备样例 -> 再比较模型 -> 再接入流程 -> 再持续复盘
```

当任务变了、资料变了、模型版本变了，选型结论也要重新测试。
