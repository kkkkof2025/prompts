# 前沿与过时技术案例库

最后维护：2026-05-13

这份案例库用于记录 AI 技术从“新概念、演示项目、热门框架”进入真实使用时发生了什么。它不把技术分成“值得写”和“不值得写”，而是看它能不能帮助读者理解 AI 系统怎样演进、怎样失败、怎样被吸收进下一代工具。

本页的基本判断：

- 案例可以长。只要案例有效、有特点、能帮助读者复盘，就不必为了短而删掉关键过程。
- 案例可以不止一个。同一类技术如果有不同失败方式、应用场景或治理问题，可以分别写。
- 前沿技术可以写。只要概念、来源和边界没有写错，就可以作为学习对象纳入。
- 过时技术也可以写。过时不等于没有价值，它常常能解释今天的工具为什么变成现在这样。
- 不把技术写成永久结论。模型、接口、协议和产品形态会变，案例应该保留核验日期和适用范围。

建议配合 [AI 前沿发展全景](chapters/12-frontier-landscape.md)、[Agent，从聊天到行动](chapters/08-agents.md)、[工具调用、RAG 与知识库](chapters/06-tools-rag.md)、[Skills，把经验固化成能力](chapters/07-skills.md)、[安全、伦理与治理](chapters/13-safety-governance.md)、[资源与引用](appendix-resources.md) 和 [前沿资料季度复核执行手册](frontier-review-playbook.md) 使用。

## 技术案例收录标准

一个技术案例值得写入本书，不一定因为它“最新”，而是因为它至少满足下面一项：

| 收录理由 | 判断问题 |
| --- | --- |
| 解释一类技术趋势 | 它能说明 AI 从对话、工具、工作流、agent 到协议化协作的哪一步吗？ |
| 暴露真实失败方式 | 它能展示幻觉、权限、成本、可靠性、评估或数据边界问题吗？ |
| 帮助读者做选择 | 它能帮助读者判断该用 prompt、RAG、skill、agent、工具调用还是人工流程吗？ |
| 代表一个阶段 | 它是不是某个时期常见的架构、产品形态或实践路线？ |
| 已被后来技术吸收 | 它是否解释了后来的工具为什么强调结构化输出、权限、审计、协议和评估？ |
| 有迁移价值 | 它虽然过时，但方法、失败经验或治理思路还能迁移到今天吗？ |

不建议收录的情况：

- 只有营销口号，没有可复盘的任务、输入、输出和失败证据。
- 需要大量未经核验的传闻才能成立。
- 只能证明某个产品“很厉害”，不能帮助读者学习方法。
- 涉及医疗、法律、金融、教育评价、招聘等高风险场景，却没有写清人工责任和专业边界。

## 案例写法模板

```text
技术或现象：
核验日期：
资料来源：

它当时想解决什么问题：

它有特点的地方：

它适合的任务：

它容易失败的地方：

如果今天还要使用：
需要增加哪些边界、评估、权限和人工复核。

如果它已经过时：
它留下了什么经验，哪些部分被新工具吸收。

读者练习：
让读者用一个真实任务复现、改写或复盘这个技术案例。
```

## 案例 1：插件式工具接入

### 为什么值得写

早期 AI 工具接入常用“插件”这个词来解释模型怎样连接外部服务：订票、查数据库、读网页、调用业务系统、生成文件。它的价值不只是某个插件产品本身，而是让普通用户第一次看到：AI 不只是回答问题，还可以通过外部系统采取行动。

这个阶段非常适合做学习案例，因为它暴露了一个核心问题：模型会说话，不代表它知道什么时候应该调用工具、怎样传参、怎样处理失败、怎样保护权限。

### 有特点的地方

- 它把“对话”推进到“行动”。
- 它让用户第一次关心工具权限、认证、数据范围和失败回滚。
- 它把 prompt 问题扩展成接口契约问题。
- 它让“AI 输出是否能进入下一步流程”变得更具体。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 工具描述不清 | 模型不知道什么时候调用工具，或把工具用于错误任务 |
| 参数结构不稳定 | 同一任务多次输出字段不同，后端难以接收 |
| 结果解释过度 | 工具返回有限数据，模型却补出不存在的结论 |
| 权限边界弱 | 用户没有意识到工具可能读取或修改真实数据 |
| 缺少回滚 | 执行动作后才发现输入错了、对象错了或范围错了 |

### 今天还能学什么

插件形态本身可能被新的工具调用、连接器、MCP、平台 actions 或 agent SDK 吸收，但它留下的学习价值很明确：

1. 每个工具都需要清晰的用途说明。
2. 每个参数都需要类型、范围和示例。
3. 每个高风险动作都需要确认或人工审批。
4. 工具返回值要区分事实、推测和错误。
5. 真实系统接入必须有日志、权限和回滚设计。

### 练习

选择一个你熟悉的工具，例如日历、表格、CRM、知识库或项目管理系统，写一张工具卡：

```text
工具名称：
能做什么：
不能做什么：
输入字段：
输出字段：
需要用户确认的动作：
常见失败：
人工复核点：
```

然后判断：这个工具只适合普通工具调用，还是需要放进完整 agent 工作流。

## 案例 2：早期自主 agent 演示

### 为什么值得写

早期自主 agent 演示常常给用户一种强烈印象：只要给一个目标，AI 就能自己拆任务、上网、写代码、调用工具、反思和继续执行。它们很适合作为“技术想象力”和“工程边界”的对照案例。

这类案例即使某些实现已经不再流行，也仍然重要。因为今天的 agent 设计仍然绕不开同一组问题：目标是否清楚、行动是否可控、观察是否可靠、循环什么时候停止、谁对结果负责。

### 有特点的地方

- 把“目标 -> 计划 -> 行动 -> 观察 -> 反思”做成显式循环。
- 让用户看到多步任务可以由模型持续推进。
- 也让用户看到失控循环、错误累积和成本失控。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 目标过大 | agent 不断生成计划，但没有稳定完成任何可验收产物 |
| 观察不可靠 | 搜索结果、网页内容或工具返回被误读 |
| 反思空转 | 每轮都说要改进，但下一步没有变得更具体 |
| 成本失控 | 多轮调用、搜索、代码运行和重试叠加 |
| 停止条件缺失 | 不知道什么时候应该交还给人 |
| 权限过宽 | agent 能操作文件、网络、账号或业务系统，但没有审批 |

### 今天还能学什么

早期自主 agent 的最大价值，是提醒读者不要把“会规划”误当成“能负责”。今天更稳的做法通常是：

1. 把目标拆成短链路任务。
2. 给每一步明确输入和输出。
3. 对高风险动作加人工确认。
4. 使用 traces、日志或运行记录复盘。
5. 用小评测集判断 agent 是否真的变稳。
6. 设置预算、轮次和失败退出条件。

### 练习

把一个“大目标”改成受控 agent 任务：

```text
原始目标：
帮我完成竞品分析。

受控版本：
1. 只分析 3 个公开网页。
2. 只输出功能对比、价格信息和无法确认的信息。
3. 每条事实必须带来源。
4. 不自动注册账号、不提交表单、不下载未知文件。
5. 如果信息不足，停止并列出需要人工确认的问题。
```

复盘时问：

- 哪些步骤必须由人批准？
- 哪些信息必须可追溯？
- 哪些任务不应该交给 agent 自动执行？

## 案例 3：RAG 从“向量搜索”走向“知识系统”

### 为什么值得写

很多团队第一次做 RAG，会把它理解成“把文档切片、生成向量、检索相似片段、让模型回答”。这个版本容易做出演示，但很难直接进入真实业务。

RAG 是典型的技术演进案例：它没有过时，但早期粗糙做法会过时。真正有价值的不是“向量库”这个单点，而是文档治理、权限、检索质量、引用、评估和反馈闭环。

### 有特点的地方

- 它解决模型不知道内部资料的问题。
- 它把回答质量和资料质量绑定在一起。
- 它让“知识库是否可信”成为系统问题，而不是 prompt 问题。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 文档质量差 | 旧版制度、重复文档、草稿和正式文件混在一起 |
| 切片不合理 | 检索到的片段缺少上下文，模型只能猜 |
| 权限缺失 | 用户问到了自己本不该看到的内容 |
| 引用不清 | 回答看起来像事实，但无法回到原文 |
| 评估缺失 | 只能凭感觉说“好像能用” |
| 更新流程缺失 | 文档变了，知识库没有同步 |

### 今天还能学什么

RAG 不是“把资料喂给 AI”，而是一个知识系统。最小可用版本也应该包括：

1. 资料准入规则。
2. 文档版本和更新时间。
3. 权限过滤。
4. 引用和证据片段。
5. 不能回答时的拒答规则。
6. 小型评测集。
7. 错误反馈入口。

### 练习

选一个团队知识库任务，写出 RAG 验收标准：

```text
任务：
资料范围：
哪些资料不能进入：
用户权限分级：
必须引用的字段：
不能回答时怎么说：
评测问题 5 条：
人工抽查方式：
```

## 案例 4：长上下文不是知识治理的替代品

### 为什么值得写

模型上下文窗口变长后，很多人会自然产生一个想法：既然能放更多资料，是不是就不需要 RAG、摘要、结构化输入和资料筛选了？

这个案例适合提醒读者：长上下文提升了可处理材料的上限，但不自动解决资料质量、权限、引用、冲突和成本问题。

### 有特点的地方

- 它让长文档、合同、论文、代码库和会议材料处理变得更方便。
- 它降低了复杂任务前期切片和摘要的门槛。
- 它也可能让用户更容易把大量无关或敏感信息一次性塞进去。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 输入过多 | 模型抓住显眼片段，忽略真正关键的约束 |
| 资料冲突 | 新旧版本混在一起，模型没有识别冲突 |
| 成本上升 | 每次都传大量材料，延迟和费用变高 |
| 引用松散 | 回答没有清楚对应原文位置 |
| 权限粗糙 | 不该进入上下文的内容被一起上传 |

### 今天还能学什么

长上下文适合提升阅读和综合能力，但仍然需要任务设计：

1. 先说明任务目标，再提供资料。
2. 把资料分成“必须依据、参考资料、可忽略材料”。
3. 要求模型先列出引用依据，再给结论。
4. 对冲突信息要求单独标注。
5. 对敏感材料先做筛选和匿名化。

### 练习

把“直接上传一整包资料”改成结构化输入：

```text
目标：
必须回答的问题：
资料清单：
资料优先级：
如果资料冲突：
如果证据不足：
输出格式：
```

## 案例 5：Skills 从 prompt 模板走向能力包

### 为什么值得写

prompt 模板可以复用一句话，skill 则试图复用一套能力：触发条件、操作步骤、参考资料、脚本、模板和验收标准。它代表一个重要演进：从“每次把说明塞进对话”走向“把工作方法打包给 agent 按需使用”。

根据官方文档，Agent Skills 可以把 instructions、metadata、可选资源、脚本和模板打包，并在相关任务中按需使用。这类设计很适合解释“渐进式加载”和“经验固化”。

### 有特点的地方

- 它把可复用经验从对话里移到文件和目录里。
- 它让复杂流程可以带上示例、脚本和参考资料。
- 它能减少重复 prompt，也能降低上下文浪费。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 触发条件模糊 | agent 不知道什么时候该用这个 skill |
| skill 过大 | 什么都想管，反而难以维护 |
| 示例不足 | agent 读了规则，但不知道好输出长什么样 |
| 缺少验收 | skill 执行完无法判断是否成功 |
| 脚本风险 | 脚本能读写文件或联网，但没有权限说明 |

### 今天还能学什么

skill 的核心不是文件格式，而是“把经验变成可触发、可执行、可复盘的能力”。无论使用哪家平台，都可以学习这套结构：

```text
名称：
何时使用：
不适用场景：
输入要求：
执行步骤：
可选工具或脚本：
输出格式：
验收标准：
失败处理：
示例：
```

### 练习

把你常用的一个 prompt 改写成 skill 卡。不要只写“帮我总结”，要写清：

- 它在什么任务中触发。
- 它需要哪些输入。
- 它应该先做什么、后做什么。
- 它不能替你做哪些判断。
- 它输出后怎样验收。

## 案例 6：MCP 把工具接入推向协议化

### 为什么值得写

MCP 的学习价值在于：它把“每个 AI 应用单独接一遍工具和数据源”的问题，推进到更标准化的连接方式。官方文档把 MCP 定位为连接 AI 应用与外部系统的开放标准，可连接数据源、工具和工作流。

对学习者来说，MCP 不只是一个协议名，而是一个很好的系统设计案例：当 AI 应用越来越多，工具越来越多，连接层需要从临时集成走向可复用、可管理、可审计。

### 有特点的地方

- 把工具、数据源和工作流抽象成可连接的服务。
- 让同一个 server 可以被不同 AI 客户端使用。
- 让权限、认证、能力描述和调试成为连接层问题。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 只追求能连上 | 没有定义哪些资源可读、哪些动作可写 |
| server 描述含糊 | AI 不知道工具边界，误用能力 |
| 凭据管理薄弱 | token、账号、内部地址被暴露 |
| 审计不足 | 不知道 AI 何时访问了哪个资源 |
| 安全假设过强 | 以为协议标准化就自动安全 |

### 今天还能学什么

MCP 适合放进“连接层治理”学习：

1. server 能暴露什么资源。
2. 哪些工具只读，哪些能写入。
3. 用户怎样授权和撤销。
4. 日志记录到什么粒度。
5. prompt 注入怎样影响工具调用。
6. 失败时如何降级。

### 练习

为一个假想 MCP server 写能力边界：

```text
server 名称：
连接的数据源：
只读能力：
写入能力：
禁止能力：
认证方式：
日志字段：
需要人工确认的动作：
安全测试样例：
```

## 案例 7：A2A 与 agent 互操作

### 为什么值得写

当一个 agent 只在单个应用里工作时，问题主要是工具调用和工作流控制。当多个 agent 来自不同框架、不同组织或不同系统时，问题会变成：它们怎样发现彼此、描述能力、交换消息、返回结果、处理权限和失败？

A2A 这类 agent 互操作协议的学习价值，在于让读者看到多 agent 协作不能只靠“让两个模型互相聊天”。它需要能力描述、消息结构、artifact、认证、安全和任务边界。

### 有特点的地方

- 它把 agent 协作从自然语言聊天推进到协议化交互。
- 它提醒读者区分“协作演示”和“可治理系统”。
- 它适合讨论企业场景中的跨系统代理协作。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 能力声明不真实 | 一个 agent 声称会做，但实际输出不可用 |
| 任务边界不清 | 多个 agent 互相转交，没人负责最终质量 |
| artifact 不可追溯 | 生成的文件、摘要或决策没有来源 |
| 安全继承混乱 | 下游 agent 获得了不该有的权限 |
| 失败协议缺失 | 无法区分拒绝、异常、证据不足和需要人工介入 |

### 今天还能学什么

多 agent 不是越多越好。A2A 类案例应该让读者练习：

1. 哪些任务真的需要多个 agent。
2. 每个 agent 的职责是否可验收。
3. 中间产物是否可追溯。
4. 权限是否随任务最小化传递。
5. 最终由谁批准输出。

### 练习

把一个多 agent 设想写成协议化任务：

```text
总任务：
agent A 职责：
agent B 职责：
交接消息：
中间产物：
失败时谁处理：
最终验收人：
不得自动执行的动作：
```

## 案例 8：个人 AI 助手工作台

### 为什么值得写

个人 AI 助手工作台类项目把很多能力放到一起：对话、工具、浏览器、文件、自动化、记忆、多模型和多通道操作。它们适合展示 agent 时代的真实复杂度：越接近真实电脑和真实账号，越需要权限、隔离、日志和回滚。

OpenClaw 这类个人 AI 助手工作台案例，可以帮助读者理解“一个能做很多事的助手”为什么既有吸引力，也有风险。

### 有特点的地方

- 把单次对话扩展成持续工作空间。
- 把模型能力和本地文件、浏览器、应用连接起来。
- 适合讨论个人效率、自动化和安全边界。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 权限过宽 | 助手能读写太多文件或访问太多账号 |
| 操作不可见 | 用户不知道助手具体做了什么 |
| 记忆污染 | 错误偏好或过时信息被长期保留 |
| 工具链脆弱 | 一个依赖或插件变化导致整个流程失效 |
| 误操作难回滚 | 文件、邮件、网页操作已经影响真实环境 |

### 今天还能学什么

个人 AI 助手工作台的学习重点不是“装上就用”，而是：

1. 为助手准备隔离工作目录。
2. 高风险动作先模拟后执行。
3. 所有外发、删除、购买、提交动作必须确认。
4. 记忆系统需要查看、修改和删除入口。
5. 工具、插件和依赖需要定期复核。

### 练习

设计一个个人助手边界清单：

```text
允许读取的目录：
禁止读取的目录：
允许联网的任务：
禁止自动执行的动作：
需要确认的动作：
记忆保存范围：
日志保存位置：
出错后的回滚方式：
```

## 案例 9：开放模型路线与本地部署

### 为什么值得写

开放权重模型、本地部署和私有化推理让用户看到另一条路线：不是所有任务都必须通过云端闭源模型完成。它们适合做模型选型、成本、隐私、延迟、可控性和能力边界的综合案例。

这类案例也适合解释为什么“开源/开放权重”不是一个单一答案：许可证、模型大小、推理成本、上下文、工具调用、中文能力、生态支持和安全评估都要一起看。

### 有特点的地方

- 给企业和个人更多部署选择。
- 让隐私、成本和可控性进入模型选型讨论。
- 促使读者区分模型能力、部署能力和工程能力。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 只看榜单 | 榜单任务强，不代表真实任务强 |
| 忽略许可证 | 模型能下载，不代表能任意商用 |
| 低估运维 | 推理、显存、并发、监控和升级都需要成本 |
| 忽略工具能力 | 文本能力好，但结构化输出或工具调用不稳定 |
| 没有评测集 | 换模型后不知道质量变好还是变差 |

### 今天还能学什么

开放模型路线适合训练读者的选型能力：

1. 先定义任务，不先选模型。
2. 用真实样例做小评测。
3. 同时记录质量、成本、延迟和风险。
4. 检查许可证和部署限制。
5. 为模型升级准备回归测试。

### 练习

为一个本地部署候选模型写选型表：

```text
任务：
候选模型：
许可证：
部署环境：
评测样例：
质量得分：
延迟：
成本：
不能接受的失败：
是否进入试点：
```

## 案例 10：长期记忆与个性化助手

### 为什么值得写

长期记忆让 AI 助手从“每次重新认识你”走向“持续理解你的偏好、项目、习惯和背景”。这对个人效率很有吸引力，也带来隐私、过时信息、错误记忆和可解释性问题。

HiMeS 这类个性化记忆系统研究适合作为学习案例，因为它提醒读者：记忆不是把聊天记录无限保存，而是要考虑写入、检索、更新、遗忘和用户控制。

### 有特点的地方

- 把上下文管理从单次对话扩展到长期用户模型。
- 让个性化不再只靠 prompt 临时说明。
- 迫使系统设计处理记忆质量和删除权。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 错误写入 | 助手把一次偶然选择当成长期偏好 |
| 过时记忆 | 项目、身份、职责变了，助手仍按旧信息回答 |
| 隐私不清 | 用户不知道哪些内容被记住 |
| 检索错配 | 不相关记忆进入上下文，影响回答 |
| 删除困难 | 用户无法查看、修改或清除记忆 |

### 今天还能学什么

长期记忆系统至少需要四个入口：

1. 写入规则：什么可以记，什么不能记。
2. 查看入口：用户能看到系统记住了什么。
3. 修改入口：用户能纠正错误记忆。
4. 删除入口：用户能删除敏感、错误或过时记忆。

### 练习

为个人助手写记忆政策：

```text
可以记住：
不可以记住：
每次写入前是否确认：
多久复查一次：
用户如何查看：
用户如何修改：
用户如何删除：
记忆出错时怎么纠正：
```

## 案例 11：computer use 与受控工作空间

### 为什么值得写

computer use、浏览器自动化和受控桌面让 agent 能操作真实或模拟的计算环境。它们很适合作为“能力越强，边界越重要”的案例：模型可以点击、输入、下载、运行命令或修改文件时，系统就不能只依赖一句“请小心”。

这类能力在数据录入、网页操作、测试、办公自动化和软件维护中有价值，但也最容易触碰账号、文件、支付、隐私和供应链风险。

### 有特点的地方

- 把 AI 从文本生成推进到环境操作。
- 让任务结果变成可观察的文件、页面或系统状态。
- 需要把权限、沙箱、确认、日志和回滚作为核心设计。

### 容易失败的地方

| 失败点 | 表现 |
| --- | --- |
| 页面理解错误 | 点错按钮、提交错表单、误读弹窗 |
| 文件误操作 | 覆盖、删除或移动了不该动的文件 |
| 账号风险 | 自动登录、读取消息或访问敏感页面 |
| 命令风险 | 运行未知脚本、安装不可信依赖 |
| 日志不足 | 无法复盘 agent 做过哪些操作 |

### 今天还能学什么

受控工作空间的关键不是“能不能操作电脑”，而是“怎样把操作限制在可承受范围内”：

1. 使用隔离目录或沙箱。
2. 对外发、支付、删除、提交、安装动作加确认。
3. 记录每一步观察和动作。
4. 出错时能恢复到快照。
5. 对下载文件、脚本和依赖做安全检查。

### 练习

把一个电脑操作任务改成受控流程：

```text
任务：
允许访问的网站或目录：
禁止访问的范围：
允许执行的动作：
需要确认的动作：
日志字段：
失败退出条件：
回滚方式：
```

## 技术过时后的复盘问题

当一个工具、框架、协议或产品形态不再流行时，不要急着从书中删掉。先问：

1. 它过时的是产品入口、接口形态，还是底层思想？
2. 它解决的问题是否仍然存在？
3. 它的失败是否解释了后来的工具设计？
4. 它有没有被新的平台、协议或 SDK 吸收？
5. 它是否仍然适合作为反例、历史案例或课堂讨论材料？
6. 它如果继续保留，是否需要标注“历史案例”或“截至某日期”？
7. 它是否会误导读者以为这是当前推荐方案？

建议处理方式：

| 情况 | 处理 |
| --- | --- |
| 技术仍可用且概念稳定 | 保留正文，并按季度复核 |
| 产品形态变化但思想仍重要 | 改成“技术演进案例” |
| 已不推荐直接使用但失败有代表性 | 改成“历史复盘案例” |
| 信息不确定 | 移到资源附录或复核记录，等待核验 |
| 会误导读者采取高风险行动 | 从操作教程中移除，保留风险复盘 |

## 课堂或读书会用法

可以把本页变成一次 90 分钟讨论：

```text
0-10 分钟：选一个技术案例
10-25 分钟：讨论它当时想解决什么问题
25-40 分钟：列出它的失败方式
40-55 分钟：判断哪些思想被今天的工具吸收
55-75 分钟：把案例改写成一个可控工作流
75-90 分钟：写出保留、更新或移除这个案例的理由
```

输出要求：

- 不只说“这个技术过时了”。
- 必须说明它为什么出现。
- 必须说明它解决了什么和没解决什么。
- 必须说明今天还能学什么。
- 如果建议删除，必须说明删除后读者是否会失去一个重要历史线索。

## 维护提醒

更新本页时，按以下顺序处理：

1. 如果新增前沿技术，先查 [资源与引用](appendix-resources.md) 中是否已有官方来源。
2. 如果涉及模型、协议、SDK 或平台能力，按 [前沿资料季度复核执行手册](frontier-review-playbook.md) 记录核验日期。
3. 如果是过时技术，标注它是“历史案例”“演进案例”还是“仍可使用但需复核”。
4. 如果案例很长，不因为长度删除关键过程；优先检查它是否有明确任务、失败证据、复盘问题和迁移价值。
5. 如果同一技术有多个有特点的场景，可以拆成多个案例，而不是强行压成一个概述。
