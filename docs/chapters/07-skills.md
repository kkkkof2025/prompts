# 第 7 章：Skills，把经验固化成能力

Skill 可以理解为“可复用的任务能力包”。它通常包含说明、流程、模板、示例、脚本、资源和边界条件。它比单个 prompt 更稳定，因为它把一类任务的做法沉淀了下来。

## 本章导读

- 预计阅读时间：12-18 分钟。
- 学习目标：理解 skill 解决的复用问题；写出 skill 的输入、输出、流程和边界；区分 skill、prompt 和 agent。
- 练习入口：[章节练习与验收映射表](../chapter-validation-map.md) 和 [AI Skill/Card 可复用模板](../../examples/skill-card-template.md)。
- 相关材料：[教学示范作业集](../teaching-examples.md) 和 [AI 工作流配方库](../workflow-recipes.md)。

## Skill 解决什么问题

如果你经常这样说：

```text
还是按上次那个格式。
继续用我们之前那套流程。
帮我像以前一样检查。
```

说明你需要 skill。

Skill 的价值是：

- 减少重复 prompt。
- 统一输出质量。
- 保存团队经验。
- 让 agent 在合适场景自动调用流程。
- 把工具、模板和验收标准放在一起。

## Skill 的基本组成

一个好 skill 通常包含：

- 名称：这个 skill 解决什么问题。
- 触发场景：什么时候应该使用。
- 输入要求：用户需要提供什么。
- 操作流程：按什么步骤做。
- 输出格式：交付物长什么样。
- 验收标准：如何判断完成。
- 边界：什么不能做，什么时候要询问。
- 示例：至少一个完整输入输出样例。

## 示例：会议纪要 Skill

```text
名称：meeting-notes

触发场景：
当用户提供会议录音转写、会议聊天记录或零散会议笔记，希望整理为可执行纪要时使用。

输入要求：
- 会议原始内容
- 会议主题
- 参会角色，如果有

流程：
1. 提取会议目标。
2. 区分事实、决定、待办和争议。
3. 合并重复内容。
4. 给每个待办补负责人和截止时间；缺失则标注“待确认”。
5. 输出结构化纪要。

输出格式：
- 会议摘要
- 关键决定
- 待办事项
- 风险和争议
- 待确认问题

边界：
不要编造未出现的决定、负责人和日期。
```

## Skill 和 Prompt 的区别

Prompt 更像一次性任务说明。

Skill 更像可维护资产。它可以被版本管理、团队共享、持续改进，也可以和脚本、模板、测试样例一起使用。

## Skill 和 Agent 的关系

Agent 是能计划和行动的系统。Skill 是 agent 可调用的能力。

可以这样理解：

```text
Agent = 目标管理 + 计划 + 工具 + 记忆 + skills + 权限 + 评估
Skill = 某类任务的可复用操作说明
```

没有 skill 的 agent 容易每次临场发挥。有 skill 的 agent 更容易形成稳定风格和流程。

## 设计 Skill 的原则

先从高频任务开始。不要为了显得专业而创建几十个 skill。

写清楚边界。尤其是法律、医疗、财务、隐私、删除文件、发邮件、对外发布等高风险场景。

保留失败案例。一个 skill 不只需要好例子，也需要记录哪些输入会导致失败。

定期更新。模型能力和工具接口会变，skill 也需要维护。

## 连续案例：反馈分析 Skill

[从客户反馈知识库到可治理行动助手](../cases/rag-skill-agent-memory.md) 的第 3 轮把“每周客户反馈分析”沉淀成 `customer-feedback-triage` skill。这个例子适合观察 skill 和普通 prompt 的区别：

- prompt 只说明本次要输出什么。
- skill 固定触发场景、输入要求、操作流程、输出格式和禁止事项。
- skill 把失败复盘写回流程，例如“导出慢”和“导出失败”不能只按模块合并。
- skill 让后续 agent 可以调用成熟流程，而不是每次重新临场发挥。

你写自己的 skill 时，可以先问：这个任务是否每周、每月或每个项目都会重复出现？如果答案是肯定的，就值得把 prompt 升级为 skill。

教学场景可以读 [从教学资料库到受控助教助手](../cases/teaching-rag-skill-agent-memory.md)。它把匿名化作业反馈沉淀成 `teaching-feedback-draft` skill，重点展示如何避免评价学员人格、如何把反馈指向具体文本，以及如何把正式评分保留给讲师确认。

工程场景可以读 [从代码库问答到受控修复助手](../cases/codebase-rag-skill-agent-memory.md)。它把缺陷定位沉淀成 `codebase-bug-triage` skill，重点展示如何限定读取路径、生成最小修复计划、保留测试命令，并把“不能读取秘密配置、不能自动提交推送”写进边界。

读完三条连续案例后，可以用 [连续案例练习与复盘评分表](../cases/continuous-case-exercises.md) 检查自己的 skill 是否真的可复用，还是只是把一个 prompt 换了名字。

### 如何测试你的 Skill

Skill 写好了不代表能正常工作。测试方法：

**第 1 步：准备 3-5 个真实输入**

从你过去处理过的同类任务中抽取。至少包含：
- 1 个简单输入（理想情况）
- 1 个模糊输入（信息不完整）
- 1 个异常输入（格式错误、超长、包含敏感信息）

**第 2 步：逐条运行，记录结果**

| 测试输入 | AI 输出 | 符合预期？ | 问题 |
|----------|---------|-----------|------|
| 正常会议记录 | ✅ 格式正确，待办清晰 | 是 | — |
| 只发了一句话"讨论了Q3" | ❌ 只输出"待确认"一条 | 否 | 信息太少的输入需要明确提示用户补充 |
| 超长邮件线程（5000字） | ✅ 成功提取关键信息 | 是 | 但花了 12 秒，可以在 prompt 里要求"只提取重点" |

**第 3 步：修好问题，重新跑一遍**

> 不要用同一批测试数据跑完就说"好了"。找 2 个同事用他们的真实任务跑一遍，你才会发现更多边界情况。

**第 4 步：把失败案例写进 Skill**

```text
已知失败场景：
- 如果输入少于 50 字，先提示用户补充信息，不要猜测
- 如果输入超过 3000 字，先提炼关键点再处理
- 不要处理标注为"机密"或包含身份证号/银行卡号的内容
```

### Skill 模板

如果你不知道从哪下手，直接填空：

```markdown
# Skill：{名称}

## 我什么时候用它
{描述触发场景——什么情况下你希望 AI 自动知道该怎么做}

## 用户需要给我什么
{输入要求——列举用户必须提供的信息}

## 我按什么流程做
1. {步骤1}
2. {步骤2}
3. {步骤3}

## 输出长什么样
{输出格式——表格/文本/代码/JSON？有什么结构？}

## 怎么算做好了
- {验收标准1}
- {验收标准2}

## 我不能做什么
- {禁止事项1}
- {禁止事项2}
- {什么时候必须停下来问}

## 示例
输入：{一个真实的输入}
输出：{对应的正确输出}

## 已知会出错的情况
- {什么输入会产出差结果，怎么处理}
```

把这个模板填入实际内容，就是你的第一个可复用 Skill。

## 练习

选择你最常让 AI 做的一类任务，例如：

- 写周报。
- 改简历。
- 总结论文。
- 审查代码。
- 生成短视频脚本。
- 分析客户反馈。

用 [Skill/Card 模板](../../examples/skill-card-template.md) 写一个最小 skill。先不要追求完美，只要能复用。
