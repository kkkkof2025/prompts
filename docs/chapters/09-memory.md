# 第 9 章：记忆系统与个性化助手

如果 AI 每次对话都像第一次见你，它就很难成为真正的长期助手。记忆系统的目标是让 AI 保存有用信息，并在合适时机使用。

## 本章导读

- 预计阅读时间：12-18 分钟。
- 学习目标：区分短期记忆、长期记忆、工作记忆和禁止保存内容；写一份个人记忆文件；识别记忆系统的隐私风险。
- 练习入口：[章节练习与验收映射表](../chapter-validation-map.md) 和 [常用检查清单](../appendix-checklists.md)。
- 相关材料：[Context Engineering：上下文工程](../context-engineering.md)、[安全事故复盘案例集](../safety-incident-retrospectives.md) 和 [AI 安全案例更新指南](../safety-case-updates.md)。

## 记忆分几类

短期记忆：当前对话中的上下文。关闭对话或超过上下文窗口后可能消失。

长期记忆：跨会话保存的偏好、事实、项目状态和历史经验。

工作记忆：当前任务中的中间计划、待办、临时结论。

情景记忆：与具体事件相关的记录，例如某次会议、某个项目决策。

语义记忆：更稳定的知识，例如用户偏好、术语表、项目背景。

## 什么值得记

值得记：

- 用户长期目标。
- 常用输出格式。
- 写作风格偏好。
- 项目背景。
- 重要术语。
- 反复出现的流程。
- 明确授权保存的信息。

不该随便记：

- 密码、密钥、验证码。
- 身份证、银行卡、医疗隐私。
- 未经同意的他人隐私。
- 临时情绪和一次性偏好。
- 高度敏感商业信息。

## 记忆不是越多越好

记忆太多会带来问题：

- 过时信息影响新任务。
- 隐私风险增加。
- 检索噪音变大。
- AI 可能把过去偏好错误套用到当前场景。

好的记忆系统需要更新、删除、过期和冲突处理。

> **一个"记忆腐烂"的真实例子**：
>
> 你的 `profile.md` 里写着："我在用 Vue 2 做前端项目"。
> 三个月后，你的项目已经迁移到 Vue 3 + Composition API。
> 但你忘了更新 profile。
>
> 于是每次你让 AI 帮你写代码，它都生成 Vue 2 的 Options API 写法。
> 你开始觉得"AI 怎么越来越笨了"——其实不是它笨，是你的记忆烂了。
>
> **教训**：每季度至少检查一次你的记忆文件，删掉过时内容，更新新知识。记忆的敌人不是遗忘，是"以为记得但其实是错的"。

### 记忆维护节奏

| 频率 | 操作 |
|------|------|
| 每次重要对话后 | 用"记忆更新 prompt"提取值得保存的信息 |
| 每周 | 扫一遍短期记忆，删掉一次性对话内容 |
| 每月 | 检查长期记忆是否有冲突（如"用A框架"和"已迁移到B"） |
| 每季度 | 审计隐私敏感记忆：是否误保存了不该存的？ |
| 项目/职位变更时 | 立即更新所有相关记忆文件 |

## 一个个人 AI 记忆文件

```text
# profile.md

## 基本背景
我是中文用户，主要使用 AI 做学习、写作、编程和项目管理。

## 输出偏好
- 优先使用简体中文。
- 复杂任务先给计划。
- 代码任务最后说明测试结果。

## 长期目标
- 建立一套可发布的 AI 学习方法开源书。

## 禁止保存
- 不保存账号、密码、密钥、身份证号和客户隐私。
```

## 记忆更新 prompt

```text
请从本次对话中提取值得长期保存的信息。
要求：
1. 只保存对未来任务有帮助的信息。
2. 不保存敏感信息。
3. 每条记忆写明来源和日期。
4. 如果信息可能只是临时偏好，请标注为临时。
```

## HiMeS 的启发

HiMeS 代表一种更系统的记忆思路：为 AI agent 构建分层、个性化、可长期更新的记忆系统。它提醒我们，AI 记忆不应该只是“把聊天记录塞进去”，而应该区分不同记忆类型，并设计写入、检索、更新和遗忘机制。

对普通用户来说，最重要的启发是：

- 记忆需要结构。
- 记忆需要权限。
- 记忆需要过期。
- 记忆需要被任务调用，而不是无条件注入。

## 记忆是上下文来源，不是上下文全部

memory 最大的误用，是把所有长期记录都塞进当前对话。更好的做法是把 memory 当成上下文工程中的一个来源，由任务来决定是否调用。

例如，同一个用户偏好在不同任务中的处理方式不同：

| 记忆 | 当前任务 | 是否注入 | 原因 |
| --- | --- | --- | --- |
| 喜欢简洁回答 | 写会议摘要 | 是 | 影响输出风格 |
| 喜欢简洁回答 | 做合同风险审查 | 部分注入 | 可以简洁，但不能省略风险依据 |
| 某项目采用 Node.js | 修改该项目代码 | 是 | 影响工具链和测试命令 |
| 某项目采用 Node.js | 写通用 AI 学习文章 | 否 | 与当前任务无关 |
| 过去客户投诉某功能 | 生成产品路线建议 | 需要脱敏后注入 | 原始投诉和客户身份不能直接进入上下文 |

这也是为什么 memory 需要来源、日期、权限和删除机制。没有这些元数据，记忆越多，越容易变成上下文污染。

## 连续案例：什么能记，什么不能记

[从客户反馈知识库到可治理行动助手](../cases/rag-skill-agent-memory.md) 的第 5 轮展示了一个重要边界：客户反馈本身应该进入业务知识库，不应该被个人助手随意保存为长期记忆。

适合保存到 memory 的是稳定偏好和流程经验：

- 管理层摘要要短。
- 产品版报告必须保留反馈编号。
- 工程版要区分 bug、性能、权限配置和使用误解。
- “导出慢”和“导出失败”不能只按模块合并。

不适合保存的是客户真实名称、联系人、合同金额、原始投诉、安全事件细节和未经确认的价值判断。记忆系统越强，越要写清楚禁止保存清单。

教学场景可以读 [从教学资料库到受控助教助手](../cases/teaching-rag-skill-agent-memory.md)。它强调 teaching memory 应保存课程结构、讲师偏好和匿名化共性误解，而不是保存学员姓名、成绩、原始作业或对学员能力的长期判断。

工程场景可以读 [从代码库问答到受控修复助手](../cases/codebase-rag-skill-agent-memory.md)。它强调 repo memory 应保存测试命令、模块路径、代码评审偏好和已确认的调试流程，而不是保存 API keys、access tokens、生产配置、客户数据或未公开漏洞细节。

读完三条连续案例后，可以用 [连续案例练习与复盘评分表](../cases/continuous-case-exercises.md) 检查自己的 memory 是否只保存稳定偏好和复盘经验，而不是保存隐私、秘密或未经确认的推断。

## 练习

创建一个 `profile.md`，写入：

- 你常用 AI 做什么。
- 你喜欢的回答风格。
- 你正在做的长期项目。
- 哪些信息不允许 AI 保存。

然后让 AI 基于这个文件为你定制一个学习计划。
