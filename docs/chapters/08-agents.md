# 第 8 章：Agent，从聊天到行动

聊天机器人主要回答问题。Agent 不只是回答，它会围绕目标进行计划、调用工具、观察结果、调整策略，并在一定边界内持续执行。

## 本章导读

- 预计阅读时间：15-22 分钟。
- 学习目标：理解 agent 的目标、计划、行动和观察循环；判断哪些任务适合 agent；写出允许动作、禁止动作和人工确认点。
- 练习入口：[章节练习与验收映射表](../chapter-validation-map.md) 和 [Agent 工作流安全检查清单](../../examples/agent-workflow-checklist.md)。
- 相关材料：[AI 任务选择决策指南](../task-decision-guide.md) 和 [安全事故复盘案例集](../safety-incident-retrospectives.md)。

## Agent 的基本循环

一个简化的 agent 循环：

```text
目标 -> 计划 -> 行动 -> 观察 -> 反思 -> 下一步行动 -> 完成
```

例如，让 AI agent 修复代码缺陷：

1. 阅读错误信息。
2. 搜索相关代码。
3. 推断原因。
4. 修改文件。
5. 运行测试。
6. 根据测试结果继续修复。
7. 总结变更。

## Agent 需要哪些组件

- 模型：负责理解、规划和生成。
- 工具：执行搜索、文件、代码、API、浏览器等操作。
- 记忆：保存任务状态、用户偏好和历史经验。
- Skills：调用成熟流程。
- 权限：限制能读什么、写什么、发什么。
- 评估：判断是否完成。
- 日志：记录做过什么，便于审计和回滚。

## 什么时候该用 Agent

适合 agent 的任务：

- 目标明确，但步骤需要探索。
- 需要多次使用工具。
- 需要根据中间结果调整计划。
- 有可验证的完成标准。
- 错误可以被检测和修复。

不适合 agent 的任务：

- 后果很严重但无法回滚。
- 目标本身不清楚。
- 没有验收标准。
- 涉及高风险法律、医疗、金融决策。
- 需要访问敏感数据但没有权限控制。

## 给 Agent 的任务说明

```text
目标：
请修复项目中登录页提交后无响应的问题。

边界：
- 只修改登录相关文件。
- 不要改数据库结构。
- 不要删除已有测试。
- 修改前先说明计划。

验收：
- 登录成功后跳转到 dashboard。
- 错误密码显示错误提示。
- 相关测试通过。

过程要求：
- 先阅读相关文件。
- 每次修改后运行最小相关测试。
- 最后总结修改文件和验证结果。
```

## Agent 的风险

Agent 的风险来自“行动能力”。

常见风险：

- 读取不该读取的文件。
- 修改过多无关代码。
- 调用外部 API 产生费用。
- 把草稿内容发布到外部。
- 删除数据。
- 在错误假设下长时间执行。
- 生成难以审计的复杂变更。

## Agent 安全边界

最小权限原则：只给完成任务必需的权限。

分阶段授权：先读，再计划，再写，再执行高风险动作。

可观察：保留日志、diff、命令输出和结果摘要。

可回滚：重要操作前要能恢复。

人工确认：发送邮件、支付、删除、发布、改变权限等动作必须确认。

## 连续案例：受控行动助手

在 [从客户反馈知识库到可治理行动助手](../cases/rag-skill-agent-memory.md) 中，agent 的任务不是替团队做产品决策，而是在明确边界内做几件低风险动作：

- 读取已匿名化的客户反馈知识库。
- 调用反馈分析 skill 生成内部周报。
- 检查帮助文档是否已有说明。
- 在人工确认后创建内部任务草稿。
- 输出执行日志和不确定信息。

这个案例特别适合练习“能力分层”：只读、写草稿、执行内部动作、对外发布是完全不同的风险等级。agent 可以先获得只读和写草稿权限，对外邮件、公告、修复承诺和路线图变更必须保留人工确认。

教学场景可以读 [从教学资料库到受控助教助手](../cases/teaching-rag-skill-agent-memory.md)。它把 agent 限定为受控助教：可以读取允许给 AI 的课程资料和匿名化作业，可以写反馈草稿和复盘摘要，但不能直接评分、不能给学员发送反馈、不能发布课程公告。

工程场景可以读 [从代码库问答到受控修复助手](../cases/codebase-rag-skill-agent-memory.md)。它把 agent 限定为受控修复助手：可以读取允许路径、运行相关测试、生成补丁草稿和 diff 摘要，但不能读取秘密文件，不能自动 commit、push 或部署。

读完三条连续案例后，可以用 [连续案例练习与复盘评分表](../cases/continuous-case-exercises.md) 检查自己的 agent 是否写清工具权限、禁止动作、人工确认点和日志要求。

### 实战：看一次 Agent 完整执行

以下是一次真实 agent 修复登录 bug 的执行日志（简化版）：

```text
🔄 第 1 轮
  行动: 读取 src/pages/Login.tsx
  观察: 发现 handleSubmit 函数没有处理 loading 状态

🔄 第 2 轮
  计划: 添加 loading 状态管理，防止重复提交
  行动: 编辑 src/pages/Login.tsx - 在 handleSubmit 中添加 `if(loading) return;`
  观察: 修改成功

🔄 第 3 轮
  行动: 运行 npm test -- Login.test.tsx
  观察: 3/3 测试通过 ✅

🔄 第 4 轮
  行动: 运行 git diff 查看变更
  观察: +3 行，仅修改 Login.tsx

✅ 完成
  总结: 
  - 修改 1 个文件：src/pages/Login.tsx
  - 添加 double-submit 防护
  - 相关测试全部通过
  - 未发现其他影响
```

> **从这条 trace 你能看出什么？**
> 1. Agent 不是"一次对话完成"，而是多轮循环
> 2. 每一步都先读再改，最后验证
> 3. 好的 agent 会自己检查边界（只改了 1 个文件，3 行）
> 4. 如果中间某一步失败（如测试不过），agent 会回到第 2 轮修复

**一个失败的 agent trace（对比学习）**：

```text
🔄 第 1 轮: 读取 Login.tsx
🔄 第 2 轮: 修改了 5 个文件（Login.tsx, App.tsx, router.tsx, config.ts, types.ts）
🔄 第 3 轮: 修改了 package.json，添加了 3 个新依赖
🔄 第 4 轮: npm test 失败，12 个测试报错
❌ 失控：无法确定是哪个改动导致的，也无法回滚
```

**教训**：Agent 的边界比能力重要。没有"只改 Login 相关文件"的约束，agent 会过度自由。

### Agent 权限分级

不是所有 agent 都需要所有权限。按风险从小到大分级授权：

| 级别 | 权限 | 示例任务 | 适合场景 |
|------|------|---------|---------|
| L0 只读 | 读取指定文件/目录 | 分析代码、查文档、生成报告 | 安全审查、新人学习 |
| L1 草稿 | L0 + 写草稿文件（不覆盖已有） | 生成分析报告、写周报草稿 | 日常办公辅助 |
| L2 修改 | L1 + 修改已有文件 + 运行测试 | 修 Bug、重构、更新文档 | 开发辅助 |
| L3 高风险 | L2 + 发邮件/付款/发布/删除 | 自动发布、定时任务 | 需人工确认+审计日志 |

> **升级规则**：从 L0 开始，每升级一级必须通过 5 次以上的真实任务验证。不要"我想试试 agent"就给它 L3 权限。

## 多 Agent 协作

多 agent 协作适合任务可以拆成相互独立的部分。例如：

- 一个 agent 查资料，一个 agent 写代码，一个 agent 做审查。
- 一个 agent 写前端，一个 agent 写后端。
- 一个 agent 从初学者视角读稿，一个 agent 从安全视角审查。

关键是写清楚各自的文件范围和责任边界。否则多个 agent 会互相覆盖。
