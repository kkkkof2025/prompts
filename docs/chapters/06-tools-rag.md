# 第 6 章：工具调用、RAG 与知识库

当 AI 只能聊天时，它主要依靠已有知识和你提供的上下文。当 AI 能调用工具时，它可以搜索、计算、读文件、写代码、查数据库、操作浏览器。能力更强，风险也更大。

## 本章导读

- 预计阅读时间：15-22 分钟。
- 学习目标：理解工具调用和 RAG 的区别；设计知识库边界；列出工具权限、安全检查和维护规则。
- 练习入口：[章节练习与验收映射表](../chapter-validation-map.md) 和 [常用检查清单](../appendix-checklists.md)。
- 相关材料：[Context Engineering：上下文工程](../context-engineering.md)、[团队 AI 落地手册](../team-adoption-playbook.md) 和 [AI 安全案例更新指南](../safety-case-updates.md)。

## 工具调用是什么

工具调用是让模型在需要时请求外部函数或系统。例如：

- 搜索网页。
- 查询数据库。
- 读取文件。
- 运行代码。
- 发送邮件。
- 创建日程。
- 调用企业内部 API。

模型负责判断“该用哪个工具、传什么参数、如何解释结果”。系统负责真正执行工具。

## 工具调用的边界

给 AI 工具时，要同时给边界。

```text
你可以读取 docs/ 目录下的 Markdown 文件。
你不能读取 .env、keys、credentials、客户隐私数据。
在写入文件前，先说明准备修改哪些文件。
删除文件必须先获得确认。
```

工具越接近真实世界，越需要权限控制和审计。

## RAG 是什么

RAG 是 Retrieval-Augmented Generation，通常译为检索增强生成。它的思路是：先从知识库中检索相关资料，再把资料作为上下文交给模型生成回答。

RAG 适合解决两个问题：

- 模型不知道你的私有资料。
- 模型内置知识可能过时。

一个典型 RAG 流程：

```text
用户问题 -> 查询改写 -> 检索文档 -> 排序筛选 -> 注入上下文 -> 生成回答 -> 引用来源
```

## RAG 不是万能的

RAG 常见失败点：

- 文档切分太碎，丢失上下文。
- 检索词不好，找不到正确资料。
- 找到了资料，但模型没有正确使用。
- 知识库里本身有过时或冲突信息。
- 回答没有标明引用位置。

所以 RAG 项目不只是“把文件丢进去”。你需要设计文档结构、元数据、更新流程和评估集。

## 从 RAG 走向上下文工程

RAG 解决“从哪里找资料”，但更完整的问题是“下一步应该让模型看到什么”。这就是 [Context Engineering：上下文工程](../context-engineering.md) 要处理的范围。

一个知识库问答系统至少需要同时决定：

- 检索到的资料是否真的相关。
- 哪些资料应该排在前面。
- 长资料是否需要压缩成可引用摘要。
- 过时、冲突或低权限资料是否应该隔离。
- 生成结果是否能追踪到来源。
- 当前任务是否需要调用 memory、skill、工具结果或项目规则。

所以，一个成熟 RAG 系统的下一步通常不是“把向量库换成更贵的”，而是建立上下文包：任务目标、规则、证据、权限、状态、记忆和复核标准分层进入模型。

## 建立个人知识库

个人知识库可以很简单：

```text
knowledge/
├── profile.md       # 个人背景、偏好、长期目标
├── projects.md      # 当前项目
├── writing-style.md # 写作风格样例
├── glossary.md      # 常用术语
└── sources/         # 原始资料
```

你可以在对话中告诉 AI：

```text
请优先依据我提供的 knowledge/ 内容回答。
如果知识库没有答案，请明确说明，不要猜测。
```

## 知识库维护原则

- 原始资料和总结分开。
- 每条重要信息保留来源和日期。
- 定期删除过时内容。
- 对冲突信息做标记。
- 私密资料单独存放，限制访问。

## 连续案例：客户反馈知识库

如果你想看一个完整场景，可以读 [从客户反馈知识库到可治理行动助手](../cases/rag-skill-agent-memory.md)。在第 6 章对应的部分，重点看它怎样把零散工单、社区帖子和客户成功记录整理成 RAG 知识库，并为每条结论保留反馈编号、来源、日期和隐私等级。

如果你是教师或培训者，可以读 [从教学资料库到受控助教助手](../cases/teaching-rag-skill-agent-memory.md)。它展示了怎样把课程大纲、讲义、匿名化作业和评分量规整理成教学 RAG，并避免越级讲解、引用错误和学员隐私泄露。

如果你是工程师，可以读 [从代码库问答到受控修复助手](../cases/codebase-rag-skill-agent-memory.md)。它展示了怎样把代码路径、模块说明、测试命令、API 契约和事故复盘整理成代码库 RAG，并避免读取 `.env`、密钥、生产配置和真实用户数据。

这些案例的共同关键不是“接入向量数据库”，而是先定义资料边界：

- 哪些资料可以进入知识库。
- 哪些原始资料必须脱敏、屏蔽或禁止读取。
- 哪些回答必须引用反馈编号、资料编号、文件路径或测试结果。
- 哪些结论只能写成不确定信息。
- 哪些高风险动作不能由知识库回答直接触发。

读完三条连续案例后，可以用 [连续案例练习与复盘评分表](../cases/continuous-case-exercises.md) 检查自己的 RAG 资料结构、检索评估样例和权限边界是否完整。

## 工具调用安全清单

在让 AI 使用工具前，问自己：

- 它是否真的需要这个工具。
- 工具能访问哪些数据。
- 工具能修改什么。
- 是否有删除、发送、付款、发布等高风险动作。
- 是否有日志记录。
- 是否能回滚。

## 练习

创建一个小型知识库，放入 3 篇你自己的资料。然后让 AI 回答一个问题，并要求：

```text
请只依据我提供的资料回答。
每个结论后标注来自哪份资料。
如果资料不足，请说明缺口。
```
