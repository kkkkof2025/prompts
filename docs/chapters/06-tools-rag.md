# 第 6 章:工具调用、RAG 与知识库

当 AI 只能聊天时,它主要依靠已有知识和你提供的上下文。当 AI 能调用工具时,它可以搜索、计算、读文件、写代码、查数据库、操作浏览器。能力更强,风险也更大。

## 工具调用是什么

工具调用是让模型在需要时请求外部函数或系统。例如:

- 搜索网页。
- 查询数据库。
- 读取文件。
- 运行代码。
- 发送邮件。
- 创建日程。
- 调用企业内部 API。

模型负责判断"该用哪个工具、传什么参数、如何解释结果"。系统负责真正执行工具。

## 工具调用的边界

给 AI 工具时,要同时给边界。

```text
你可以读取 docs/ 目录下的 Markdown 文件。
你不能读取 .env、keys、credentials、客户隐私数据。
在写入文件前,先说明准备修改哪些文件。
删除文件必须先获得确认。
```

工具越接近真实世界,越需要权限控制和审计。

## RAG 是什么

RAG 是 Retrieval-Augmented Generation,通常译为检索增强生成。它的思路是:先从知识库中检索相关资料,再把资料作为上下文交给模型生成回答。

RAG 适合解决两个问题:

- 模型不知道你的私有资料。
- 模型内置知识可能过时。

> **一个直观对比**:假设你的团队有一个内部 Wiki,记录了所有项目的技术架构。
>
> **不用 RAG**:
> ```text
> 你问:"我们的用户认证系统用的是 JWT 还是 Session?"
> AI:"根据常见实践,JWT 更适合分布式系统..."
> ```
> AI 在猜。它不知道你的系统长什么样。
>
> **用了 RAG**:
> ```text
> 你问:"我们的用户认证系统用的是 JWT 还是 Session?"
> AI:"根据《认证系统架构设计》(2025-03-15)第3.2节,
> 当前系统使用 JWT + Redis refresh token 双方案。
> Access token 有效期 15 分钟,refresh token 7 天。"  ← 引用来源
> ```
> 不确定 → 确定。猜测 → 引用。这就是 RAG 的核心价值。

一个典型 RAG 流程:

```text
用户问题 -> 查询改写 -> 检索文档 -> 排序筛选 -> 注入上下文 -> 生成回答 -> 引用来源
```

## RAG 不是万能的

RAG 常见失败点:

- 文档切分太碎,丢失上下文。
- 检索词不好,找不到正确资料。
- 找到了资料,但模型没有正确使用。
- 知识库里本身有过时或冲突信息。
- 回答没有标明引用位置。

所以 RAG 项目不只是"把文件丢进去"。你需要设计文档结构、元数据、更新流程和评估集。

### 实战：从零建一个 RAG 知识库

假设你要为团队建一个"产品 FAQ 知识库"，让同事问 AI 能直接引用最新的产品文档。

**第 1 步：准备文档**（结构决定质量）

```text
faq-docs/
├── 001-定价方案.md        ← 每条 FAQ 一个文件，编号+标题
├── 002-功能对比表.md
├── 003-退款政策.md
├── 004-企业版部署.md
├── 005-API限额说明.md
└── README.md             ← 索引：编号→标题→更新日期
```

> **关键规则**：一个文件 = 一个主题。不要把 50 条 FAQ 塞进一个文件，检索时召回不准。

**第 2 步：每条文档写清楚元信息**

```markdown
# 定价方案
- 来源：内部产品文档 v2.3
- 最后更新：2026-04-20
- 适用范围：所有付费用户
- 相关文档：002-功能对比表.md

正文内容...
```

**第 3 步：建评测集**（上线前先测）

```text
评测问题：
1. 企业版多少钱？ → 预期答案：按坐席计费，每坐席 ¥99/月
2. 是否能退款？ → 预期答案：购买 7 天内可全额退款
3. API 调用超过限额怎么办？ → 预期答案：自动降级，不会中断服务
```

每个问题跑一遍 RAG，检查：
- ✅ 找到正确文档了吗？
- ✅ 答案引用了来源吗？
- ✅ 没有编造信息吗？

**第 4 步：维护规则**

| 触发条件 | 操作 |
|----------|------|
| 产品功能更新 | 更新对应文件，修改"最后更新"日期 |
| 新增 FAQ | 新建编号文件 + 更新 README.md 索引 |
| 旧政策废除 | 在文件开头加"⚠️ 已失效"标记，不移除（保留历史） |
| 月度 | 跑一遍评测集，确认没有退化 |

**第 5 步：教 AI 正确使用**

```text
请回答用户问题，规则：
1. 先从 faq-docs/ 中检索相关资料
2. 每个结论后标注来源文件编号和更新时间
3. 如果知识库没有确切答案，说"目前文档中未找到相关信息"
4. 如果找到的资料标注了"已失效"，告知用户这是过时信息
```

> **五步总结**：准备结构化的文档 → 写元信息 → 建评测集 → 定维护规则 → 教 AI 正确引用。大部分 RAG 失败，是因为跳过了第 3 步和第 5 步。

## 从 RAG 走向上下文工程

RAG 解决"从哪里找资料",但更完整的问题是"下一步应该让模型看到什么"。这就是 [Context Engineering:上下文工程](../context-engineering.md) 要处理的范围。

一个知识库问答系统至少需要同时决定:

- 检索到的资料是否真的相关。
- 哪些资料应该排在前面。
- 长资料是否需要压缩成可引用摘要。
- 过时、冲突或低权限资料是否应该隔离。
- 生成结果是否能追踪到来源。
- 当前任务是否需要调用 memory、skill、工具结果或项目规则。

所以,一个成熟 RAG 系统的下一步通常不是"把向量库换成更贵的",而是建立上下文包:任务目标、规则、证据、权限、状态、记忆和复核标准分层进入模型。

## 建立个人知识库

个人知识库可以很简单:

```text
knowledge/
├── profile.md       # 个人背景、偏好、长期目标
├── projects.md      # 当前项目
├── writing-style.md # 写作风格样例
├── glossary.md      # 常用术语
└── sources/         # 原始资料
```

你可以在对话中告诉 AI:

```text
请优先依据我提供的 knowledge/ 内容回答。
如果知识库没有答案,请明确说明,不要猜测。
```

## 知识库维护原则

- 原始资料和总结分开。
- 每条重要信息保留来源和日期。
- 定期删除过时内容。
- 对冲突信息做标记。
- 私密资料单独存放,限制访问。

## 连续案例:客户反馈知识库

如果你想看一个完整场景,可以读 [从客户反馈知识库到可治理行动助手](../cases/rag-skill-agent-memory.md)。在第 6 章对应的部分,重点看它怎样把零散工单、社区帖子和客户成功记录整理成 RAG 知识库,并为每条结论保留反馈编号、来源、日期和隐私等级。

如果你是教师或培训者,可以读 [从教学资料库到受控助教助手](../cases/teaching-rag-skill-agent-memory.md)。它展示了怎样把课程大纲、讲义、匿名化作业和评分量规整理成教学 RAG,并避免越级讲解、引用错误和学员隐私泄露。

如果你是工程师,可以读 [从代码库问答到受控修复助手](../cases/codebase-rag-skill-agent-memory.md)。它展示了怎样把代码路径、模块说明、测试命令、API 契约和事故复盘整理成代码库 RAG,并避免读取 `.env`、密钥、生产配置和真实用户数据。

这些案例的共同关键不是"接入向量数据库",而是先定义资料边界:

- 哪些资料可以进入知识库。
- 哪些原始资料必须脱敏、屏蔽或禁止读取。
- 哪些回答必须引用反馈编号、资料编号、文件路径或测试结果。
- 哪些结论只能写成不确定信息。
- 哪些高风险动作不能由知识库回答直接触发。

读完三条连续案例后,可以用 [连续案例练习与复盘评分表](../cases/continuous-case-exercises.md) 检查自己的 RAG 资料结构、检索评估样例和权限边界是否完整。

## 工具调用安全清单

在让 AI 使用工具前,问自己:

- 它是否真的需要这个工具。
- 工具能访问哪些数据。
- 工具能修改什么。
- 是否有删除、发送、付款、发布等高风险动作。
- 是否有日志记录。
- 是否能回滚。

## 练习

创建一个小型知识库,放入 3 篇你自己的资料。然后让 AI 回答一个问题,并要求:

```text
请只依据我提供的资料回答。
每个结论后标注来自哪份资料。
如果资料不足,请说明缺口。
```
