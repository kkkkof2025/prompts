# 团队 AI 落地手册

个人会用 AI，不等于团队能用好 AI。团队落地需要把个人经验变成共同流程：哪些任务适合先做，哪些数据不能碰，怎样判断输出质量，谁负责维护模板和知识库，出现问题如何处理。

这份手册面向管理者、团队负责人、培训者和内部 AI 推广者。建议配合 [团队 AI 落地案例集](team-adoption-cases.md)、[AI 安全与模型选型工作坊](workshop-safety-model-selection.md)、[AI 任务选择决策指南](task-decision-guide.md)、[AI 能力评估量表](assessment-rubric.md)、[连续案例团队试点版](cases/continuous-case-team-pilot.md)、[连续案例样例库](cases/continuous-case-samples.md)、[常见误区与纠偏指南](common-pitfalls.md) 和 [安全、伦理与治理](chapters/13-safety-governance.md) 使用。

## 落地原则

先做低风险高频任务。

不要从自动审批、客户承诺、敏感数据分析或生产系统修改开始。先从会议纪要、资料整理、公开信息分析、草稿生成、内部知识库问答等任务开始。

先建标准，再扩工具。

工具可以替换，但任务说明、验收标准、数据边界和人工复核流程应该稳定。

先试点，再推广。

一个团队先跑通 2-3 个场景，比全员同时“自由探索”更容易沉淀经验。

先记录失败，再沉淀模板。

团队真正有价值的资产，不只是好 prompt，也包括失败案例、边界、检查清单和人工修改记录。

## 30 天最小落地路线

第 1 周：任务和风险盘点。

```text
目标：
找出 5-10 个适合 AI 试点的低风险高频任务。

产出：
1. 任务清单。
2. 数据分类。
3. 禁止上传清单。
4. 试点场景候选。
```

第 2 周：建立 2 个试点工作流。

```text
目标：
把两个真实任务写成可重复执行的工作流。

产出：
1. 工作流说明。
2. prompt 模板。
3. 验收标准。
4. 人工复核点。
```

第 3 周：建立小型评测和模板库。

```text
目标：
用真实样例测试工作流是否稳定。

产出：
1. 每个任务 5-10 条测试样例。
2. 评分表。
3. 可复用模板。
4. 失败案例记录。
```

第 4 周：制定团队规则并复盘。

```text
目标：
决定哪些做法可以推广，哪些必须停止或修改。

产出：
1. 团队 AI 使用底线。
2. 模板维护人。
3. 试点复盘。
4. 下一轮推广计划。
```

## 任务盘点表

先列任务，不要先列工具。

```text
任务名称：

当前做法：

频率：
每天/每周/每月/偶尔

耗时：

涉及数据：
公开/内部/敏感/客户/个人

输出用途：
个人参考/团队内部/对外发布/决策依据/系统动作

风险等级：
低/中/高

是否容易验收：
是/否

是否适合试点：
是/否

原因：
```

优先选择：

- 高频。
- 低风险。
- 输入资料明确。
- 输出容易检查。
- 有明确负责人。
- 可以复用为模板。

暂缓选择：

- 涉及敏感数据。
- 输出直接影响客户权益。
- 需要专业资质判断。
- 一旦出错难以回滚。
- 团队还说不清验收标准。

## 数据分级

团队至少把数据分成 4 类：

| 等级 | 数据类型 | 使用建议 |
| --- | --- | --- |
| 公开 | 官网、公开文档、公开报告 | 可用于普通 AI 任务 |
| 内部 | 内部流程、非敏感会议纪要 | 只在允许工具和权限内使用 |
| 敏感 | 客户资料、合同、财务、人事 | 默认禁止，除非有明确合规流程 |
| 密钥 | 密码、令牌、验证码、私钥 | 永远不输入 AI |

数据规则模板：

```text
允许输入：
1.
2.
3.

禁止输入：
1.
2.
3.

需要先匿名化：
1.
2.
3.

需要负责人审批：
1.
2.
3.
```

## 试点场景选择

推荐优先试点：

| 场景 | 原因 | 验收方式 |
| --- | --- | --- |
| 会议纪要 | 高频，格式稳定 | 待办是否准确 |
| 周报整理 | 高频，风险较低 | 进展和风险是否清楚 |
| 公开资料摘要 | 输入可控 | 是否标注来源和不确定信息 |
| 用户反馈初分 | 可保留原文证据 | 分类是否稳定 |
| 内部流程改写 | 适合模板化 | 新人是否看得懂 |
| 测试用例建议 | 可由工程师复核 | 是否覆盖边界 |

不建议第一批试点：

- 自动发送客户邮件。
- 自动审批费用。
- 自动发布公开内容。
- 自动修改生产系统。
- 自动处理员工评价。
- 自动生成法律、医疗、金融建议。

## 试点工作流模板

```text
场景名称：

目标：

适用范围：

输入材料：

禁止输入：

执行步骤：
1.
2.
3.
4.
5.

输出格式：

验收标准：
1.
2.
3.

必须人工复核：
1.
2.
3.

失败处理：

维护人：

下次复查日期：
```

判断一个试点是否成功：

- 至少连续 3 次在真实任务中有效。
- 人工修改量减少。
- 输出质量能被同一标准检查。
- 没有绕过数据边界。
- 团队成员愿意继续使用。

## 模板库建设

模板库不是 prompt 收藏夹。一个合格模板至少包含：

```text
模板名称：

适用场景：

不适用场景：

输入要求：

Prompt 模板：

输出格式：

验收标准：

常见失败：

人工复核点：

维护人：

版本记录：
```

模板入库标准：

- 已经用真实任务测试。
- 有明确输入要求。
- 有验收标准。
- 有失败案例。
- 不包含敏感数据。
- 有维护人。

模板下线标准：

- 结果长期不稳定。
- 依赖过时工具能力。
- 引发数据或安全风险。
- 已被更好的模板替代。
- 没有人维护。

## 知识库建设

团队知识库不要从“把所有文件丢进去”开始。先选一个小范围：

- 新人常问问题。
- 产品公开说明。
- 内部流程手册。
- 已确认的项目规则。
- 常用术语和写法规范。

知识库文件最小元信息：

```text
标题：
来源：
负责人：
适用范围：
创建日期：
最后更新：
权限：
过期规则：
```

知识库问答验收标准：

- 回答必须标注依据。
- 资料没有说明时写“资料未说明”。
- 不把旧资料当新结论。
- 不回答权限外问题。
- 对高风险问题提示人工确认。

## 评估机制

团队 AI 评估不需要一开始很复杂。先建立小型评测集：

```text
任务名称：

测试样例数量：

正常样例：

边界样例：

高风险样例：

评分维度：
1. 准确性
2. 完整性
3. 可执行性
4. 格式稳定性
5. 安全边界

合格线：

复测周期：
```

评分建议：

| 分数 | 含义 |
| --- | --- |
| 1 | 不能使用 |
| 2 | 需要大量人工重做 |
| 3 | 可作为草稿 |
| 4 | 少量修改后可用 |
| 5 | 稳定可复用 |

不要只看：

- 回答是否流畅。
- 字数是否很多。
- 语气是否积极。
- 是否看起来专业。

必须看：

- 是否符合事实。
- 是否有依据。
- 是否能进入下一步。
- 是否保留风险。
- 是否遵守数据边界。

## 团队角色分工

小团队也需要基本分工：

| 角色 | 责任 |
| --- | --- |
| 业务负责人 | 决定试点场景和验收标准 |
| 模板维护人 | 维护 prompt、工作流和 skill |
| 知识库维护人 | 管理资料来源、权限和更新 |
| 安全负责人 | 定义禁止数据和高风险动作 |
| 使用者 | 按规则使用并记录反馈 |
| 审查者 | 抽查输出质量和边界 |

一个人可以兼任多个角色，但责任不能消失。

## 治理底线

团队至少写清：

```text
哪些数据可以输入 AI：

哪些数据禁止输入 AI：

哪些工具允许使用：

哪些输出必须人工复核：

哪些动作禁止自动执行：

重要任务如何记录日志：

发生错误谁负责处理：

多久复查一次规则：
```

高风险动作默认人工确认：

- 删除。
- 发送。
- 发布。
- 支付。
- 审批。
- 改权限。
- 修改生产环境。
- 保存长期记忆。

## 推广节奏

不要用一次培训完成全部推广。建议节奏：

```text
第 1 轮：一个团队、两个低风险场景。
第 2 轮：增加模板库和评估集。
第 3 轮：扩展到相邻团队。
第 4 轮：建立知识库和治理例会。
第 5 轮：考虑 agent 和工具调用试点。
```

每轮复盘 5 个问题：

```text
1. 哪些任务真正节省了时间？
2. 哪些输出质量不稳定？
3. 哪些数据边界被误解？
4. 哪些模板值得保留？
5. 下一轮应该扩大、暂停还是修改？
```

## 常见失败模式

只买工具，不改流程。

结果是每个人都在单独摸索，组织没有沉淀。

只收集 prompt，不做验收。

结果是模板很多，但质量无法判断。

只追求效率，不管边界。

短期看起来快，长期会带来隐私、版权、合规和责任风险。

把 AI 输出当最终结论。

AI 可以生成草稿和分析，但团队仍需要负责人做判断。

过早引入 agent。

如果普通工作流和模板都没跑通，agent 只会放大混乱。

## 团队 AI 例会模板

每两周开一次 30 分钟例会即可：

```text
1. 本周期新增的 AI 使用场景。
2. 最成功的一个案例。
3. 最明显的一次失败。
4. 是否出现数据或安全问题。
5. 哪些模板需要更新。
6. 哪些资料需要进入或移出知识库。
7. 下一周期试点任务。
```

会议产出：

- 更新模板。
- 更新禁止清单。
- 记录失败案例。
- 调整试点范围。
- 明确负责人和截止时间。

## 90 天成熟度路线

第 1 阶段：个人探索。

表现：

- 成员各自使用 AI。
- prompt 分散在个人文档里。
- 输出质量靠个人判断。

下一步：

- 收集 3 个真实成功案例。
- 选 2 个低风险场景做试点。

第 2 阶段：团队试点。

表现：

- 有少量共用模板。
- 有基本禁止上传清单。
- 有人工复核意识。

下一步：

- 建立模板库。
- 建立小型评测集。
- 指定维护人。

第 3 阶段：流程沉淀。

表现：

- 高频任务有工作流。
- 模板有版本记录。
- 知识库有来源和权限。

下一步：

- 建立质量抽查。
- 训练团队使用同一验收标准。

第 4 阶段：治理化使用。

表现：

- 有数据分级。
- 有日志和事故处理流程。
- agent 和工具调用有权限边界。

下一步：

- 评估更多自动化场景。
- 定期审查权限、记忆和知识库。

## 最后提醒

团队 AI 落地不是“让大家多用 AI”，而是把 AI 放进可检查、可复用、可治理的工作系统。

最小可行目标不是全员都会写复杂 prompt，而是：

```text
每个高频任务都有清楚输入、稳定输出、验收标准、人工复核点和维护人。
```
