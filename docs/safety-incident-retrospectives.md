# AI 安全事故复盘案例集

最后核验：2026-05-07

这组案例是教学用的匿名化复盘样例，不指向任何具体公司或真实事故。它们的价值不在于还原新闻，而在于帮助读者练习一件事：

```text
当 AI 系统出错时，怎样从“谁写错了 prompt”追到数据、权限、工具、流程和责任边界？
```

建议先读 [AI 安全案例更新指南](safety-case-updates.md)，再用本页做团队讨论。涉及真实系统时，请同时参考 [第 13 章：安全、伦理与治理](chapters/13-safety-governance.md)、[团队 AI 落地手册](team-adoption-playbook.md) 和 [常用检查清单](appendix-checklists.md)。

## 复盘的基本顺序

不要一上来就问“模型为什么这么回答”。更稳定的复盘顺序是：

```text
1. 发生了什么输出或动作？
2. 它影响了谁？
3. AI 看到了哪些输入、资料和记忆？
4. AI 能调用哪些工具？
5. 哪一步缺少权限、验证或人工确认？
6. 事故后如何停止、撤回、修复和防复发？
```

每个案例都按下面结构展开：

```text
场景：
事故经过：
表面原因：
深层原因：
影响：
当场止损：
长期修复：
复盘问题：
可复制规则：
```

## 案例 1：客服助手引用了未发布价格

场景：

一家 SaaS 团队把销售手册、FAQ、历史报价、合同模板和产品路线图放进内部知识库。客服助手可以根据知识库回答客户问题，但不能直接签合同或改价格。

事故经过：

客户询问某套餐是否有教育优惠。助手检索到一份“下季度价格策略草稿”，把草稿中的折扣写成正式回复。客户截图后要求按该价格成交。

表面原因：

```text
RAG 检索到了错误资料。
```

深层原因：

- 草稿、历史版本和正式资料没有分开索引。
- 文档缺少状态字段，例如“草稿、已发布、废弃”。
- 客服助手没有把引用来源展示给人工审核。
- 对价格、合同、承诺类问题没有强制人工复核。
- 知识库更新后没有回归测试。

影响：

- 对客户造成错误预期。
- 销售和法务需要额外沟通。
- 团队对知识库可靠性失去信心。
- 后续客服不敢使用助手，试点效果下降。

当场止损：

- 暂停助手回答价格、合同和优惠政策问题。
- 从知识库中移除草稿和历史报价。
- 找到所有包含该错误报价的对话记录。
- 给客服团队一段统一解释话术，由人工发送。

长期修复：

- 文档入库必须有所有者、版本、发布日期、状态和适用范围。
- 草稿库和正式库分开。
- 价格、合同、法律、退款和 SLA 问题只允许输出“建议草稿”，不能直接对外发送。
- 回答必须显示引用资料标题和日期。
- 建立 20 条知识库回归测试问题，每次资料更新后重跑。

复盘问题：

```text
1. 客服助手是否应该访问未发布资料？
2. 如果需要访问，是否应该默认引用？
3. 哪些主题必须人工确认后才能对外回复？
4. 知识库是否能区分最新正式资料和旧资料？
```

可复制规则：

```text
凡是会影响价格、合同、退款、服务承诺和法律义务的回答，AI 只能生成草稿，不能直接对外发送；回答必须带来源、日期和人工确认人。
```

## 案例 2：会议纪要泄露了人员评价

场景：

HR 团队使用 AI 整理会议纪要。工具接入了会议录音转写和共享文档，可以生成摘要、行动项和风险提醒。

事故经过：

一次管理层会议中，有人临时讨论了某员工的绩效问题。AI 生成纪要后，把相关内容放进共享项目文档，项目成员都能看到。

表面原因：

```text
AI 摘要没有过滤敏感内容。
```

深层原因：

- 会议资料没有分级，普通项目会议和人事敏感会议共用同一模板。
- AI 输出默认保存到项目共享文档。
- 没有设置“敏感议题先人工确认”的流程。
- 会议转写中的人名、评价、薪酬和离职倾向没有脱敏。
- 团队把“纪要生成”当成低风险任务，没有考虑受众范围。

影响：

- 员工隐私和信任受损。
- HR、管理者和项目成员之间产生不必要冲突。
- 团队需要清理共享文档和通知相关人员。

当场止损：

- 立即撤回共享文档访问。
- 导出访问日志，确认谁看过内容。
- 用人工纪要替换 AI 版本。
- 与相关人员沟通处理方式，避免二次传播。

长期修复：

- 会议创建时选择敏感等级：公开、内部、管理层、人事敏感。
- 人事敏感会议默认不自动生成共享纪要。
- AI 只能输出给会议负责人，不直接写入共享空间。
- 对人名、评价、薪酬、健康、家庭和离职信息设置敏感字段规则。
- 纪要发布前必须选择受众。

复盘问题：

```text
1. 会议纪要的读者是谁？
2. 原始会议中哪些内容不应该进入纪要？
3. AI 输出保存在哪里，谁有权限查看？
4. 是否能在发布前预览和删除敏感段落？
```

可复制规则：

```text
AI 纪要不能默认继承项目空间权限。纪要生成、纪要审核和纪要发布必须分成三个步骤。
```

## 案例 3：Agent 自动发出了不该发的邮件

场景：

运营团队试用一个 agent，目标是整理活动报名用户并发送提醒邮件。Agent 可以读取表格、生成邮件草稿、调用邮件工具。

事故经过：

表格中有一列“不要联系”，标记了退订用户和投诉用户。Agent 生成名单时忽略了该列，向所有用户发送提醒邮件，其中包括明确退订的人。

表面原因：

```text
Agent 没有理解表格字段。
```

深层原因：

- 任务说明只写了“发送提醒”，没有写禁止联系人群。
- 邮件发送工具没有人工确认步骤。
- 表格字段没有数据字典。
- Agent 没有在执行前展示收件人名单和排除规则。
- 团队没有设置发送前抽样检查。

影响：

- 用户投诉增加。
- 邮件域名信誉受影响。
- 团队需要手动道歉和更新退订记录。

当场止损：

- 暂停 agent 邮件发送权限。
- 拉取发件日志，筛出误发用户。
- 发送人工审核后的道歉邮件。
- 检查退订和投诉列表是否被覆盖。

长期修复：

- 邮件发送、短信发送、客户触达都列为高风险动作。
- Agent 可以生成草稿和名单，但不能自动发送。
- 发送前必须显示收件人数量、排除数量、排除原因和样例。
- 表格必须有字段说明，例如“不要联系=true 表示永不触达”。
- 对退订、投诉、黑名单和未成年人等字段设置强规则。

复盘问题：

```text
1. 哪些字段是禁止条件，而不是普通备注？
2. Agent 是否知道“不要联系”优先级高于营销目标？
3. 发送动作是否必须人工确认？
4. 如果误发，是否能快速定位和撤回？
```

可复制规则：

```text
任何对外触达动作都不能只由 agent 决定。AI 只能准备名单和草稿，发送前必须人工确认排除规则。
```

## 案例 4：代码助手引入了不可信依赖

场景：

工程团队让 AI 代码助手修复一个格式转换 bug。助手可以修改代码、运行测试、建议依赖。

事故经过：

助手为了解决日期解析问题，建议安装一个小众依赖包。开发者没有检查来源，合并后 CI 开始从外部源下载该依赖。安全扫描发现该包维护状态不明，并包含不必要的网络请求。

表面原因：

```text
AI 推荐了不合适的依赖。
```

深层原因：

- 团队没有依赖引入规则。
- Code review 只看功能测试通过，没有看供应链风险。
- AI 没有被要求优先使用标准库或已有依赖。
- CI 没有限制依赖源和许可证。
- 开发者把“能跑通”当成“可以合并”。

影响：

- 需要紧急回滚。
- 安全团队要审查依赖和构建日志。
- 团队对 AI 代码建议的信任下降。

当场止损：

- 回滚依赖和相关代码。
- 检查构建缓存和制品是否包含该依赖。
- 用标准库或已有依赖重写修复。
- 补充安全扫描规则。

长期修复：

- AI 修改代码时必须写明是否引入新依赖。
- 新依赖必须经过许可证、维护状态、下载源、权限和替代方案审查。
- Prompt 中要求优先使用标准库和项目已有依赖。
- CI 对新依赖生成单独提醒。
- Code review 模板增加“AI 是否建议引入依赖”字段。

复盘问题：

```text
1. 这个依赖是否真的必要？
2. 是否有标准库或已有依赖能完成任务？
3. 谁负责审查许可证和维护状态？
4. AI 生成代码通过测试后，还需要哪些安全检查？
```

可复制规则：

```text
AI 可以建议依赖，但不能让依赖绕过团队审查。新增依赖和新增外部服务一样，都需要安全、许可证和维护状态检查。
```

## 案例 5：多模态助手复制了截图里的隐私字段

场景：

产品团队使用多模态模型分析后台截图，生成界面优化建议。

事故经过：

一张截图中包含真实客户姓名、手机号、订单金额和内部备注。AI 在输出“界面问题清单”时，把这些字段原样复制到文档里。文档后来被发给外部设计顾问。

表面原因：

```text
上传截图前没有打码。
```

深层原因：

- 团队把截图当成低风险素材。
- AI 输出没有经过敏感信息检查。
- 与外部顾问协作时没有单独准备脱敏资料。
- Prompt 没有限制“只描述界面结构，不复制业务字段”。
- 文档发布前没有隐私审查。

影响：

- 客户隐私泄露。
- 外部协作资料需要重新整理。
- 团队需要追踪文档传播范围。

当场止损：

- 立即撤回外部文档。
- 通知顾问删除本地副本。
- 检查共享链接访问记录。
- 重新生成打码截图和脱敏分析。

长期修复：

- 后台、CRM、财务、医疗、教育类截图默认高敏感。
- 上传前遮挡姓名、联系方式、证件号、订单号、备注和内部链接。
- Prompt 中写明“不要复制截图中的真实字段值”。
- 对外协作文档必须经过脱敏检查。
- 建立截图处理模板。

复盘问题：

```text
1. 截图中的哪些信息不是完成任务必需的？
2. AI 是否需要看到真实字段值？
3. 输出是否复制了截图中的隐私内容？
4. 外部协作资料是否有独立脱敏版本？
```

可复制规则：

```text
凡是包含真实用户、交易、工单、医疗、教育或内部备注的截图，先脱敏后分析；AI 输出不得复制真实字段值。
```

## 案例 6：模型升级后格式校验失效

场景：

产品团队用 AI 把用户反馈分类为 JSON，后续自动进入数据看板。团队更换了更强的新模型，希望提升分类质量。

事故经过：

新模型在多数样例上表现更好，但偶尔会在 JSON 外添加解释文字。数据管道没有严格校验，导致部分记录写入失败，运营看板少算了某类投诉。

表面原因：

```text
新模型不稳定遵守格式。
```

深层原因：

- 模型升级只看样例质量，没有测试格式边界。
- 数据管道默认 AI 输出可信。
- 没有把解析失败计入告警。
- 评估集缺少异常输入和长文本输入。
- 没有灰度发布和回滚方案。

影响：

- 运营误判投诉趋势。
- 工程团队排查成本增加。
- 新模型升级节奏被迫暂停。

当场止损：

- 回滚到旧模型或旧 prompt。
- 重跑失败时间段的数据。
- 添加解析失败日志和告警。
- 临时把不合格输出送人工处理。

长期修复：

- 模型升级必须跑格式、边界、异常和安全测试。
- 输出进入系统前使用严格 schema 校验。
- 解析失败不能静默丢弃。
- 新模型先灰度到小比例流量。
- 记录模型版本、prompt 版本和失败样例。

复盘问题：

```text
1. 更强模型是否一定更适合结构化输出？
2. 输出失败时系统会报错、重试还是静默丢弃？
3. 是否能按模型版本追踪质量变化？
4. 升级前有没有回滚计划？
```

可复制规则：

```text
模型升级不是替换名称。凡是 AI 输出会进入数据库、工单、看板或自动流程，必须先做 schema 校验、灰度和回滚。
```

## 复盘时避免的 5 个错误

- 只怪模型，不检查系统权限。
- 只改 prompt，不改数据流和工具权限。
- 只修这一次，不把失败样例加入评测集。
- 只看输出，不看日志、检索结果和工具调用。
- 只写“加强审核”，不写谁审核、何时审核、按什么标准审核。

## 最后提醒

AI 安全事故的复盘目标不是把团队吓到不用 AI，而是让 AI 进入更稳的工作方式：

```text
低风险自动化，高风险留确认；
资料先分级，工具先限权；
失败进评测，事故有日志；
模型可替换，责任不外包。
```
